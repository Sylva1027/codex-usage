## WorkBuddy 数据源可行性评估（只调研，未改代码）

- 数据位置：`%USERPROFILE%\.workbuddy-ai\projects\<cwd-slug>\<sessionId>.jsonl`，旁挂 `<sessionId>\tool-results\*.txt`（须跳过）。
- 记录类型：`message` / `function_call` / `function_call_result` / `reasoning` / `session-meta` / `ai-title` / `file-history-snapshot`。
- 用量在 `providerData.usage`（camelCase）+ `providerData.rawUsage`（OpenAI 风格）；`message.usage`（snake_case）是同值冗余，只能取一份。
- **去重关键**：一个模型响应会产生 N 条同 `providerData.messageId` 的 `function_call`（并行工具调用），usage 只挂在其中一条。实测 26 条 function_call / 14 次响应，直接累加放大 1.86 倍。按 messageId 去重。
- **口径**：`inputTokens == prompt_tokens == prompt_cache_hit + prompt_cache_miss`，输入**已含缓存**；与 Claude 相反，不能再加 cache_read。cached=`inputTokensDetails[0].cached_tokens`，reasoning=`outputTokensDetails[0].reasoning_tokens`。
- **模型身份缺口**：Auto 模式写 `model=default-model` / `requestModelName=Auto`（本机 7/15 事件），价目表无法识别；`rawUsage.credit` 是备选费用口径（deepseek 线路为 0）。
- 无请求时长 → TPS 不支持；`traces/` 的 generation span 有 duration 但 traceId 与 session 记录无法对齐。
- **分类冲突**：`.workbuddy-ai` 同时有 `sessions/` 和 `projects/<slug>/*.jsonl`，现有 `claudeHomeLooksUsable` 只看结构 → 会把它误判成 claude-home（甚至 codex-home）。WorkBuddy 判定必须排在 Claude 之前，且最好内容感知（存在 `session-meta`/`function_call`）。
- 结论：可行性高、难度低—中；`src/workbuddy-usage.js` 预计 350–420 行，全链路改动约 900–1100 行，编码 6–10 小时，真机验收需 2–3 天观察期。
- 待用户决策：Auto 事件如何计价、是否做 TPS、是否纳入 `~/.codebuddy` 等其他 home。

## 第四轮：WAL 异常增长定位（2026-10-21）

- 现场：`usage-index.sqlite` 240MB，`-wal` 从 5.09GB 涨到 5.43GB（约 23MB/分钟），`checkpoint_seq` 卡在 12，1,322,419 帧 / 58,679 页 ≈ 22.5 倍冗余。
- 触发：每次 `GET /api/status` 都会触发 sync，每次 sync 追加 10–24MB。
- 根因（高置信）：`usage-executor.js:131-168` 在整个 sync 期间用第二连接 `BEGIN` + `SELECT` 钉住读快照，所有提交的自动 checkpoint 都越不过该快照 → BUSY；下次 sync 又在写前钉新快照，checkpoint 永远轮不到。次要放大：每轮重写 `perf_codex_projections` 86MB。
- 影响：页面开着时约 33GB/天；崩溃恢复要重放 5GB；备份 5.6GB。
- 建议修复：sync finally 中读者关闭后 `PRAGMA wal_checkpoint(PASSIVE/TRUNCATE)` + `journal_size_limit`，或缩短快照生命周期。未实施，需重启服务。
- 证据文档：`docs/validation/2026-10-21-wal-growth/README.md`。
- **归属已证实**：psutil 查到 PID 135340（node src/cli.js run，cwd=本项目）同时持有 usage-index.sqlite / -shm / -wal 三个句柄；路径由 `usage-store.js:1828` 写死。
- 库参数：`auto_vacuum=0`、`freelist_count=4 页(16KB)`、`synchronous=FULL`、`journal_size_limit=-1`、`wal_autocheckpoint=1000`。VACUUM 当前只能回收 16KB。
- 修复要点：sync finally 读者关闭后 `wal_checkpoint(TRUNCATE)` + `journal_size_limit=64MB`；根因是把快照读者缩到单请求；顺序必须 checkpoint → VACUUM。
- 文档落点：`docs/plans/2026-10-21-workbuddy-source-plan.md` §3.4 增加"为什么两种模式体积一样（白板/卷轴 + freelist）"与"VACUUM 与空间回收"两小节；`docs/validation/2026-10-21-wal-growth/README.md` 增加归属确认、checkpoint 四种模式对比、一次性处理顺序、监控与回归；`docs/02-tasks.md` 候选区新增 WAL 待修条目。
