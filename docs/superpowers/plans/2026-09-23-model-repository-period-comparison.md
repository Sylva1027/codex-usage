# 模型与仓库多时间范围用量对比：实施计划

> 交接对象：下一位实施模型。本文是任务清单；本轮仅新增计划文档，没有修改应用代码。

**目标：** 在 Web UI 中按模型和仓库同时比较今日、本周、本月、全部的 token 消耗。每个单元格可查看可信的输入、缓存输入、未缓存输入、输出、推理输出和缓存命中率；Git 仓库中的不同工作目录归为同一仓库。

**范围：** 本地 Web UI、SQLite 索引、完整报告与静态 HTML 导出。保留现有时间趋势、自定义/最近范围、CLI 摘要和现有 API 字段。`Unknown model` 保留为独立分组；本次不提供手动模型归属功能。

**技术栈：** Node.js 22.13+、`node:sqlite`、原生 ES Modules、原生浏览器 JS/CSS、`node:test`。项目位于 `E:\12 AI\ccusage\codex-usage`；目前是 GitHub ZIP 解压目录，**没有 `.git` 元数据**。

## 0. 开始前的事实与基线

- 当前 SQLite `events` 表只有 `project`（原始 `cwd`）和五项数值；`UsageStore.groupedRange()` 只汇总当前范围。`/api/usage` 的普通路径使用 SQLite，`detail=full` 使用完整报告。不要把四列对比建立在全量事件数组上。
- `public/app.js` 对静态快照单独运行 `summarize(report)`。静态导出路径不能依赖运行中的 API，也不能在浏览器里访问文件系统来识别 Git 根目录。
- 当前模型和项目列表显示的是所选范围的总量；详细数值在 tooltip 中。新增四列对比表应有可点击、可键盘操作的展开明细，不能只依赖悬浮。
- 本轮基线 `npm.cmd test` 为 **63 项中 61 通过、2 失败**：`cud command opens the dashboard by default` 因 Windows 无 symlink 权限报 `EPERM`；`cli stop terminates all running usage services from the state file` 期望退出码 `[0,0]`，实得 `[1,1]`。实施时先记录此基线；新功能验收必须让新增和相关测试通过，不把这两个既存失败误判为新回归。

## 1. 产品与数据契约

### 1.1 页面行为

- 在现有时间趋势下增加“按模型比较”和“按仓库比较”两张表。每行一个模型或一个仓库；列固定为今日、本周、本月、全部，数值为该组在该范围内的 **总 token**。
- 行集合取四个范围的并集，默认按“全部”总量降序；相同总量时按稳定的名称排序。某范围无事件显示 `0`。保留 `Unknown model` 和 `Unknown cwd` 行，以便各列可与全局总量对账。
- 选择一个数值后，在该行下方展示该范围的明细：总量、输入、缓存输入、未缓存输入、输出、推理输出、缓存命中率，以及缺失明细的 token 数。再次选择则收起；键盘 Enter/Space 可操作，焦点与 `aria-expanded` 正确。移动端允许横向滚动表格并固定行名，不能挤掉数字。
- 四列是**相互重叠**的范围，页面需明确说明不可相加。四列使用当前机器本地时区和现有 `resolveDateRange` 规则；周一为本周起点，今日/本周/本月截止到今日结束，全部覆盖可用事件。它们不随页面顶端所选范围改变；顶端筛选仍控制旧图表和旧列表。
- 现有“项目目录”列表改名为“仓库分布”，采用与新表相同的仓库身份；若仍需要原始路径，将它显示在展开信息/tooltip 中。旧 API `summary.projects` 可以保留作兼容字段，新增字段应命名清楚，避免无声改变外部消费者语义。

### 1.2 建议 API 形状

在 `/api/usage` 和 `/api/summary` 的普通响应增加 `periodComparison`，不修改现有 `summary`：

```json
{
  "asOf": "2026-09-23T00:00:00.000Z",
  "periods": [
    { "key": "today", "start": "...", "end": "..." },
    { "key": "week", "start": "...", "end": "..." },
    { "key": "month", "start": "...", "end": "..." },
    { "key": "all", "start": "...", "end": "..." }
  ],
  "models": [
    {
      "key": "gpt-6-astra",
      "name": "gpt-6-astra",
      "periods": {
        "today": { "total": 0, "knownInput": 0, "cached": 0, "output": 0, "reasoning": 0, "unattributedDetailTokens": 0 }
      }
    }
  ],
  "repositories": []
}
```

`periods` 对每行必须包含四个 key；具体字段名可调整，但服务端与静态快照要一致。每次请求捕获**同一个 `asOf`**，供四个范围共用，避免跨午夜时列边界不同。前端不要从格式化字符串反推数值。

### 1.3 token 口径

- Codex 原始 `input_tokens` **包含** `cached_input_tokens`。`uncachedInput = knownInput - cached`，`cacheHitRate = cached / knownInput`（分母为 0 时显示 `—`）；`reasoning` 是 `output` 的子集，绝不能再加进总量。不要用五项之和重算 `total`。
- `total` 始终是记录报告的总量。对只提供总量、缺少拆分的事件，保留总量并标记 `detailAvailable=false`，不把缺失字段伪装成真实的 0。对混合分组，展示可核实的已知明细并附“另有 N token 明细未提供”；命中率只以已知输入为分母，并注明是已知部分。纯总量记录各明细显示“明细未提供”。
- 在源解析时依据字段**是否存在**和数值一致性判断明细可用性；不能只因模型是 `Unknown` 就判缺失，也不能单凭数值为 0 判断缺失。对输入/缓存/输出有部分字段的外部项目日志，保留可用字段的语义，不能把未知字段作为真实 0。定义一套明确的事件级完整性标志或各字段可用性标志，并在 SQLite、完整报告和静态快照中保持一致。
- 保留原始模型名；没有可信事件级模型证据时用 `Unknown model`。之前查到本月 9 条、合计 1,361,582 token 的 Unknown 记录没有可靠的模型与拆分信息；线程级模型值不构成逐 token 归属证据，**不要自动改成 `gpt-5.5`**。如未来加入手动归属，须单独标明来源且不补造明细。

## 2. 分阶段实施任务

### Task 1：事件的仓库身份与明细可用性

**文件：** `src/usage-core.js`，新建 `src/repository-identity.js`（建议），`test/usage-core.test.js`，新建 `test/repository-identity.test.js`（建议）。

- [ ] 为会话日志与项目用量日志统一产出：原始 `cwd`、规范化仓库 key、展示用仓库路径、归组类型（Git / 普通目录 / 未知）、明细可用性。`parseSessionFile`、流式路径和 `buildUsageReport` 必须共用相同判定。
- [ ] Git 根目录：从存在的 `cwd` 向上查找最近的 `.git` **目录或文件**（涵盖 worktree），把同仓库子目录归到该根。每个不同 `cwd` 缓存一次查找；绝不可对每个 token 事件重复访问磁盘或启动 Git 子进程。路径不存在/不可访问时退回规范化 `cwd`，不要丢事件；无 `cwd` 归 `Unknown cwd`。不要把仅同名的不同仓库合并。
- [ ] Windows key 折叠盘符和路径大小写，统一分隔符、尾随分隔符与 `.`/`..`；展示路径保留可读的原始大小写。对存在的路径可使用 `realpath` 消除别名；对失效历史路径采用词法规范化。POSIX 路径保持大小写敏感。规定 UNC、盘符根目录和 Git worktree 的行为，并写对应测试。
- [ ] 对真实 0、纯总量、完整拆分和部分拆分分别写解析测试；明确缓存输入不能大于已知输入，以及源字段不一致时如何保留总量和标明不可对账部分。

### Task 2：SQLite 派生索引与四范围查询

**文件：** `src/usage-store.js`，`test/usage-store.test.js`。

- [ ] 扩展 `events` schema，保存原始目录、仓库 key/名称/类型及明细可用性；为仓库 key 建索引。当前 schema 版本为 1，升级时必须能打开已有数据库：采用有版本号的迁移或一次性重建派生索引，并确保中断后可恢复，不能让 gateway 因“版本不支持”永久无法启动。保留文件级增量更新能力。
- [ ] 添加四范围分组查询。用一个 `asOf` 和 `resolveDateRange` 生成边界，在 SQLite 中对模型与仓库分别聚合四范围，避免重新解析 JSONL 或把全量事件载入内存；单次请求可执行固定数量的 SQL 查询。所有范围均返回完整四 key 和稳定排序。
- [ ] 分组结果保留 `total`、可核实明细、无明细 token 数；全局列总量与所有模型行及所有仓库行分别对账。不要让现有 Top 25 截断影响对比表的合计；数据量大时由前端做搜索/分页或展开。
- [ ] 用冻结时钟测试午夜、月初、周一、本地时区与空库；用混合完整/纯总量事件测试缺失标记和命中率分母；用两种大小写的 Windows 子目录测试仓库归并；测试 v1 索引升级、文件变化后的增量重建与中断恢复。

### Task 3：API 与完整报告/静态快照一致性

- [ ] 对同一固定样例比较 SQLite API、完整报告和静态快照的模型/仓库分组、四列总量、明细可用性；包含导入的 `.codex-usage/usage.jsonl`。服务器自动刷新后新对比表随同一 fingerprint 更新。

## 完成定义

四列可同时比较模型与仓库，能展开可信明细；SQLite、完整报告、离线快照三条路径给出相同分组与数值；已有索引可升级、增量刷新继续有效；所有新增测试通过，既有测试差异有解释。实施模型不得把缺失 token 拆分或模型名称猜测成已知事实。
