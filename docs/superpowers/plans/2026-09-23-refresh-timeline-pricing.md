# 自动刷新、时间分布与计价完善计划

> 2026-09-23；仅供后续实现。本次不修改应用代码。目标是让本地服务和静态导出呈现一致的时间图表，同时把 API 等价费用的估算依据说清楚。

## 当前实现核查

- `public/app.js` 的 `startAutoRefresh()` 只负责每 60 秒创建定时器，没有关闭入口；`visibilitychange` 在页面恢复可见时也会直接检查。`loadUsage()` 不管用户意愿都会写回“自动刷新 开”。静态快照固定不刷新。
- `completeHourlyTimeline()` 只为单日小时视图及最近 1 天视图补空桶。当前“本周”“本月”默认按天，但没有补齐未来日期，少量数据导致柱子过宽。`drawTimeline()` 的文字画在槽位左边，而柱子画在槽位中央，横轴与柱子不齐。
- 后端 SQLite 的 `timelineRange()`、普通报告、浏览器静态摘要均只按渠道细分；缺少“时间桶 × 模型”与“时间桶 × 模型花销”。
- `src/pricing.js` 按 Standard 短上下文单价计算，`src/usage-store.js` 又先按模型和明细状态汇总，因此无法按单次请求判断长上下文。当前价格说明也明确承认未处理缓存写入与服务等级。
- 抽查最近 3 份原始 Codex 会话日志的字段结构：`event_msg.payload.info.last_token_usage` 含 `input_tokens`、`cached_input_tokens`、`cache_write_input_tokens`、`output_tokens` 等；`info.model_context_window` 是模型窗口容量。抽查的 `turn_context` 与 `token_count` 顶层字段没有服务等级。不能把“没有字段”解释成 Standard。

## 一、自动刷新开关

涉及 `public/index.html`、`public/app.js`、`public/styles.css`、`test/app-autorefresh.test.js`。

1. 把状态文字拆成稳定的 DOM：`自动刷新`、真正的 `<button type="button">开/关</button>`、间隔、上次检查或错误信息。按钮加下划线，开态绿色、关态橙色，保留明显的键盘焦点与 `aria-pressed`；不要通过状态消息整段 `textContent` 覆盖按钮。
2. 本地服务默认开启。关闭时立即 `clearInterval`，阻止 `visibilitychange`、首次加载完成后的回调及已排队的检查继续触发自动请求。已有请求返回后如果开关已关闭，也不得再触发自动重载；可用开关状态和请求代号/`AbortController` 处理竞态。手动“强制重扫”仍可使用。
3. 重新开启时立即检查一次，然后保持单个 60 秒定时器；连续切换不重复建定时器。把用户选择存入 `localStorage`，刷新页面后沿用；无存储权限时在当前页面有效。`上次检查`显示最后**成功**检查时间，关闭后保留该时间，不伪造新时间。检查失败单独显示错误，不改变开态。
4. 静态快照显示“自动刷新 关”及快照说明，按钮禁用或不渲染；避免暗示可以从静态文件启动轮询。

## 二、固定时间槽与横轴

涉及 `src/usage-core.js`、`src/usage-store.js`、`public/app.js`、相应摘要/图表测试。统一写一个按本地日历生成时间槽的函数，后端报告、SQLite 与静态摘要复用同一规则。

1. 默认粒度下：“今日”补 `00`—`23` 共 24 个小时槽；“本周”从周一到周日补 7 个日槽；“本月”从 1 日到月末补 28/29/30/31 个日槽。没有用量的过去时段以及尚未来到的日子只占位置，不画伪零高度柱。**只补图表槽位，统计范围仍截止今天，顶部总量和趋势比较不能计入未来日期。**
2. “今日”横轴用两位小时 `00`—`23`；“本周”用 `周一`—`周日`；“本月”用两位日期 `01`—月末。悬浮提示与无障碍标签仍给完整本地日期/时间，避免跨月或跨年时歧义。
3. 柱子和刻度都以 `slotX + slotWidth / 2` 为中心。柱宽应有上限（建议约 24–32 CSS px），即使只有少数槽也不变成宽方块；总槽数很多时仍受槽宽限制。优先保持图内完整，不出现横向滚动。窄屏可抽样展示刻度文字，但每个槽和悬浮区域必须保留。
4. 用户手动改为其他粒度时，保留其选择；`周一—周日` 和 `01—31` 格式只在“本周/本月 + 按天”成立时使用。其他粒度采用适合该桶的短标签，避免给按周汇总误贴“周一”。自定义、最近、全部遵循选定粒度，不强行补成一个自然周或月。
5. 用本地日历的 `setDate()`/构造日期生成日槽，覆盖跨月、跨年、闰年和夏令时测试；静态导出与服务端的槽位数量、键、顺序应相同。

## 三、图表标题与三种展示模式

涉及 `public/index.html`、`public/app.js`、`public/styles.css`、`src/usage-core.js`、`src/usage-store.js`、`src/static-export.js`、图表/摘要/API 测试。

1. 右上角日期范围统一为所选统计边界的**本地日历日期**：`YYYY-MM-DD 至 YYYY-MM-DD`，包括当天同日重复显示；不再显示 `HH:MM` 或 `· 按小时`。最近 1 天的跨日范围显示两天的日期，精确时间仍可放在 `title`/悬浮提示中。顶部“粒度”下拉框保留。
2. 在日期范围旁新增紧凑、可键盘操作的三态选择控件：`按渠道`（默认）、`按模型`、`按花销`。切换模式不重新定义筛选范围和时间粒度，也不改变顶部数据；支持浅色/深色主题。切换时动态更新纵轴单位、图例、提示和 canvas 的 `aria-label`。
3. `按渠道`：保持各时间槽按渠道堆叠 token，沿用现有渠道颜色。
4. `按模型`：各时间槽按模型堆叠 token；模型名缺失归入 `Unknown model`。同一模型在时间槽间用同一颜色，颜色映射也应在两种主题下清晰可辨。可将前几个模型的图例直接展示，其余放在紧凑弹出层；不要重新引入可滚动明细列表。悬浮提示给出该槽总 tokens 和各模型准确数量。
5. `按花销`：各时间槽按模型堆叠**美元估算费用**，纵轴及提示改为 `$`，各段使用与“按模型”相同的模型颜色。先按单次事件计价，再聚合成“时间槽 × 模型”，不能先把整天 tokens 汇总后判长上下文。图表小数与现有价格卡片一样显示两位；悬浮提示可提供更多位，避免很小的非零费用看成严格零。
6. 设计统一的时间槽数据结构，例如 `{key, total, channels, models, costByModel, pricedTokens, unpricedTokens, pricingStatus}`。本地服务、普通报告、静态快照保持同样语义。未知模型价格或缺少计价字段时**不要用 `$0.00` 伪装免费**：费用柱只累加可估算部分，提示写明未计价 tokens；标题或图例注明“已计价估算”。切换模式和自动刷新后仍按当前选择展示，数据变化时可重绘。

## 四、计价准确性：第 6 点的结论及实现顺序

**结论：长上下文有条件能判断，Fast mode 目前不能从本项目已经解析的字段可靠判断；现有计价确实需要修改。** 这些金额属于“按 API 单价折算的估算”，不能直接称为用户实际账单。

1. **缓存写入先修正。** 最新原始日志确有 `cache_write_input_tokens`，而解析器和 SQLite 索引目前丢弃该字段。核对 `last_token_usage` 与累积量差值的对应关系后，逐事件读取并保留缓存写入数以及“字段是否存在”。依据官方口径，普通输入 = 总输入 − 缓存读取 − 缓存写入；三类输入 tokens 分别按普通、缓存读取、缓存写入费率计价，缓存写入费不是附加在普通输入费上的第二笔钱。未知写入量与明确的 0 必须区分。费用说明更新；必要时把现有“缓存未命中”金额拆成普通输入与写入费用明细，但本次 UI 需求不强制增加第三行指标。
2. **长上下文按请求判。** 官方 GPT-6 等模型规定：单次提示输入 **超过 272K** tokens 时，该次请求的全部输入及缓存相关费率为短上下文的 2 倍、输出费率为 1.5 倍，不是只对超出 272K 的部分加价。`model_context_window` 只是可用容量，不能拿它判本次是否长上下文。优先核对 `last_token_usage.input_tokens` 是否对应一次模型请求、与累积差值是否一致；仅在可建立这种对应关系时依据**该次请求总输入**分类。日/周累计输入超过 272K 不代表存在长上下文请求。模型不适用该规则时按该模型官方价格表处理。
3. **Fast mode 按实际响应等级判。** 官方 API 响应的 `service_tier` 才表示实际使用的等级；请求侧指定 Fast 也可能降为 Standard 并按 Standard 计价。`fast` 与旧名 `priority` 按官方兼容规则归一。最近抽查的会话日志 `token_count`/`turn_context` 字段未包含该等级；要先审计其他来源或可关联的账单/API 用量数据。如果没有可靠字段，保留清楚标注的 Standard 情景估算，显示“服务等级未知，可能与实际费用不同”，不能根据模型名、速度或上下文窗口猜 Fast。
4. **改成本模型与索引。** `src/pricing.js` 改为按模型、请求时价格版本、上下文级别、服务等级及三类输入量计算；保存计价状态/缺失原因，明确未来价格变动如何重算历史估值。`src/usage-core.js`、`src/usage-store.js`、静态导出传递新字段。SQLite 升级 schema 后应强制重索引旧源文件，或把历史新字段置为 `unknown`，避免旧记录被误认为写入 0 或 Standard。现有 `GROUP BY model, detail_mask` 的先汇总计价路径也须更换，确保与逐请求规则一致。
5. 用代表性单次请求校验短上下文、恰好 272K、超过 272K、Fast、Fast 降级、缓存读/写、旧模型、缺失字段、未知模型的费用。核对 `按花销` 的所有时间槽加总与顶部同一范围的费用估算（可计价部分）一致；对照官方用量/账单做抽样校验时只称“估算吻合程度”，别用本地 tokens 声称真实支付额。

## 推荐实施顺序与验收

1. 先做自动刷新开关及生命周期测试：关闭后 60 秒和页面重新可见时均无自动请求，手动刷新可用；重新打开只产生一个轮询器；静态快照不轮询。
2. 做统一时间槽和刻度绘制测试：本周 7 槽、本月 28/29/30/31 槽、今日 24 槽；周一/日、月初/月末、未来空槽、跨年与窄屏横轴居中；统计总量与改动前相同。
3. 先核对原始日志的请求粒度、缓存写入及等级字段，再修正计价与索引迁移；同步修正费用说明。
4. 接入三模式数据、图例、纵轴和提示。用同一组样本分别走本地 API、普通报告、静态导出，核对每槽模型之和等于该槽 tokens，费用之和等于顶部**已计价估算**。切换日期/粒度/模式和自动刷新后无状态错乱。

## 官方依据

- [GPT-6 Luna model pricing](https://developers.openai.com/api/docs/models/gpt-6-luna)：超过 272K 输入时整次请求的长上下文规则及 Fast 倍率。
- [Fast mode guide](https://developers.openai.com/api/docs/guides/fast-mode)：实际响应 `service_tier`、`priority` 别名、可能降级。
- [Prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching)：缓存写入是独立输入价格类别，官方成本公式。
