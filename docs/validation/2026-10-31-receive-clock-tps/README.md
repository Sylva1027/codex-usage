# 接收时钟修复与验收

2026-10-31。首个优化版引擎已构建；实际二进制验收进一步发现完整 HTTP 分块跨多次读取时的首批扣除问题。帧边界修正已通过整合测试并冻结，正在重新构建 release。尚未进行本轮生产切换或再次重启 Desktop，GitHub release 待新包实际采用验证后替换。

## 已确认的错误

此前 v6 的逐层数值一致，并不能证明接收时间正确。自然请求出现 680 个参考 token / 15 ms；进一步用本机一次发出 1,100 个 SSE 片段复现了同类问题。

1. Tokio 的协作调度可以在队列仍有数据时返回 Pending。旧逻辑把预填满的队列分成了 9 个接收批次。
2. 仅去掉协作调度影响仍不够。Hyper 的 HTTP/1 body 队列会跨调度轮交付同一次 IO 已收到的字节；实际 HTTP 反例仍产生 854 token / 11 ms。
3. DSH 使用的 fetch 消费队列也可跨微任务交付同批内容。900＋200 两批输出中，旧采集误把首批的 366 个 token 加进后续窗口。

这些时间差来自本机排队和交付，不代表模型生成。修正没有引入速度上限、最短时长、倍数或端到端耗时回退。

## 实际二进制验收发现的帧边界问题

首个 release 引擎 `b2ce963e` 构建用时 45 分 35 秒。测试发送端先发现 `response.cork()` 不保证整批数据只有一次 socket 写入；一次所谓缓冲发送实际上调用了 1,108 次写入。发送端改为同时 cork socket，并断言实际内容写次数后，单批测试通过；16 条路径仍有一条两批 SSE 测试将 200 错计为 811。

剩余错误是完整 HTTP 分块跨异步读取时被拆成不同生成批次。帧边界修正把同一协议帧覆盖的接收段绑定到同批，保留最后接收时刻，并把同次接收的后续帧一并归入该批。首批完成时刻同步更新，避免只扣部分首批或把其传输时间留在分母。数据字节、流式交付、费用与用量不变。HTTP/1 新回归 121 项、HTTP/2 核心 63 项、Codex API 整合 238 项通过。`b2ce963e` 未安装或发布。

确定性反例把首批 900 个 token 放在同一 HTTP 分块中，拆为两次接收并间隔 40 ms；后批 200 再间隔 140 ms 到达。修正后只计后批 200，计时从首批接收完成后开始。另覆盖同批多个正文 lane、跨帧读取剩余字节、后续独立批次，以及终止事件不能延长输出时间。

## 修正后的采集

Codex 的 HTTP/1 时间戳在实际 IO 读取时生成，跟随数据穿过 body 队列；HTTP/2 将收到的字节范围映射到 DATA 帧，再随流队列交付。消费者读取到的是对应帧的原时间戳，不是消费时刻或连接的最新时间戳。连续 Ready 读取归为同批，真正的 IO Pending 才开始下一批；读取不受 Tokio 协作预算制造的 Pending 影响。

SSE 独立接收泵保留批次信息，后续事件解析和消费者暂停不重新计时。WebSocket 接收泵也排除协作调度造成的假边界。HTTP 请求使用 identity 编码，压缩响应不套用未压缩帧时钟。

DSH 的 fetch 采集合并同一轮 IO 中跨微任务交付的片段，保留原响应字节、取消和背压行为。WorkBuddy 的 Node HTTP 采集在对应反例中未复现此错误，保留既有实现。

计数口径沿用用户确认的统一本地分词：完整正文、拒绝文本、函数参数和自定义工具输入按完整 lane 编码一次；按最终 UTF-8 token 结束位置分配到窗口，扣除首批全部字节。分母是窗口区间并集。思考内容、协议字段和工具执行不计入；原始账单用量与费用独立保留。

这是本机观察到的实际输出速度。服务端或中间网络的缓冲仍会影响收到内容的节奏，本机观测不能反推出服务端逐 token 的内部解码时间。

## 版本与历史

当前方法为 tps-v7，Codex 原生摘要为 schema 4，投影版本为 v8；DSH companion 为 schema 2，WorkBuddy companion 仍为 schema 1。旧 schema 3 与 DSH schema 1 不作为修正后的接收证据。v1 至 v6 保留历史方法归属、用量和模型身份，不重标为新测量。

冷归档继续识别 v6 的参考 token 证据，按其原方法验证与恢复；不会误要求它提供旧式外部计时。只有 v7 进入当前速度统计。新证据必须精确绑定请求身份，不能用热库临时状态代替可恢复的归档证据。

另修复了未变化的 DSH/WorkBuddy 文件在升级后继续复用旧样本的问题：两条读取路径的文件指纹包含统计方法版本。升级会重新读取已有采集，失败仍保留原指纹供下次重试，不要求用户改动会话文件或删除索引。

schema 23、RANGE/SYNC、费用、排序和界面结构保持现有行为。没有增加 UI 说明；当前源码的 public 目录未修改。
