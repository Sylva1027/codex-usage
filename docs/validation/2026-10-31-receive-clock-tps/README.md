# 接收时钟修复与验收

2026-10-31。已确认一次应用写入也可能在客户端分成多个真实接收批次。当前源码为 tps-v8 / 原生 schema 5，以 100 ms 的观察精度处理初始传输碎片；Rust 241 项及 Codex 读取、索引回归 156 项通过，优化版引擎正在构建。尚未进行本轮生产切换或再次重启 Desktop，GitHub release 待新包实际采用验证后替换。

## 已确认的错误

此前 v6 的逐层数值一致，并不能证明接收时间正确。自然请求出现 680 个参考 token / 15 ms；进一步用本机一次发出 1,100 个 SSE 片段复现了同类问题。

1. Tokio 的协作调度可以在队列仍有数据时返回 Pending。旧逻辑把预填满的队列分成了 9 个接收批次。
2. 仅去掉协作调度影响仍不够。Hyper 的 HTTP/1 body 队列会跨调度轮交付同一次 IO 已收到的字节；实际 HTTP 反例仍产生 854 token / 11 ms。
3. DSH 使用的 fetch 消费队列也可跨微任务交付同批内容。900＋200 两批输出中，旧采集误把首批的 366 个 token 加进后续窗口。

这些时间差来自本机排队和交付，不代表模型生成。后续真实 socket 核验还发现了传输碎片问题，处理规则见下文；没有速度上限、倍数或端到端耗时回退。

## 实际二进制验收发现的帧边界问题

首个 release 引擎 `b2ce963e` 构建用时 45 分 35 秒。测试发送端先发现 `response.cork()` 不保证整批数据只有一次 socket 写入；一次所谓缓冲发送实际上调用了 1,108 次写入。发送端改为同时 cork socket，并断言实际内容写次数后，单批测试通过；16 条路径仍有一条两批 SSE 测试将 200 错计为 811。

剩余错误是完整 HTTP 分块跨异步读取时被拆成不同生成批次。帧边界修正把同一协议帧覆盖的接收段绑定到同批，保留最后接收时刻，并把同次接收的后续帧一并归入该批。首批完成时刻同步更新，避免只扣部分首批或把其传输时间留在分母。数据字节、流式交付、费用与用量不变。HTTP/1 新回归 121 项、HTTP/2 核心 63 项、Codex API 整合 238 项通过。`b2ce963e` 未安装或发布。

确定性反例把首批 900 个 token 放在同一 HTTP 分块中，拆为两次接收并间隔 40 ms；后批 200 再间隔 140 ms 到达。修正后只计后批 200，计时从首批接收完成后开始。另覆盖同批多个正文 lane、跨帧读取剩余字节、后续独立批次，以及终止事件不能延长输出时间。

## 修正后的采集

每条输出 lane 的每个生成阶段，以首次可见输出为起点，把前 100 ms 内的内容作为初始基线；同一原始接收批次若跨过这个边界，仍完整纳入基线。基线 token 结束位置与最后接收时刻一起推进，其后的可见输出除以实际时间差。只有这个时间差达到 100 ms 才形成测量；不会把窗口长度当作实际耗时，也不延迟原始流或删减内容。

这是一项明确的采样精度约定，用来避免把几毫秒的网络传输碎片当成可辨认的生成过程。比如首批 900 被拆成 382 和 518，间隔 9 ms，后批 200 在第 158 ms 到达：计数为 200，耗时为 149 ms。一次性回包分成 0/1 ms 两段不形成测量；持续 10、50、100、200、600 和 2,000 token/s 的确定性输入保持原速。短阶段保留用量，长阶段继续参与统计，不按速度高低筛选。

Codex 的 HTTP/1 时间戳在实际 IO 读取时生成，跟随数据穿过 body 队列；HTTP/2 将收到的字节范围映射到 DATA 帧，再随流队列交付。消费者读取到的是对应帧的原时间戳，不是消费时刻或连接的最新时间戳。连续 Ready 读取归为同批，真正的 IO Pending 才开始下一批；读取不受 Tokio 协作预算制造的 Pending 影响。

SSE 独立接收泵保留批次信息，后续事件解析和消费者暂停不重新计时。WebSocket 接收泵也排除协作调度造成的假边界。HTTP 请求使用 identity 编码，压缩响应不套用未压缩帧时钟。

DSH 的 fetch 采集合并同一轮 IO 中跨微任务交付的片段，保留原响应字节、取消和背压行为。WorkBuddy 的 Node HTTP 采集在对应反例中未复现此错误，保留既有实现。

计数口径沿用用户确认的统一本地分词：完整正文、拒绝文本、函数参数和自定义工具输入按完整 lane 编码一次；按最终 UTF-8 token 结束位置分配到窗口，扣除首批全部字节。分母是窗口区间并集。思考内容、协议字段和工具执行不计入；原始账单用量与费用独立保留。

这是本机观察到的实际输出速度。服务端或中间网络的缓冲仍会影响收到内容的节奏，本机观测不能反推出服务端逐 token 的内部解码时间。

## 版本与历史

当前方法为 tps-v8，Codex 原生摘要为 schema 5，投影版本为 v9；DSH companion 为 schema 3，WorkBuddy companion 为 schema 2，标准测量携带 `samplingWindowMs: 100`。旧原生版本不作为新测量；v1 至 v7 保留历史方法归属、用量和模型身份。

冷归档继续识别 v6/v7 的参考 token 证据，按其原方法验证与恢复；不会误要求它提供旧式外部计时。只有 v8 进入当前速度统计，且需要相应精度证据。新证据必须精确绑定请求身份，不能用热库临时状态代替可恢复的归档证据。

另修复了未变化的 DSH/WorkBuddy 文件在升级后继续复用旧样本的问题：两条读取路径的文件指纹包含统计方法版本。升级会重新读取已有采集，失败仍保留原指纹供下次重试，不要求用户改动会话文件或删除索引。

schema 23、RANGE/SYNC、费用、排序和界面结构保持现有行为。没有增加 UI 说明；当前源码的 public 目录未修改。

随后构建的 release `5d5be13d` 在 TLS/HTTP2 的 8 条路径通过；首次 SSE/WebSocket 验证为 14/16，两条大批 SSE 分别计入 518、226 个 token，预期均为 200。追查发现，隔离环境仍会读取 Windows 系统代理；代理重分块后，客户端收到的 HTTP chunk 与测试服务器写出的 chunk 不同。仅核对发送端原始字节不足以证明客户端帧边界。

使用与引擎完全相同的 release 依赖复现：默认代理路径计入 518，显式直连及子进程精确设置 `NO_PROXY=127.0.0.1,localhost` 均计入 200，直连重复 20 次通过。实际 CLI 和 app-server 的 TCP 四元组及 PID 也确认连接直达本机测试端口，两条均计入 200。修正仅作用于 localhost 测试子进程，没有改变用户代理、模型路由或产品配置。

修正测试环境后，16 条路径为 15/16。剩余 `exec-large-buffered-ws` 将一次性发送的 1,100 个 delta 算成 718 token / 1 ms。该包仍未安装或发布。进一步诊断同时记录原始 AsyncRead 和解析消息的 Pending：初步运行中，缓冲回包的 1,100 个字符属于同一批次，真实两批输出保持 900/200；尚未据此解释完整引擎中的反例。一次应用写入也不保证一次网络读取，必须区分真实传输分段与解析、调度造成的假边界。

加入实际消息泵及预热后的重复诊断捕获了相同分割边界：服务器一个 `_writev` 的首批 900，在接收端变成 382＋518，间隔约 9 ms，期间原始 AsyncRead 确实返回 Pending。后续 200 保持独立。这证实仅靠底层 Pending 也无法认定服务端正在生成，因而增加上述统一时间精度；没有把这条反例改成通过。
