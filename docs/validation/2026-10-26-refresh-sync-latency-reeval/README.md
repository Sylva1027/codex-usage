# 历史保留完成后的刷新性能复测

日期：2026-10-26。状态：**隔离复测与评估完成，原计划已修订为 v3；产品优化尚未实施。** 范围仅为隔离测量、评估与文档，不是优化效果验收。

## 结论与建议

当前卡顿有可重复的后端成本，不宜先通过关闭 spinner、增加响应缓存或拆进程处理。首先修正“缺失但保留的历史来源反复被当成新的文件集合变化”的规划判据，同时去除逐文件整映射复制；之后处理 Magpie 的增量关联与条件性第二轮。查询、前端和读写分离按这些改动后的残余进入。

历史保留账本已完成 **20/20**，但功能交付不等于生产数据已经封存。本次一致性副本有 **0 个 archive segments**，135,880 条 events 仍在热库；测到的是最终工作树处理当前实际全热数据的表现，不能外推为实际冷热淘汰后的表现。本轮没有执行封存、迁移或重启正式服务。

## 资源预算

沿用仓库 `scripts/run-with-memory-limit.ps1` 的 Windows Job Object。测量进程树硬上限 **7,168 MiB**，Node heap 上限 **1,536 MiB**，为控制程序预留最多 1 GiB；同一时间只跑一棵服务/浏览器测量树。准备使用 1,024 MiB / heap 512 MiB，小型结果汇总与只读检查使用 128 MiB 或控制预算。

Job 限制的是整树提交内存，不应写成已测得的整树 RSS 峰值。Node RSS 包含其 worker，Chromium 子进程另受同一 Job 约束。正式直接基线 Node 高水位约 **1.01 GiB**，浏览器试验 Node 记录峰值 **1.27 GiB**；周期中 RSS 会回落至约 0.35–0.42 GiB，采样的整机可用内存最低 **13.95 GiB**。没有内存触限或资源余量中止；这不构成任意时长无泄漏的证明。未以 heap 限制冒充 RAM 限制，未运行百万级放大、2×/4×输入或并行全仓门禁。

## 剩余瓶颈

### 1. 保留的缺失路径反复触发整 home 规划

静止库有 1,394 条 Codex source_files，但只发现 1,388 个当前文件；差的 **6 条是保留历史**，关联 **14,416 events / 359 perf_samples**。不得通过删除它们换取速度。

`syncRound()` 从全部已保留 source_files 构造 `oldPaths`，再与实时 `expectedPaths` 比较。HTTP 插桩证实暖态 `pathSetChanged=true`，而 metadataChanged、dirty、degraded、partial、policyNeedsUpgrade、unkeyable 均为 false。这个触发原因足以使每轮重新进入 `planStableCodexHome()`。

正式 20 轮每轮都读取 **1,388 份完整前缀 / 2,803,376,137 bytes**，前缀阶段 p50 **2,046 ms**；另有约 **791 MB** 的同步读取，包含其它探针，不能全部称作全文解析。计数为 API 实际返回字节，可能命中 OS 缓存，不代表同量物理磁盘 I/O 或同时占用的 RAM。暖态 fold 只有 6 次，说明已有投影/未受影响线程复用正在生效，不能再说每轮都全文解析并折叠所有线程。

建议先让“已确认缺源且保留的事实”与“本轮实时发现集合”各自承担正确职责：真实缺失、回归、替换仍触发必要重规划，稳定缺失不再每轮触发。先测这个修正的净收益，再决定是否需要改变前缀证据表示。

### 2. 逐文件整映射复制仍是固定热点

正式 20 轮每轮 fingerprints getter **1,595 次**、warnings getter **1,594 次**，合计复制 **5,695,557 个条目**。两个复制阶段平均各约 **638 / 630 ms**，合计约 **1.27 s/轮**；这是同轮两个互不嵌套的阶段均值，不是端到端提速承诺。

建议复用现有轮内视图，只读校验按键取值；保留写方副本、提交后更新与回滚隔离。不要把所有 getter 一律改为共享对象。

### 3. Magpie 成本是变化触发，第二轮是有条件的

正式 20 个无变化样本均只有 **1 次 syncRound**；暖态 Magpie 导入检查 p50 **0.44 ms**。因此撤回“每次刷新必有两轮 / 固定全历史导入”的表述。

控制增量后，Magpie 阶段约 **1.84–3.01 s**，总折叠调用约 **2,764–2,773 次**，应按导入包围阶段与折叠子阶段分别看，不能相加。第一组 index=7（第 8 个周期）已复现 **2 次 syncRound / 5,606,757,880 bytes 前缀读取 / sync 12,321 ms**，第二轮存在 dirty timing thread。返回的 updatedFileCount 只是最后一轮计数，不能把这个整次增量误记成“无变化”。范围应针对 ledger/native/publication 变化时的全历史关联，以及证据实际改变后重复的发现/规划；必要的性能发布、迟到关联和失败恢复仍须保留。

仅改变 ledger 的自动检查没有发现 source fingerprint 变化。建议把 ledger 的变化检测与相关请求/线程增量关联一起评估，避免时长证据必须等待无关来源下一次变化才可见；不能只让 status 发现 ledger 后再启动昂贵的完整同步，不因此改变 token 用量口径。

### 4. 查询有残余，但已有缓存不应推倒重做

today 首次 dashboard 的冠军计算约 **1.61 s**；后续相同上下文已命中。month 的 timeline 阶段平均约 **870 ms**，完整暖查询仍约 **2.37 s**；不能把全部时间归给冠军。补充阶段计数还确认：month 的 groupedRange 两次合计约 **551–584 ms**、perfSummaryForRange 约 **867–953 ms**；all 暖态 timeline 已复用，但 perfSummaryForRange 仍约 **812–978 ms**，是 all 暖查询的主要残余。后者包含样本捕获与 buildPerfSummaryForRange，不能再把其子阶段耗时相加。每次真实增量后的 today 查询会重新计算部分冠军与周期结果，须与静止命中区分。

E-1 的具体候选改为：在现有读修订/投影机制下复用不变的性能统计，再按残余选择 month 分组/日线及真实更新后的失效成本。实施排在同步去重之后，逐项对拍确认范围；不预先加入通用响应缓存，不裁掉卡片或返回旧载荷。

## 浏览器与状态时序

Chromium **156.0.8078.4**，1440×1000，Asia/Shanghai，headless 前台计时设置。跑了 **2 组 × 10 个真实 60 s 周期**：4 个静止、6 个 Claude 追加、2 个 Codex 新文件、4 个 Codex 追加、4 个 ledger-only。第一组取满 10 周期后主动结束，为显式固定后台价目端点，恢复输入并新建第二组；不是一棵进程连续 20 周期，也不是故障/内存触限。两组初始化追赶均排除在周期分布之外，第二组恢复时间戳造成的首次重新导入不作为可比较首屏基线。

12 次 token 改动每次精确 **+1,000,107 total / +1,000,007 output**。核对源写入、status、usage 响应、精确 total/output title 与双 requestAnimationFrame 边界，所有增量均准确、无浏览器错误。程序采样使用 DOM/帧边界，不是屏幕扫描输出的硬件时间；总量 B 单位两位舍入可能不变，不能用它判断新数据没有到达。输出指标跨过 M 单位舍入阈值，quota 补测另直接记录其可见 textContent。

- **检查 → 目标 DOM/双 rAF**：12 个混合增量样本 **8,900–21,136 ms**，中位 **12,019 ms**。
- **写入 → 目标 DOM/双 rAF**：**51,798–80,984 ms**，中位 **60,408 ms**。包含刚过静止检查后写入，不只选下一次检查前写入。
- 两组内实际 status 请求间隔共 18 个，**59,990–60,010 ms**。上述慢增量已超过 G1 的 max 8 s；若干写入也超过约 60 s 周期 +5 s。各来源组未达到 20 个暖样本，因此不声称它们的正式 p95 验收完成。
- 普通增量样本中，busy 关闭与新值在同一 DOM 批次、同一双 rAF 观察边界，未复现数秒空窗；不据此排除所有其它分支。
- 新进程第一组页面初始化 **20,643 ms**，含来源追赶；不是纯查询冷启动。三档筛选直接浏览器样本：today **693/749 ms**，month **2,338/2,525 ms**，all **1,885/2,121 ms**。
- 双标签页新页面默认读取与当前页面 month 筛选并发，整体落定 **12,787 ms**；原脚本记录的是两者汇合时间，不是第一页面筛选自身独立完成时间。n=1 不作吞吐或尾延迟保证。
- 4 个 ledger-only 周期均 status.changed=false、无 usage 请求；随后其它来源变化时，匹配计时证据被导入并可触发第二轮。它们不是“计时新值已成功可见”的样本。

**quota 纠正：受控分支，n=1。** 在一次 quota 自动检查响应中，注入“已无可选 Codex metadata”，其它业务载荷来自隔离真实服务，纠正后的 today/skipCheck 第二请求也走真实服务。第一响应后 busy 在 `1793023706893` 关闭，目标 DOM 在 `1793023707690` 更新，双 rAF 在 `1793023707701`；约 **797 ms DOM / 803 ms 帧观察空窗**。可见输出由 **12.52M → 13.52M**，精确用量对上，最终 preset=today。它证明该分支的提前结束状态，未复现自然发生的数秒–10 秒幅度或生产触发频率。

## 建议实施范围与验收

1. **第一批：D-1/D-2 + 新增 P-1 规划判据修正。** 最小范围限 store 与相关既有测试。静止缺源仍保留 14,416 events / 359 samples；真实删除、回归、重命名、追加、旧前缀改写、失败重试都按既有契约处理。稳定无变化轮不再因相同缺源集合规划整个 home，逐文件只读热路径整映射复制为 0。
2. **第二批：C-4 + B-1/B-2 + L-1 ledger 触发。** 将发现、受影响线程关联与发布依赖一起处理；保留同轮 native + ledger、新证据迟到、冲突、截断/替换及重试。取消重复完整发现/规划，允许必要的定向性能阶段。
3. **后续定向候选：E-1 查询。** 优先不变性能统计的复用，再按第一、二批后的残余选择 month 分组/日线与增量后的缓存失效。沿用已有读修订/投影，不引入通用响应缓存。
4. **暂缓：分块/Merkle 存证、通用响应缓存、独立读 worker/进程、刷新频率/跨标签页调度改造。** 先消除触发重复工作的根因；现有轻量 status 已快，尚不足以支持先做架构改造。
5. **独立小卡：F-1 仅 quota 纠正完成状态。** 保持 busy 到纠正请求完成并绘制正确值，保留取消、过期响应及错误恢复。普通成功路径没有数秒空窗证据，不做泛化的 render 顺序重排；控制分支不外推为每轮都发生。

继续沿用原计划 G1/G2/G3 候选目标：普通增量检查到新值首帧 p95 ≤3 s / max ≤8 s，写入到可见 ≤实际周期+5 s，无变化/普通增量 sync p95 ≤3 s / max ≤8 s。它们是后续同源 A/B 的验收门槛，不是从阶段计时相减得出的收益承诺。每个入选场景至少 20 个暖完整样本，首屏单列；来源与预热固定，新增值精确对拍。

本轮只推荐范围，不将建议视为产品开工。不存在可发布的“优化后”数据或补丁。
