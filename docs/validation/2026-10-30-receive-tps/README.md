# 原生 TPS token 窗口修正

2026-10-30。Codex 原生采集存在两个独立缺陷：缓冲解析时间冒充生成时间，以及全回复 token 数与首末输出窗口不匹配。DSH、WorkBuddy 也使用了没有依据的固定首 token 扣除。只修接收时钟不足以恢复生成速度。读侧撤销这些原生窗口的速度准入，tps-v5 使对应旧数值失效，用量和费用保留。本轮不采用实验引擎，不需重启 Desktop。

## 真实样本核验

同一次只读快照核对了 759 条原生样本，包含 405 条 group/deepseek 和 354 条 gpt-6.1-sol。所有样本的原生非 reasoning 输出均等于服务端报告的 output_tokens 减 reasoning_output_tokens，索引再减 1；没有发现这条算术路径重复计算 reasoning。

页面 609.0 附近的实际 DeepSeek 请求为 `(103 - 7 - 1) × 1000 / 156 = 608.9744 tok/s`；sol 111.5 对应请求为 `(4413 - 4233 - 1) × 1000 / 1606 = 111.4570 tok/s`。算术与原始记录相符，但分子没有被证明属于这个时间窗口，因此不能认定为模型生成速度。

此前 E2E 与 streaming 的约 1.6 倍，只是当时那批相同请求两种口径的比较结果，不能作为校正系数，也不能据此确定真实速度。

## 两个可重复的缺陷

旧 SSE 采集器在事件解析后取时钟，WS 在 mpsc 消费后取时钟。同一已收到的缓冲可被拆成不同时间。旧 release 的纯 loopback 复现将 1,100 个工具参数 delta 一次发送，仍得到 279 tokens / 2 ms，即 139,500 tok/s。真实日志中 278 tokens / 6 ms 则得到 46,333.3 tok/s。

实验 schema 2 把时钟移到原始 SSE 接收和 WS socket pump，记录接收批次 ID。该修复能排除同批解析耗时，却仍固定 start_output_tokens 为 1。假设首批已经包含 M 个 token，总输出为 N，则首批至末批窗口应该对应 N-M，而不是 N-1。不同 read_id 不能证明 M=1；全回复计数是否还包含窗口外的工具名、协议结构等输出，也缺少逐 token 证据。

新 release 的实际两批 loopback 验证了这个缺口：模拟服务明确给出首批 900、末批 200、总计 1,100 个 token。接收批次为 1 和 2，实测间隔 209 ms；原路径用 1,099 个 token 算出 5,258.37 tok/s，而该窗口对应的 200 个 token 是 956.94 tok/s，高估 5.495 倍。这是可变的窗口错配，不存在统一除数。

两次复现均使用独立临时 home、本机模拟服务和真实 release 引擎，没有调用真实模型、读取账户凭据或改动当前 Desktop。实验引擎只保留作本地诊断，不作为完整生成 TPS 方案发布。

## 读侧修正

- 不再将 schema 1/2 原生 generation_timing 投影为可测生成样本，原始日志、usage、模型身份和用量累计保留。
- DSH 原生 stream 保留逐片段时间、内容和最终 usage，缺少窗口起点的累计 token 数。WorkBuddy 的正文时间和三侧一致性证明也没有提供首批 token offset。两个 reader 保留接收时钟诊断，不再将固定 N-1 对应到该时段。
- tps-v5 拒绝 Codex v4、DSH/WorkBuddy v3/v4 的派生速度；旧行保留且不改名冒充新测量。OpenCode、ZCode、Claude 及 Codex 既有显式计时 adapter 仍按其提供的精确计数契约读取，不按模型名或速度筛选。
- Codex 投影版本升至 v6，持久摘要缓存升至 4；冻结、冷归档、重新导入和 SQLite 查询都经过相同统计门禁。主库 schema 保持 23。
- 不添加速度上限、最短时长、模型白名单、字符/token 估算或 1.6 校正，不回退到 E2E。没有有效样本时沿用现有 `—`，不增加 UI 说明、徽标或框体。
- 保留 RANGE/SYNC、已有 TPS 降序与区间条，以及并行实验改动。

## 验证

原接收时钟修复的 27 项 producer 单测通过，release 离线锁定依赖构建成功，用时 50 分 32 秒。它通过接收批次测试，却在上述 token 窗口反例中失败，因此不视为完整采集验收。

DSH 定向回归 105 项、WorkBuddy 定向回归 79 项通过。本地完整检查运行 3,529 项：3,504 通过、25 跳过、0 失败；随后独立审查发现并修正 Codex 覆盖率仍计入退休窗口的问题，相关 13 项核心回归通过。类型检查与 27 个改动 JS 文件的 Biome 检查通过。测试用普通系统临时目录；另一次带空格、较深的临时目录运行出现归档 SQLite 路径失败，不作为通过依据。

正式看板已切至固定运行包 `ce274b47d7c2`，采用 tps-v5、schema 23。schema23 完整数据恢复点已保留且 quick_check 为 ok，没有外部冷段。只读数据库副本及正式 API 的 2026-09-15 UTC 汇总均确认用量、费用不变；今日的 Codex/WorkBuddy 模型保留为 missing_duration，旧速度和 P90 均为空。全部 104 个运行文件已固定，public 文件与旧服务逐字节一致。

看板服务保持独立托管和原 128 MiB heap、7 GiB 服务树预算，一次性启动任务已清理。Desktop GUI 和 app-server 的进程身份与旧引擎路径均未改变。新实验引擎没有安装、采用或发布，不需要用户手动 resume。

## 生成速度的剩余采集条件

现有原生摘要没有精确首批 token offset，也没有与同一 response、同一 token 范围对应的服务端 generation start/end。仅有客户端接收时间，不能还原服务端内部生成速度，旧日志无法回算真实值。

后续可用采样需要服务端提供匹配 token 范围的生成时段，或精确逐 token 时间与计数。即使取得精确分批计数，客户端接收窗口得到的也只是接收速率。此缺口不能由换本地时钟、固定减 1 或重新标记统计名称解决。
