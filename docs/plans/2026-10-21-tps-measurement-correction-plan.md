# TPS 计量口径修订与历史恢复方案

日期：2026-10-21。状态：**v2 代码与接线专项通过，原六轮真实历史已在临时索引/API/页面复算通过；最终全仓 2,792 通过、3 失败、20 跳过，失败在皮肤浏览器测试，正式服务与真实索引尚未切换**。具体分工见[三 worker 执行单](2026-10-21-tps-measurement-parallel-execution.md)，当前裁定以[执行账本](../validation/2026-10-21-tps-measurement-correction/README.md)和[整合验收](../validation/2026-10-21-tps-measurement-correction/review/final-integration/README.md)为准；隔离恢复不等于正式上线。

本稿修订采样方法，沿用已确认的[模型速度视图](2026-10-20-model-speed-view-plan.md)及其[实施计划](2026-10-21-model-speed-implementation-plan.md)的布局、行身份和交互。旧方法的测试与 G4 通过记录仍是历史事实，但不能证明此次发现的计量问题不存在。

## 1. 已确认的事实

### 1.1 触发案例

今天指 Asia/Shanghai 的 2026-10-21：`2026-10-20T16:00:00Z <= ts < 2026-10-21T16:00:00Z`。

Codex `opendesign/deepseek-v4.1-flash / max` 的 6 个完成轮次，共 326 次请求：

- 请求输出量、请求增量之和、轮次累计输出、SQLite 中的输出量均为 **233,379 token**，逐轮相等；没有发现这批数据重复加总。
- 旧分母是 `Reasoning` 与 `AgentMessage` 的条目时长之和，合计 **475,234 ms**；旧均值 **491.0823 tok/s**，算术正确。
- 其中 11 次请求只有工具类完成条目，没有文字/推理条目，输出 **13,638 token** 却没有增加旧分母。
- 有文字/推理条目的请求同样可能生成工具参数，因此剔除上述 11 次请求仍不能补齐计时；只从分子减去这部分输出，结果仍约 **462.4 tok/s**。

本机既有 Magpie 账本提供了一条独立恢复线索。按 rollout 的 `response_id` 查找，326/326 找到对应记录，输出 token 326/326 相等，没有重复匹配，HTTP 状态均为 200，`ms` 均为正整数。其 `ms` 总和 **1,742,789 ms**，相除为 **133.9112 tok/s**。

**133.9 是按账本 `ms` 字段计算的候选请求吞吐，不是已经认证的解码 TPS，也不是已经上线的修后值。** 仍需核实账本生产端的计时起止点、流式完成、重试及多个尝试的范围；精确 ID 与 token 匹配证明关联正确，不能单独证明时长含义正确。

### 1.2 已扩大到其他 Codex 模型

在同一个 SQLite 只读事务中提取当天候选及其既有脱敏投影，沿用生产 ownership 证明后进行结构核查。没有重新扫描原始目录或运行索引同步。

该时点有 238 个通过现有数值/状态规则的 Codex 轮次，全部可作单 rollout 顺序核查：

- `gpt-6.1-sol / high`：10 轮、244 请求；5 轮有异常结构区间，共 37 次、12,086 token。
- `gpt-6.1-sol / medium`：5 轮、150 请求；3 轮有异常结构区间，共 18 次、13,013 token。
- `opendesign/deepseek-v4.1-flash / max`：6 轮、326 请求；4 轮有异常结构区间，共 11 次、13,638 token。

共 14 轮、70 个有输出却没有对应目标 item 的顺序区间，涉及 **39,863 token**。投影没有保存 item 的 `response_id`，这里用的是同轮内物理记录顺序，属于结构性异常筛查；**不能反过来把这个顺序规则当成新计时关联算法**。触发案例的两份原始 rollout 已另行核对过工具类型及原始计数。

缓存同时保留 9,414 个 Codex 候选，其中 6,814 个通过旧数值/状态规则。它们共享同一旧公式，均属于需要重新判定的集合，不能声称 6,814 条全部已经证实高估。当天统计也不等于用户当前目录筛选和发布策略下的页面行数。

本轮[可复跑审计](../validation/2026-10-21-tps-scope-audit/audit.mjs)及[脱敏证据](../validation/2026-10-21-tps-scope-audit/evidence.json)保留了时间、索引版本、范围、逐组计数及网关匹配结果。它们不含对话正文、工具参数、原始响应 ID 或鉴权信息。

## 2. 根因：完整性验证的对象选错了

1. **计数与时长分别正确，覆盖范围却不相同。** `codex-candidates.js` 对全部 request 求输出和，只对两类 item 求时长和。一个 request 的输出可以包含推理、文字、工具调用名称及参数；item 并不是 request 的完整生命周期。
2. **`PARTIAL_ITEM_SPAN` 只检查已经进入目标集合的 item。** 非目标类型在 reader 中先被跳过，所以“75 个目标 item 都有时长”不能证明“70 次请求的全部输出都有时长”。缺少的工具生成阶段根本没有参与完整性判断。
3. **折叠后没有保留 request 与完整计时的关联。** fold 的 request 有响应 ID 和输出计数，item 有自己的 ID 与起止时间；现有账本没有证明二者一一对应。全轮相加只是绕过了这个缺口。
4. **标记为估算没有修复偏差。** `METHOD_ESTIMATE` 是提示位，仍参与采样。系统性漏掉输出阶段不是可以靠提示或扩大样本量消除的随机误差。
5. **测试继承了错误前提。** `test/perf-codex.test.js` 明确断言“整轮 request 输出 / 两类 item 时长”，并将完整多请求轮放入 sampled。这些测试保护了实现与旧规格一致，未验证计量范围是否成立。
6. **显示统一后，方法差异仍在。** 新 models 投影按来源、模型、强度合并，并在同一表排序；不同来源仍各用各的时间边界。不是均值、nearest-rank 或排序本身算错，而是错误输入获得了正常排名资格。

先前登记 WebSearch 解决的是文件因未知类型被拒绝，与此次发现的分母遗漏是两个问题。不能通过把 WebSearch、CommandExecution 等工具执行时间加入目标集合来补救。

## 3. 其他来源的检查结论

以下结论来自现有 reader 与专题的代码检查；除上述 Codex 证据外，本轮未逐条认证其他来源真库。

- **DSH**：按 `(session, turn, step)` 关联 `step/start` 与 `assistant/message`，使用该组输出和两者时间差。没有复用 Codex 的部分 item 时长算法。需补证开始确在该 step 的请求前、结束在模型响应完成后，且 usage 不是跨 step 累计。执行中的工具耗时不得混入请求窗口。
- **OpenCode**：`tokens.output + tokens.reasoning` 除以 message 的 `completed-created`。现有专题已经说明 message 不保证与一次 provider request 一一对应；需检查重试、工具循环和 v2/未知 session 版本。若 message 内有多个请求，必须证明计数与整个 message 窗口范围一致，不能把它未经验证地称作原生单请求计时。
- **ZCode**：每次尝试行的 `output_tokens` 与 `duration_ms`，没有显式时长时才用行内起止时间差。数据粒度较接近目标，但“字段存在且为正整数”不能证明单位和覆盖范围；需核对写库点、重试与失败状态。
- **WorkBuddy**：按 messageId 关联响应输出与 generation span，比 Codex 当前拼接方式完整。需检查 generation span 的实际起止点、是否一 span 对应一个响应。另有可见实现风险：持久化使用 `INSERT OR IGNORE`，同 ID 的冲突时长会被先到先得规则吞掉；这是已确认的风险路径，本轮没有证明真机已存在冲突数据。
- **Claude Code / project-log**：当前缺少可靠请求时长，不在此次修复中凭空新增 TPS，也不从相邻消息时间推导。**更新（2026-10-21）：** Claude 已由[Claude Code TPS 方案](2026-10-21-claude-code-tps-plan.md)单独认证（转录时间戳回退、请求端到端，不在本次修复内）；project-log 仍为结构性不支持。

不按绝对 TPS 高低筛掉样本，也不因为源名不同就宣布其他来源正确。验证对象应是源写入的计数范围、计时范围和同一调用身份。

## 4. 推荐的统一口径

### 4.1 当前主视图采用完整请求的有效输出速度

对被认证的模型调用：

```text
requestTps = requestReportedOutputTokens * 1000 / fullRequestDurationMs
averageTps = sum(matchedOutputTokens) * 1000 / sum(matchedRequestDurationMs)
```

`fullRequestDurationMs` 指开始该次模型调用至其流式或非流式响应完成，覆盖该次调用的等待与完整输出过程，**包含 TTFT**；模型完成工具调用参数后执行外部工具的时间不属于该请求。它衡量用户实际获得输出的请求速度，不能声称是模型硬件或纯解码速度。

本轮不改为 `duration-TTFT`。完整 output 是否包含首 token、隐藏 reasoning，以及不同系统 TTFT 从哪个事件起算，都需要额外的匹配证据。不能只因为账本有 `ttft_ms` 就直接相减。

各来源必须明确输出是否已经包含 reasoning，避免二次加总。无法确定包含关系时保留源报告范围，并在内部方法说明中写清；已知范围不匹配的样本不得纳入正常平均速度。

### 4.1.1 跨来源统一排名的准入条件

2026-10-21 补充：用户明确追问 Codex 的 `item_span_estimate` 是否能与其他工具的 E2E 放在一起比较。**现状不能作为同口径的统一速度排名。** 即使 item 计数与计时完全匹配，item 活跃阶段排除了请求等待，E2E 包含等待，两者仍衡量不同对象；本次确认的输出范围遗漏是叠加在此之上的另一项缺陷。

例如同样输出 1,000 token，生成阶段 5 秒、此前等待 5 秒：只计生成阶段是 200 tok/s，完整请求是 100 tok/s。这个差距不证明前者所在工具或模型更快。当前 `projectPerfModels()` 虽按来源分行，没有把 Codex 与其他来源求成一个均值，仍按这些不同口径的数值作全局排序，因此来源列本身没有解决可比性。

恢复统一排名之前，对每个参与来源验证：

1. 起止边界是同类完整模型调用窗口；均包含请求等待与 TTFT，排除响应完成后的工具执行、用户空闲。不能只检查 `timingKind === "request_e2e"`；DSH 的 step、OpenCode 的 message、WorkBuddy 的 generation span 仍需各自的 producer 证据。
2. 输出范围一致，尤其是 reasoning 已含、单列或未知的区别。范围未知的旧数据可以保留为历史诊断，不能仅在内部写一条说明就认定它已获得跨来源排名资格。
3. 统一后的均值仍是历史实际调用条件下的有效速度，会受到上下文长度、等待和调用线路影响；这可以回答“我实际用起来多快”，不能作为模型硬件或固定条件的解码基准。
4. Codex 保持轮级样本时，pooled 均值仍可由完整请求的总输出/总时长得到；但轮级 p10/p90 与其他来源的请求/message/step 级分位数并不具有相同统计粒度。本轮右栏保留各行自身的历史分布，不能把跨工具的分位差解释成同一请求级波动。若后续要比较请求级稳定性，再单独统一粒度，不能暗改本轮 n 和分位定义。

未取得一致边界证明的旧数值不进入新的统一排名；继续保留其底层记录供恢复和诊断。修复数据与准入规则，沿用现有简洁视图，不通过堆叠估算标签、解释文字或另一套筛选机制替代修复。

### 4.2 Codex 保持现有轮次粒度，内部改用完整请求计时

优先采取最小改动：**不把一轮拆成 70 行，不改变现有 sampleKey，也不顺手把分位数改成请求级。**

1. 保留 request 按 `(homeId, threadId, responseId)` 去重、turn 归属、模型/强度及累计输出交叉核验。
2. 每个 request 必须取得同一调用的完整计时证据，并核对该调用输出 token 与 rollout 计数。
3. 一轮所有参与输出求和的 request 均有有效计时，才计算轮分母 `sum(request.durationMs)`；不包含工具执行、轮间空闲和子线程的调用时间。
4. 有任一 request 缺时长或计数冲突，不得用剩余计时配全轮输出。缺时长整轮保留候选，`durationMs=null`，使用既有 `MISSING_DURATION`；冲突使用既有 `RECORD_CONFLICT`。内部执行报告记录缺多少次、为何缺，主界面不增加说明墙。
5. 保持 `[codex, homeId, threadId, turnId]` 身份，`window=turn`；内部 `timingKind` 改为 `request_e2e`，含义是轮内完整请求时长之和。`requestCount` 保持真实次数。
6. `AgentMessage/Reasoning` 时长可保留作诊断，不能再决定 v2 的 TPS 分母；缺 item span 不再否决已有完整 request 计时的轮次。`METHOD_ESTIMATE` 不得再仅因 sourceKind 是 Codex 就自动加上。
7. 日历归属继续使用既有最后一个已识别请求的 rollout 时间，避免顺手改变日期选择结果。请求起止时刻有可靠证据时才填写窗口包络；只有 duration 时不得捏造两端。

仍对同一批有效轮次计算 pooled 均值和轮级 nearest-rank p10/p90。六轮全部恢复时仍为 n=6；不因为取得了 326 次计时就把样本数改成 326。

### 4.3 时长来源的优先级与冲突处理

优先使用**同一工具已有的、可按响应身份关联的完整请求计时**。原始 rollout 没有完整时长时，可使用明确配置的独立计时证据；不得只看数值接近就合并。

这台机器已有网关账本，是历史恢复的优先试点，**不写死 `127.0.0.1:3425`，不让常规 summary 请求访问网关，不读取鉴权配置后自动联网**。先离线导入最小计时证据，正常查询只读本地索引。普通用户没有该网关仍可使用其他来源；其 Codex 记录在取得原生计时前不能继续沿用已知错误的 item 比值。

最小导入记录的字段范围固定为：

```text
schemaVersion, evidenceOrigin, responseId, requestedModel,
reportedOutputTokens, durationMs, status,
completedAtMs（仅生产者能证明时填写）
```

- `evidenceOrigin` 是无鉴权信息的稳定来源标识，用于避免不同发行者同名 ID 碰撞；导入配置必须明确映射目标 home，不按模型名猜 home。
- 响应 ID 精确匹配，输出计数必须相等；请求模型与线路模型的别名只能来自记录中的明确映射，不能用字符串相似度判断。
- 完成状态、毫秒单位、正整数时长、调用范围均经 producer 语义认证后，才允许导入为有效计时。
- 同身份、同字段重复记录幂等；同身份不同计数、时长或范围为冲突。不能任选第一条、最新一条或最短一条，也不能看到有原生计时就把冲突外部证据覆盖掉。
- 网关额外调用、失败尝试、子代理调用不能凭“同模型、相近时间”吸收到父轮；只有 rollout 中真实存在的响应 ID 才可关联。
- 导入的持久化证据不因上游日志自然到期而消失；来源指纹、采集版本及冲突状态必须可追溯。

本轮有界检查了目标 worker 的原生 `logs_2.sqlite` 最近 1,000 条：有工具/压缩相关 duration 字段，但没有 `response_id` 字段与计时共同出现的记录。**这没有证明原生历史请求计时永远不存在。** 在后续卡中最多再做一次有界的原生证据核对；没有完整身份与时间证据就结束该分支，不再反复重扫同一目录。未来原生遥测采集单独作为后续能力，不能用它阻塞已经可恢复的网关历史。

### 4.4 不采用的补丁

- 限制 TPS 上限、乘一个经验系数、对 DeepSeek 特判，或按模型速度预期过滤。
- 把“没有文字/推理条目”的 request 删掉：既不能补齐其他 request，也会系统性筛掉工具密集任务。
- 加入 CommandExecution、FileChange、WebSearch 等执行 span：执行工具与生成工具参数是不同阶段，且可能并行重叠。
- 全轮 `task_complete.duration_ms`、相邻 usage 时间差，或“整轮减工具 span”直接替换完整请求计时：会混入/误减工具、并行等待、压缩及调度时间。
- 按输出正文字符数估算 token，或把 reasoning token 当作完整输出。
- 把 n、估算徽标、分组菜单和诊断说明重新塞回主界面，代替计量修复。

## 5. 缓存、版本与历史处理

1. 这是采样定义变更，正式实现使用 **`tps-v2`**；旧 `tps-v1` 数值不得原地改标签冒充新方法。源日志、用量事件、价格及费用不变。
2. **先有已核验的计时证据，再构建新候选，最后原子发布。** 保持旧数据物理可恢复；不能删掉数据库再期望扫描自动治好，也不能半轮写入 v2。
3. query/API/models/旧 groups 必须消费同一批 v2 sampled；没有完整计时的轮次仍保留诊断，但不继续进入均值、分位和排名。不能只在 models 隐藏旧算法而让 groups 继续称其为有效 TPS。
4. 现有 `codexProjectionMethodVersion()` 将采样版本与解析版本耦合。若 rollout 投影字段未变，可在验证 `codex-projection-v3` 结构、归属和文件指纹均兼容后复用其解析结果，重新 fold/计时；**采样版本改变不应导致已经持久化的 895 份投影无条件重读全文**。读取兼容旧投影不等于允许旧候选进入 v2。
5. 真正改变投影字段才升级 projection 解析版本。不要为了本轮修复重开 paginated ownership、WebSearch 兼容或 publication policy 规则。
6. 其他来源通过范围复核且公式未变时，允许从已有结构化候选重建 v2，证明数值不变；不能只批量 UPDATE method_version。WorkBuddy 若发现或修复时长冲突，必须重新核验对应 trace 证据，旧 `capture_version` 不自动获得新认证。
7. 增加计时证据的持久化需要一个小的 side table，保存关联键、经核验的时长、输出计数、来源/方法版本及冲突状态；**不存响应正文，不复用 WorkBuddy 专属表硬塞 Codex**。沿用 UsageStore 的事务与依赖失效机制，导入后仅标记涉及的 Codex thread 需要重建。
8. 数据库迁移号在实施时读取实际 schema 的下一个空号，不在计划里预占，避免与历史保留等并行任务冲突。迁移失败回滚，重开、重复导入和重复同步幂等。
9. summary 缓存键、store revision、索引 fingerprint 均必须包含本轮方法/计时证据变化。活服务不能只刷新 HTML 继续返回缓存的 v1 排名。
10. 在线冻结保留当时方法版本与结果，不静默重算或改名；解除冻结重新加载 v2。历史导出保留原 methodVersion，不能与 v2 混在同一个实时排名池。

## 6. 实施卡与交付边界

当前只有调查 R0 完成；以下 R1–R6 均待实施。每个模块维护一份滚动报告，失败就追加原报告；相同失败第二次必须缩小到最小复现，不再生成多版 handoff 或原样重跑全套。

### R0：证据与原因（本轮已完成）

- R0.1：触发六轮的原始计数、时长与累计量核对。
- R0.2：当日其他 Codex 模型脱敏投影筛查；与网关 326 次精确 ID/输出关联。
- R0.3：检查所有来源 reader，区分确认缺陷、实现风险和未核实的 producer 语义。

交付：[调查记录及执行边界](../validation/2026-10-21-tps-scope-audit/README.md)、审计脚本与证据 JSON。

### R1：锁定计时契约，先做离线六轮原型

R1.1 核实账本 `ms` 的写入代码或可信 producer 规范，记录版本及精确起止点；明确 HTTP/流式完成、重试和工具执行边界。**若 `ms` 包含多个失败尝试却只有最终响应的 token，不能通过本卡。** 对原生证据只进行上文约定的一次有界核查。

R1.2 编写不接生产的最小适配，按响应 ID 和输出量关联六轮，验证 326 次完整计时。导出固定脱敏夹具，包含六轮的 token、逐请求 duration、匹配状态和手算结果。若 producer 语义否决 `ms`，明确报告哪一段时间范围不匹配并使用已证明的替代字段；没有替代时停止该证据分支，不编新公式。

R1.3 一次性确认 v2 契约：保留 turn 粒度、`request_e2e`、reasoning 包含关系、缺失与冲突的处理、旧 item flags 失效范围、证据导入字段、版本迁移和正常样本集合。

主要边界：review 原型、固定夹具、规格；本卡不修改正式 reader/store。通过条件是能够独立复算六轮，而不是只有一个“133.9”的摘要。

### R2：持久化计时证据

R2.1 在 `src/usage-store.js` 增加最小 side table 和读写接口，schema 迁移在短事务内完成。证据与候选更新失败都回滚，旧用量不变。

R2.2 实现离线证据导入：来源明确映射 home；去重、冲突、单位、状态、输出量、采集版本均校验。网络采集与查询分离；本机账本提取器作为显式运行的工具，端点从参数读取，不在正常 summary 路径自动发现服务或读密钥。

R2.3 计时新增/修订/冲突只失效对应 thread；旧计时不因 trace/账本到期丢失。导入不自动声明所有历史都完整。

主要边界：`src/usage-store.js`、一个小的证据导入模块及其测试；共享 store 文件由本卡单写。通过条件：重复导入不增量、同身份冲突阻止误采样、回滚和重开后状态一致。

### R3：Codex 公共采样与统计内核

R3.1 在 `codex-fold.js` 保留现有身份、累计核验和请求账本，为每个已识别请求接入 R2 计时；`codex-candidates.js` 将分母改为完整 matched request 时长之和。

R3.2 统一 memory 与 store 的证据 lookup；缺一请求不配全轮分子。工具-only 输出也必须取得时长；不能因没有 item 就丢掉正确请求。

R3.3 更新 `perf-stats.js` 的 Codex 语义、方法版本和 flags 生成条件，更新 `usage-types.js` 说明。沿用既有 `MISSING_DURATION`、`RECORD_CONFLICT`，不新增一套公共告警码和主界面状态。

主要边界：`src/perf-sources/codex-{fold,candidates,thread}.js`、`src/perf-stats.js`、`src/usage-types.js`、`src/usage-core.js` 及对应 perf 测试。schema 与导入由 R2 负责；本卡不改 ownership。

通过条件：旧错误公式的针对性回归在修复前失败；六轮复算与 R1 相等；原 key、日期归属和轮次 n 保持一致。

### R4：其他来源的范围认证与确定性修补

R4.1 为 DSH、OpenCode、ZCode、WorkBuddy 各保留一份计数/开始/结束写入点证据或明确的未核实结论；每来源选一个纯文字调用和一个工具调用。验证工具执行延长不会改变已完成的模型请求计时。

R4.2 WorkBuddy 同 messageId 的同值 trace 幂等，异值 trace 必须持久化冲突，正反导入顺序、跨文件和进程重开均不能任意选值。采集版本随此变化升级；时长曾过期且无法复核的旧记录如实留缺口。

R4.3 OpenCode 验证 message 多请求/重试时输出量和整个窗口是否匹配；只有已证明相同的完整范围才能保留原公式。ZCode 验证单位及尝试行范围；DSH 验证 usage 的 step 范围。缺证据仅影响该来源的认证，不拖延已经有完整证据的 Codex 历史修复。

主要边界：各自 reader/测试及 WorkBuddy trace 采集；不重写共同 normalizer。通过条件：每来源明确标出“已证实一致 / 已修复 / 尚缺什么”，不以测试全绿代替 producer 语义。

### R5：版本切换、重建与回滚

R5.1 实现第 5 节的 v1→v2、投影兼容复用和 query cache 失效；未变原始文件无需重新全文解析，候选必须真正按新证据重建。

R5.2 隔离库验证首次升级、旧投影、缺计时、完整回填、重复 sync、损坏证据和事务中断。不得出现部分新候选与旧 meta 的混合发布；events、用量、费用与升级前逐项一致。

R5.3 正式启用前先准备有效计时并完成隔离验证，再按项目服务管理方式切换一次；不以“用户再重启/刷新试试”代替确认服务加载的方法版本与索引版本。回滚时用保留的旧程序/索引副本恢复，不能把 v2 结果伪装成 v1。

主要边界：`src/usage-store.js`、`src/usage-core.js`、必要的执行器缓存键及 projection/store/API 测试。与 R2 的 store 写入顺序协调，禁止两卡同时改同一文件。

### R6：集成验收与文档收口

R6.1 同一固定夹具核对 memory、SQLite、HTTP API、models 和旧 groups 的 token/时长/采样成员。分位数与均值来自同一批轮次；不改 pooled 算法来迁就某个期望数值。

R6.1 的跨来源验收还必须满足 §4.1.1：相同输出、相同完整请求耗时的不同来源得到相同均值；旧 item-active 比值和未经认证的 E2E 标签不能仅因数值较高进入统一排名。轮级与请求级分位不可比的限制应在方法文档保留，不在主界面新增诊断说明。

R6.2 复用当前界面做一次 API→DOM：Codex 行及详情与 v2 API 对应，平均值正确、排序重排、p10/p90 和样本数同集合；时间/目录过滤、在线冻结继续正确。不加新的入口、标签、筛选器或说明墙。

R6.3 完成受影响测试后跑一次工程门禁，更新数据源专题、长期方法说明与本计划状态；旧验证记录加关联说明，不抹去历史失败或把旧 G4 当作 v2 通过证据。

逻辑依赖仍为 R1 → R2/R3 → R5 → R6，R4 可并行。用户已明确指定三名 worker；具体执行改为[三 worker 执行单](2026-10-21-tps-measurement-parallel-execution.md)中的 A0/B0/C0 同时开工、G1 后接线：认证与隔离内核/数据库实现并行，正式版本切换串行。该执行单的单写分配优先于本节较宽的模块文件边界，避免多人同时修改 store/core/stats。

## 7. 必须通过的回归与验收

1. **可手算的异构请求**：一轮 A 输出 100、完整耗时 1,000ms，B 为工具-only 输出 900、完整耗时 9,000ms；不论文字 item 只有 100ms 还是没有 item，结果必须为 100 tok/s、n=1、requestCount=2。
2. **计时缺一不可拼**：同夹具去掉 B 的计时，整轮不能变成 1,000 token / 1,000ms；应进入既有 missing-duration 诊断，不显示伪 0。
3. **工具执行独立**：把工具执行耗时从 10ms 改为 100s，完整模型请求计时及 TPS 不变；并行/重叠工具不叠加进分母。
4. **真实目标案例**：六轮全部匹配，326 次输出逐项一致；若 R1 认证 `ms`，总分子 233,379、总分母 1,742,789ms、均值 133.9112193，n=6；p10/p90 根据新六个轮次速度重新计算，不能保留旧分位数。
5. **其他模型同路**：Sol 不走另一个 fallback；没有完整时长就如实留缺口，不能保留其旧 item 比值进入排名。
6. **身份与冲突**：跨 home、不同 thread、同模型近时请求、网关额外请求、重复响应、冲突计数/时长、失败与重试不能误配；正反输入顺序结果一致。
7. **输出范围**：包含 reasoning 的源不二次相加；OpenCode 独立分量只在各自有效时相加；零输出、零/负/秒单位时长和不完整流式结果继续按规则排除。
8. **聚合与兼容**：保留轮级 p10/p90、pooled 均值、稳定降序、整数安全求和、目录/时间过滤及 overflow 行行为；旧 groups 与 models 使用同一新采样集合。
9. **版本与故障**：旧候选不能混入 v2；升级/重开/重复导入幂等；解析投影可兼容复用；证据自然过期不删除已验证时长；冲突状态不会因重启遗忘。
10. **产品边界**：实际界面仍为时间分布下面的左右两个框体；模型原名、强度、来源和平均速度的密度不变。不能通过重新设计 UI 回避算法验收。

定向集合由实际改动选择：`perf-codex`、`perf-codex-index`、`perf-codex-api`、`perf-stats`、`perf-models`、`perf-summary-parity`、`perf-projection-*`，以及新增计时证据测试和实际改变的来源测试。定向通过后再运行 `npm run typecheck`、`npm run lint`、`npm run format:check`、`npm test`，不在每张卡后反复全仓长跑。

## 8. 完成标准与明确限制

完成不是“Codex 又显示了”，而是同一批真实输出拥有同范围的完整时长，原始计数、索引、API 与页面可复算一致；确认有缺陷的范围已停止使用旧公式，并能恢复已有可靠计时的历史。

本机目标六轮已有强关联证据，值得优先修复。没有记录完整请求边界的历史，单凭 item 时长无法无损重建纯生成 TPS；不承诺所有旧记录都能恢复。其他来源 producer 语义仍需按 R4 认证。2026-10-21 已执行本机正式切换并核对 API→DOM；原六轮均值 133.9112 tok/s，其他未认证历史不外推。
