4. **准备备份位置与空间。** 为本次切换创建新的本地目录，预留完整数据目录、所有登记冷段及可能的故障留存空间。磁盘空间按执行时实际文件大小计算；不复制约 50 GiB 的性能原始产物，不重新复制上游日志树。

## 4. 停旧实例并制作离线恢复点

1. 暂停当前页面自动刷新，暂停本项目其它会写同一数据库的命令。暂时关闭其它看板标签，避免停机后重复发起刷新。
2. 按上一节核对后的目标范围发起正常关闭。确认旧 PID 已退出、3765 端口释放、数据库写入者和相关 worker 已退出。CLI 正常关闭会等待执行器退出；关闭失败时停止操作，不能直接启动第二个写入者。
3. **在新服务第一次打开数据库之前，制作离线恢复点。** 流式复制整个 `.codex-usage` 数据目录，保留目录结构、实际存在的主库/WAL/SHM、配置和 recovery 资料；不要对仍在写入的 SQLite 仅复制主文件。
4. 在冻结副本上以只读 SQLite 查询 `PRAGMA user_version`、`archive_segments`，记录其 `segment_id`、`database_path`、`database_sha256`。复制目录之外的全部登记冷段及相邻 manifest，建立“原绝对路径 → 备份路径 → SHA256”清单；目录内冷段同样核对。**不能拿早期验收的 cold segments=0 代替当前目录核对。** 配置、import 引用的外部历史包也按实际引用一并保留。
5. 检查备份文件哈希及复制完成状态，在冻结副本上做一次 SQLite 完整性检查。再从恢复点派生一份一次性核对副本，使用回退包的 `UsageStore` 执行 `open()`、读取固定历史范围并 `close()`，核对 schema21、所需表和既有历史样本。`UsageStore.open()` 会写 PRAGMA/建表，**不能把它当只读连接，也不能让它打开唯一恢复点或活动库**；允许的写入只落在一次性副本。不调用 `sync()`，不启动自动发现；核对任务用 1 GiB Job 串行运行。若无法完成，先处理备份/回退包，不启动新服务。
6. `services.json` 可留在本地备份中供追溯，但恢复时不能直接回灌旧 PID / shutdown token。历史 CLI 的 `history verify` 面向其生成的备份包及 manifest，不能对任意原库复制品调用后宣称通过。

如使用已有 `history export` 做额外可移植备份，必须保留完整包和完成标记；导入生成的是带冻结上下文的独立 runtime，不可直接把它冒充普通 `cli run` 的活动主库。离线原路径恢复点仍用于本方案的生产数据库回退。
