本轮用户授权成文、清理文档及修订方案范围，并明确 **十套角色全部重新设计配色，已发布五套也要调整**。生成工具、工作台升级、正式色值替换及恢复延期皮肤尚未实施。下面的流程和参数是推荐方案，不将参考稿中的“已确认需求”或实施步骤自动视为用户的新要求。

分模块执行与 agent 交接见[Implementation Plan](2026-10-03-skin-palette-implementation-plan.md)：保留 7 个模块和原 32 个任务编号，M4.3 之后采用独立小卡和模板实例；固定文件归属、接口、搜索预算和验收，并明确 subagent 调度规则。本文件保留设计依据与范围，执行细节只在实施计划维护；计划成文不代表代码已实现。

## 1. 目标与当前事实

目标是重新设计 **全部 10 套角色的配色，每套提供浅色和深色两个版本，共 20 个模式槽位**，形成有辨识度的完整风格体系，同时保留现有陶瓷材质、拟物层次和角色装饰。浅深版本表达同一种气质，分别满足阅读与交互要求，无须成为 20 套互不相关的设计。ChatGPT、Claude、DeepSeek、Kimi、Muse 与另外五套采用同等设计、候选生成、选择和验收流程。

把用户的工作收敛到比较少量真实页面候选；风格策划、颜色派生、可读性修复、初筛和评审整理由代理承担。数学规则负责排除明确问题，视觉设计和真实页面比较负责美观，不能用算法分数承诺审美质量。

当前工作区事实：

- [选择器](../../public/skin-picker.js)开放 ChatGPT、Claude、DeepSeek、Kimi、Muse；延期的是 GLM、Gemini、Qwen、Grok、Mimo。
- [配色输入](../../public/skin-palettes.js)保留十套角色的 20 个模式槽位。槽位已填和校验 PASS 不代表全部颜色组合可读。
- [发布配色记录](../validation/2026-10-03-release/palettes.log)保留七条次要文字告警；现有检查只对部分文字低于 3:1 发出警告，警告不使检查失败。
- [临时工作台](../../public/skin-palette-studio.js)按 RGB 固定比例混色，并维护一份独立预览派生规则，与生产接线已经存在差异。

2026-10-03 本轮只读复算采用当前色值、WCAG 相对亮度及生产派生背景：次要文字对各自面板有 **17/20** 个组合低于 4.5:1，强调色对面板有 **9/20** 个组合低于 3:1。后者是诊断数据，不能把所有强调色用途统一判成同一标准。

代表性组合为：ChatGPT 深色主文字对面板约 3.68:1、次要文字约 1.89:1；Kimi 浅色次要文字对面板约 4.97:1，对派生凹槽约 3.21:1。它们说明已发布皮肤也需要纳入检查，以及只检查面板底会漏掉风险；是否发生在具体元素上还需实际使用位置核验。

这些数字是本轮工作区快照，不是整页合规审计或永久基线。未来实施时记录 revision、输入文件摘要和复算条件，重新测量。

## 2. 范围与工程边界

- 十套全部纳入配色重设，不按发布状态划分为“全面设计”和“只修可读性”。每套均产出新的浅深候选并参与整体协调；两款试点仅用于校准流程，最终范围始终覆盖十套。试验候选不直接覆盖正式色值。
- 仅调颜色，保留字体、字号、间距、圆角、尺寸、布局、角色几何和既有光源方向。classic 保持现有简洁模式。
- 生成、评分和候选比较优先放在开发阶段；不将自定义配色编辑器接入主程序，不新增生产依赖或远程生成服务。
- 产品色源继续使用 `public/skin-palettes.js`。最终仍输出现有允许的 12 个颜色 token；新增可选项须先证明必要性，不为生成器扩展产品配置。
- 按[PC 界面基准](../03-development.md#界面设计与验收基准)验收：高分辨率桌面、显示缩放、侧栏与并排窗口。手机页面不新增为本项目要求。
- 当前独立 HTML 导出已移除，不恢复旧导出链，也不用旧离线快照脚本验收新方案。首屏 bootstrap、在线冻结、主题切换和重载恢复仍属于相关路径。
- 保留现有角色资源和其他会话的工作。未来实施前重新检查工作区、暂存区和相关文件，避免覆盖并行修改。

## 3. 总体流程与职责

推荐流程：

**身份与风格规划 → 成对候选生成 → 生产颜色派生 → 可读性硬门槛 → 差异与材质初筛 → 真实页面评审 → 用户选择 → 定稿验收。**

代理先完成技术与视觉初筛，再为每套保留 2—3 组成对候选；用户通过“更喜欢哪组”和少量偏好反馈决定取舍。候选数量是起点，可以按实际质量收敛，不要求用户输入 HEX、逐项调 token 或确认所有技术参数。

可读性不达标的候选不得靠材质或差异度高分补偿。合格候选才进入排序；排序分别说明阅读余量、材质层次、身份一致性和最近邻相似性，不以一个总分替代判断。

## 4. 身份色与十套风格的分配

### 身份来源

从角色源色、可核实的代表色和用户表达的偏好建立身份候选，十套统一重新策划。现有正式配色作为诊断与比较基线，不默认锁定其色值、背景或整体气质；只有用户明确要求保留的身份方向或颜色才作为约束。官方品牌色可作为有来源的备选，不把未经核实的 HEX 标为官方标准。

允许多款使用蓝色或紫色。十套风格的差异同时来自表面冷暖、明度、彩度、强调色性格以及角色装饰，不强制色相相隔 25°，也不为了填满色环改掉身份。

### 风格配方

为每套建立一份简短的风格说明，包含：

1. 身份色及依据；用户明确要求保留的偏好。
2. 表面冷暖与染色程度，例如中性瓷、暖象牙瓷、冷调雪青瓷。
3. 浅色的明暗层级与深色的近黑、深染色或较亮表面倾向。
4. 强调色的柔和、鲜明或沉稳倾向；与相似皮肤如何区分。

以上是代理策划的候选维度，不是要求用户回答的配置问卷。先做十套风格的整体安排，再逐套生成，避免完成后才发现大量雷同。

可从 [Radix Colors](https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale)的背景、交互、边框和文字色阶，以及其[自定义色阶工具](https://www.radix-ui.com/colors/docs/overview/custom-palettes)取得起点。其他成熟主题仅作为素材备选；采用前核查来源与许可，不把终端主题直接认定为适合本项目的陶瓷界面。

## 5. OKLCH 候选生成与约束求解

### 输入与输出

每套输入包括身份色、表面冷暖、明度与彩度范围，以及用户明确指定的颜色锁定项；不因为已发布而默认锁定旧配色。代理可设置合理默认值；候选必须保留完整参数和固定随机种子，便于复现。

内部使用 OKLCH 组织色相 H、明度 L 与彩度 C，输出采用现有派生函数可解析的、不透明 `#RRGGBB`。不直接导出 OKLCH 字符串：当前输入格式白名单与生产派生解析能力并不完全相同。

输出包含候选 ID、所属皮肤、风格说明、完整浅深两组 token、生成参数、输入摘要和检查结果。可选 `chartSeries` 不计入 12 个标量 token；其实际生产接线核实前不作为候选生成的必填能力。

### 求解顺序

1. 根据风格范围生成页面、面板、高光与阴影，保留彩色背景的可能性，不将所有皮肤固定成同一组低彩度灰白。
2. 经现有生产规则得到陶瓷顶部、底部、凹槽、交互背景等实际色源。
3. 针对文字实际出现的背景组合求解前景色。优先保留身份色相，调整 L；必要时调整 C，避免刺眼、发灰或超出色域。
4. 对强调色的真实文字、图标、选中态和填充用途分别检查。当前单一 `accent` 承担多个用途时，取同时满足其所有必要用途的值，不只选“对面板达到 3:1”的值。
5. 做 sRGB 色域处理，优先在允许范围内降低 C。不得直接裁剪 RGB 通道后继续声称色相和对比度保持不变。
6. 转成最终 HEX 后重新派生并检查全部约束；颜色舍入、背景变化和色域处理都可能改变结果。

明度范围和层级关系按风格定义，不锁死统一的 page/panel/highlight L 值。单前景、固定背景的可行区间可用有边界的搜索求解；多背景或存在派生耦合时必须检查所有约束，并设置最大迭代次数。无解时记录原因、废弃或换配方，不无限循环，不降低正文阅读门槛。

最大可显示彩度只是色域边界，不作为强调色目标。浅深版共享身份与风格说明，分别求解，不机械反色或仅混入固定比例的黑白。

## 6. 可读性硬门槛与实际角色检查

### 阈值

- 正常交互状态中的普通文字，包括次要说明、输入占位文字、按钮文字和图表标签：对实际背景至少 **4.5:1**。
- 主文字优选目标为 **7:1**，用作阅读余量；不得因此把 4.5:1 的普通文字最低要求解释为所有文字都必须达到 7:1。
- 符合大字条件的文字可按 **3:1** 检查；必要图标、控件识别信息、选中或焦点状态、承载数据含义的图形按适用条件检查 **3:1**。
- 强调色作为普通小字时仍需 4.5:1；强调色填充按钮的文字还需独立检查其文字对填充色的对比。
- 纯装饰线稿、阴影、非必要网格和禁用状态记录适用范围，不把所有装饰描边强制成 3:1。

依据：[WCAG 文字对比度](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)、[非文字对比度](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)。以未舍入的比值判定，不能将 4.499 四舍五入后判为通过。

### 实际使用位置

建立“元素或颜色角色 → 前景 → 背景 → 状态 → 阈值”清单，至少覆盖：

- 页面与面板文字、指标数字、凹槽说明、输入与占位文字。
- 按钮的默认、悬停、选中、焦点，以及强调色文字和图标。
- 图表标签、数据标记与必要坐标信息；日历、设置和弹窗的相应角色。
- 陶瓷渐变的实际文字区域，以及透明叠加后的有效前景与背景。

不能只对 `panelBackground` 计算。透明度先按实际背后颜色合成；渐变检查文字所处区域的最低对比组合。计算以前景与背景实际色源为准，不把抗锯齿后的字边像素当作文字颜色。复杂叠加无法自动可靠判断时，明确标记待人工核验，不能视为自动通过。

当前 `controlText`、`controlBorder` 被输入白名单接受，但没有在 `paletteDeclarations` 中独立映射；图表实际颜色还包含应用自身读取和分配的变量。评分器先核实接线，检查真正生效的 `--ink`、`--muted`、`--chart-text`、`--active-ink` 等角色，不把未生效 token 的“达标”算进通过项。

既有绿色/红色状态小字属于固定 CSS 色，可能无法靠这 12 个 token 修好。实施计划 M1.4 单列受限兼容分支：先证明必要位置失败，再仅为角色浅色模式覆盖两个既有颜色变量；classic、深色、几何和 token/声明清单保持。其他无解接线仍走下面的最小建议流程，不开放任意样式改造。

如现有接线使某身份色在全部用途上无可行解，记录限制并提出最小的语义拆分建议。本方案优先沿用现有运行时，不能为了生成候选偷偷增加运行时变量或扩大编辑器范围。

## 7. 材质与跨皮肤差异评估

材质检查关注实际生产派生出的高光、面板、页面、凹槽和阴影能否表现清晰层次，光源是否一致，以及文字是否受背景和泛光干扰。明度链是诊断依据；“面板一定比页面亮”或“某个 ΔL 达标”都不足以保证陶瓷效果，不直接作为通用审美定理。

跨皮肤分别报告页面、面板、强调色及浅深成对效果的近似程度，标出每套最近邻。色差统一明确为：

`D_OK = 100 × sqrt((L1-L2)^2 + (a1-a2)^2 + (b1-b2)^2)`，其中 L/a/b 采用标准 OKLab 数值。

该尺度仅用于本工具内部比较；不与未注明尺度的“ΔE ≥12”或其他色差公式混用。阈值在试点阶段根据真实页面校准，记录其版本与用途，不宣称单一色差数值能判断整套设计雷同。

允许同色相候选通过背景冷暖、表面染色、彩度与明度倾向拉开区别，但不强迫相似色相搭配相反气质。图表多系列颜色若参与方案，需核验实际接线、背景对比、相邻系列辨识及色觉模拟；必要时配合标签或其他已有表达，不能只依赖两两色差。

## 8. 候选预览与工作台定位

### 与生产保持一致

候选预览必须走现有配色输入、`paletteDeclarations`、运行时应用及真实页面样式。推荐在隔离的开发预览中为现有配色模块提供候选数据，再加载同一套生产代码；不将候选写回正式配色文件，不复制一套新的派生函数。

首屏 bootstrap 含已有配色数据时，隔离预览应为候选同步生成测试用 bootstrap，或明确隔离其首帧影响。最终定稿仍需验证生产首屏，不能只看页面加载完成后的截图。

现有工作台的重复映射逐步退役，改为候选载入与微调台。优先支持成对候选切换、身份色锁定、实际对比度读数、局部修复和输出；OKLCH 滑杆属于后续增强，不是先完成工具才能开始设计的前置条件。

### 比较内容

- 每套保留 2—3 组候选，每组浅深同时展示，同一组合成数据、字体、视口、角色位置和透明度。
- 默认用 50% 角色透明度比较气质，另检查角色关闭及最高透明度下的阅读干扰；只检查装饰实际影响的阅读区域。
- 页面包含非空图表、多系列、密集表格、较长名称、费用和说明，避免用全零页面证明可读。
- 提供原尺寸阅读检查与缩略整体比较。十套总体比较用同尺寸缩略图和可放大的原图；十张页面不压进一张横向长图后当成阅读证据。
- 先展示关键桌面页面与必要交互状态，按 PC 基准记录实际 CSS 视口、缩放与侧栏条件；不新增手机页面验收矩阵。

代理整理每个候选的优点、最接近的另一款、硬门槛结果和剩余限制，再交给用户选择。检查流程在隔离浏览器上下文和合成数据中运行，保留用户真实服务、偏好、用量日志与缓存。

## 9. 分阶段实施建议

### P0：事实与颜色角色基线

核对当前产品状态、实际 token 接线、所有必要前景/背景组合、首屏路径与桌面验证条件。记录现有十套的诊断，并为十套统一规划身份候选与风格分工；现有色值用于前后对照，不作为设计冻结项。

交付：角色清单、可复现诊断、现有生产派生与工作台差异说明。格式检查与阅读检查分别报告，不把旧 `skins:palette` PASS 等同于新门槛通过。

### P1：两款代表性皮肤试点

推荐先做 **ChatGPT 和 Grok**：分别覆盖现有深色文字与强调色对比不足、浅色黄色强调色与表面层级的困难组合。两款均完整重新策划浅深配色，用它们校准身份表达、可读性、材质和候选选择流程。

每款先生成 3 组成对候选，代理筛成 2—3 组，完成真实页面和必要状态核验后给用户比较。用结果校准明度/彩度范围、材质诊断和差异提醒；若有效候选不足，调整配方，不用失败或近乎相同的候选凑数。

交付：少量成对页面、生成参数、硬门槛结果和简短推荐理由。试点先证明候选质量和用户选择成本，再扩展工具。

### P2：其余八套配色重设与十套整体协调

将试点流程扩展到 Claude、GLM、Gemini、DeepSeek、Kimi、Qwen、Muse、Mimo，为每套生成并评审新的浅深候选。全白层级、相近蓝紫、暖色强调与灰暗表面等问题纳入统一风格规划；不默认改成所谓官方代表色。

十套新候选放在一起协调身份、冷暖、彩度、明度与陶瓷层次；必要时回调两款试点，避免逐套看着合格、合在一起雷同。用户选择每套喜欢的候选并给出偏好反馈。已发布五套同样完成整体配色调整，不只加深文字或沿用旧方案；十套最终浅深配对都需要通过检查与视觉评审。

### P3：定稿接入与验收

十套选择确定后替换各自完整的浅深正式配色，记录每套的候选 ID、最终调整与旧值基线。已发布五套随本次统一定稿调整；接入可分批验证，但完成标准覆盖全部十套。运行 `skins:prepare` 更新必要的生成文件，再检查资源与 bootstrap 一致性；这个命令不会重新编码角色 WebP。

按实际影响执行配色、资产、类型、格式和相关测试，以及实际页面、首屏、主题切换、重载恢复、简洁模式和在线冻结路径检查。若改变共享派生或运行时接线，应补充对应回归。

恢复延期五套到正式选择器属于后续明确的产品接入范围，不能把“内部有十套候选”当作十款已经上线。验收记录注明实际开放的皮肤范围、未测项和剩余视觉意见；发布、提交与推送按届时用户要求处理。

## 10. 完成标准与失败处理

- 全部十套角色完成配色重设、候选选择和定稿，浅深共 20 个模式槽位完整；已发布五套也完成调整，身份依据、候选参数和最终色值可追溯。
- 必要文字与交互角色对实际背景通过适用硬门槛；未测或无法自动核验的组合单独列出，不混入 PASS。
- 真实页面保留陶瓷层次和角色构图；无需调整布局几何来掩盖配色问题。
- 十套整体比较后具有可解释的区别，相近色系经人工评审可以辨认。
- 工作台、候选报告与生产页面使用一致的颜色派生，最终首屏与主题切换无旧颜色残留。
- 颜色数学验证覆盖色域、最终舍入、透明合成、边界值和无解；视觉质量通过实际页面评审，不靠实现镜像测试证明。

候选失败先检查实际生效的颜色组合，再调整前景、背景或风格参数；保持身份的限制无解时说明原因，提出备选。美观不满意时回到风格配方，不让用户逐个修 HEX。生产文件在定稿前保持原状；后续替换按皮肤及模式保留可回退的原值，避免夹带其他工作。
