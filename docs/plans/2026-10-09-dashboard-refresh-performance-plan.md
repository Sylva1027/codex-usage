# 看板刷新性能修复方案与验收规格

日期：2026-10-09（Asia/Shanghai）。修订：v3，保留两轮复核的方案，另设并发施工入口。状态：**方案与 Implementation Plan 已成文，尚未实施产品代码修复，也未完成新的性能验收。**

目标：恢复网页刷新与数据刷新的响应速度，消除历史增长、异常线程和重复计算造成的持续退化，同时保留现有统计、计价、告警与冻结语义。

用户要求制定完善计划，并吸纳实际有用的复核反馈。本文件定义方案和验收要求；诊断和复核中的建议是评估材料，不作为逐项执行指令。并发实施按 [Implementation Plan](2026-10-09-dashboard-refresh-performance-implementation-plan.md) 的任务卡、文件归属和逐卡审查规则执行；施工进度只在其任务表维护，本文勾选项作为要求清单，不维护第二套进度。旧测试通过不覆盖未来改动。

## 1. 判断依据与方案取舍

证据入口：[10-08 诊断](2026-10-08-dashboard-perf-regression-diagnosis.md)、[10-09 诊断](../validation/2026-10-09-refresh-performance/refresh-performance-diagnosis.md)、[客户端测量](../validation/2026-10-09-refresh-performance/client-audit.md)。

修订依据：[第一轮计划复核](../validation/2026-10-09-refresh-performance/plan-review-2026-10-09.md)、[第二轮计划复核](../validation/2026-10-09-refresh-performance/plan-review-2026-10-09-second-pass.md)。新增实测用于确定关注项；固定输入、有效价目、预热和探针统计口径统一后，才形成本轮验收基线。

两轮报告测得：今日完整刷新约 16–24 秒，跳过同步约 1.2–2 秒；浏览器脚本与布局主要为几十毫秒。两轮参数、运行条件不同，不能据此断言一夜之间又退化了多少。四项机械修复的副本 A/B 为完整路径 22→11.3 秒、跳过同步 2→1 秒；这是阶段参考，不是最终性能承诺。

当前源码复核支持以下因果链：

- `/api/usage` 默认等待 `loadUsageStore()` 完成同步，日期筛选没有裁剪前置同步工作。
- 逐文件反查 `events.source_path` 缺索引；工作量随文件数与事件数共同增长。
- `degraded/partial`、失败文件未发布的新指纹、缺少归属记录都可能触发 home 重规划。仅删除两个状态条件不能保证停止重试。
- 历史新高、全局排名 home、限额观测、metadata 会话去重与模型活动等功能在读路径重复处理历史数据。
- 峰谷计价每事件新建 formatter，模型解析每事件重建价目索引。
- 同步文件探针、SQLite 查询和解码在 HTTP 进程中同步执行，可能阻塞其他请求。

必须纠正的建议：

- 索引在 `UsageStore.open()` 中无条件补建即可，**不为这一行索引抬 schema 版本**。
- 当前 `i18n.js` 的 DOM 键缓存已经是 `WeakMap`，不把报告所述强引用泄漏列为待修缺陷。
- 定价刷新后的 `loadUsage({ skipCheck: true })` 不重复完整同步。
- 不直接过滤历史新高查询到今日，不排除 `archived_sessions`，不通过取消告警提高表面性能。
- 不用短 TTL 改变手动刷新语义，不把 TTL 命中后的速度算成真实同步提速。
- 暂不删除发布时的 `foreign_key_check`；先消除不必要的重复发布，再评估残余成本。
- 不按旧数据 fingerprint 单独跳过整个 render；日期边界、价格、范围、语言和界面状态都可能独立变化。

## 2. 范围、正确性约束与完成标准

### 本轮范围

必做：数据库查询与计价热点、Codex 稳定失败复用和增量规划、读路径重复计算、事件循环响应、必要的前端重复渲染修复、测量与回归证据。

不纳入：TPS 新布局、分享图片、皮肤配色、删除历史数据、修改上游日志、新生产依赖、通用缓存框架和全仓重构。若其他任务先修改 TPS 投影或页面结构，按实际版本重新定位接入点，保留其新增字段与行为。

### 正确性约束

1. 用量、费用、纪录、周期对比、TPS 分组与覆盖率对同一数据和时刻保持一致；默认、dashboard、summary、full、CLI 的既有差异保持有意且可解释。
2. 坏线程的陈旧候选可保留用于回滚，但不得进入当前可信统计。健康兄弟线程继续发布；无法证明归属的错误仍按现有规则隔离。
3. 稳定坏内容可以复用失败判定；`LIVE_SOURCE_CHANGED`、读取失败、发布回滚等瞬态失败必须保留恢复路径。
4. 尝试过的内容与成功发布的内容分开记录，不能把失败尝试指纹冒充已发布指纹。
5. 保留原内容探针能力，包括同尺寸、同 mtime 改写和 SQLite WAL 变化；本轮不将其降为单纯 `size+mtime`。
6. 保留归档迁移、跨文件线程依赖、跨 home 身份变化、真实删除与暂时不可读的区别。
7. `freeze/snapshot/asOf` 保持现有契约；未知快照仍为 410，full 与冻结的不合法组合仍被拒绝。不能因缓存改变冻结路径原有计价行为。
8. 手动刷新仍检查当前来源；并发同步仍由已有 `syncPromise` 合并，不新增重复写入者。

### 性能目标

以下是**拟验收目标**，适用 P0 固定的本机数据规模、已有索引、服务预热后、正常桌面负载。用完整响应读取时间统计，不能只测响应头或缓存命中样本。

- 今日默认刷新、源文件无变化：p50 ≤1 秒，p95 ≤1.5 秒。
- 今日 `skipCheck=1`、没有正在进行的同步：p50 ≤300 毫秒，p95 ≤500 毫秒，覆盖摘要缓存未命中和命中两类。
- 代表性单线程追加：默认刷新 p95 ≤2 秒；记录该线程文件大小。超大线程不以此宣称任意大小均有相同上限。
- 同步期间轻量请求（`/index.html`、`/api/pricing`、`/api/imports`、`/api/status`）：p95 ≤100 毫秒，最大值 ≤250 毫秒；测试客户端在独立进程运行。用量/摘要/冻结创建请求不属于此集合。
- `skipCheck` 保持等待已在进行的 `syncPromise` 的语义，不返回同步中间态或悄悄切到旧快照。同步期间单独记录等待同步时间、之后的摘要时间和总耗时；其总时间不适用无同步时的 500 毫秒门槛。
- 在 P0 的隔离冻结源上，稳定文件（含已知坏 JSON）连续同步：预热后全文解析次数及 reader 原文流读取字节数为 0（内容探针字节另计），候选写入和发布次数为 0；reader 包装函数的调用与缓存命中分别计数，不能将函数调用等同全文解析。必要检查时刻与诊断元数据更新可保留。
- 一份 rollout 改变：只重新全文解析改变的文件，只重新构建受影响线程；未变化的兄弟线程不重新发布。
- 2 倍、4 倍隔离历史规模：不变文件的全文解析数仍为 0，今日读路径不能重新退化为逐请求全历史计价；P2b 就验证工作集能容纳或由持久化投影承接，不到 P6 才首次测试容量。
- 隔离冻结源、无提交时：published fingerprints/warnings 各最多解码 1 次/轮（已缓存可为 0）；发生提交时，按实际变更修订更新已解码视图，不按文件循环反复解码全表。
- 同一物理文件、同一稳定性检查窗口的内容摘要实际计算最多 1 次；统计同时覆盖 `enabledPerfSourceStat` 和 `perfContentFingerprint`。读取前、读取后、发布前为不同验证窗口，分别计数并保留新鲜探针，不能把“每窗口一次”写成“整轮只检查一次”。

冷启动单列“已有库首次打开”和“首次全量建库”，记录索引建立、投影预热和总耗时。后者不要求亚秒完成。暖态不能替代冷态报告，进程内复用不能声称跨重启持久化提速。

### 阶段预算与规模限制

P0 重测后，以同一份隔离数据逐批对照以下中间目标：

- H0/P1：反查查询计划必须走索引，原逐文件 session 反查循环目标 ≤100 毫秒；记录完整暖 sync 及其每个残余阶段，不将它等同总请求提速。
- P2：不变源暖 sync 目标 p50 ≤800 毫秒、p95 ≤1.1 秒，全文解析与候选发布均为 0；超过预算时先解决重复探针、簿记或容量失效，再进入下一批。
- P3/P4：不变源 sync 的 p50 预算 ≤600 毫秒，摘要 ≤250 毫秒，metadata/周期对比及序列化等其余请求工作合计 ≤150 毫秒。以每个请求的非重叠阶段相加核对端到端 ≤1 秒目标；不能把不同样本的分位数相加冒充一次请求。

内容探针必须单列：复核测得 store 探针约 400 毫秒，但它尚未包含 core 前后验证；该值不是最终探针总成本。保留完整检查时，摘要 I/O 仍随文件数/探针字节数增长，worker 只能隔离 HTTP 阻塞，不能自动使手动同步更快。2×/4× 增长须同时报告探针延迟与投影容量，不将当前规模的一秒目标外推为任意规模保证。

GC、I/O 等待与 CPU profile idle 作为残余观察项，不直接当作互斥阶段相加。若当前规模端到端或静态响应超预算，P4 处理对应剩余瓶颈；若增长时缓存容量超限，P2b 提前处理。不得等最终验收才发现必须新增实施阶段。

未达到绝对目标时必须保留实际值和残余归因，执行第 7 节的升级决策；不能通过改低目标、漏测慢样本或取消功能标记完成。

## 5. P2：停止稳定失败全量重试，并让变化只影响相关线程

依赖：P1。文件：[usage-store.js](../../src/usage-store.js)、[usage-core.js](../../src/usage-core.js)、[codex-thread.js](../../src/perf-sources/codex-thread.js)，必要时涉及 [codex-jsonl.js](../../src/perf-sources/codex-jsonl.js)。

### P2a：稳定失败的尝试记录

- [ ] 优先建立每个 `UsageStore` 实例私有的最近稳定尝试记录，不新增 schema 或公开 API 字段。签名包含 home 身份、排序后的完整路径集合、现有内容指纹以及解析/发布策略版本。
- [ ] 记录稳定解析结果、已隔离的线程和相应告警；仅在前后来源窗口一致时可复用。成功发布版本仍由原事务维护。
- [ ] 同签名的确定性坏内容不触发再次全文读取；指纹、集合、身份或方法版本变化立即重新判断。临时读取失败、来源读取期间变化、发布失败不记作可跳过的成功轮次。
- [ ] 覆盖 `shouldPlan` 的所有触发源，包括失败文件未发布指纹和没有 current ownership。仅使用已验证的稳定尝试记录绕过重复读取，不伪造 ownership 或发布指纹。
- [ ] 联合检查 home 规划、`pendingChange` 预扫、逐文件 `perfFileNeedsRefresh` 与发布收尾，防止规划跳过后又在另一条路径重读。同一文件的用量提交与 perf 尝试分别判断，不能因 perf 失败复用而跳过尚未提交的用量更新。
- [ ] 复用失败结果时重新投影 `partialHomes/degradedHomeIds/sourceWarnings`；不能因本轮没有执行 reader 就丢失告警，也不能每轮累加同一告警。
- [ ] 修复坏文件后自动恢复；真实删除和归档迁移清理对应尝试记录。close/open、实例销毁和方法变更使记录失效。

### P2b：复用未变化文件的标准化投影

- [ ] 复用 `readCodexRolloutMetadata` 的现有私有投影，不缓存原始 JSONL 全文，不另写一套解析器。键包含规范路径、来源身份、内容指纹和解析方法版本；先查询稳定窗口内的当前键，不能先全文读取再判断命中。
- [ ] 规划仍使用完整文件集合证明归属；仅未命中的文件需要全文读取。保留前后文件集合与指纹稳定性验证，不仅校验变化文件。
- [ ] 依据新旧归属和依赖映射建立受影响线程集合；改变文件关联的全部 rollout（包括归档片段）一起构建。身份重归属、删除和跨 home 迁移纳入原有保守处置。
- [ ] 未变化线程复用已发布候选，不重新 delete/insert。稳定失败线程仍隔离，不能只发布其好文件部分。
- [ ] 不变同步不进行候选重写、空发布和内容无变化的缓存清空。`checkedAt` 继续更新；`generatedAt/indexedAt` 保持现行语义，若需改变先明确契约并补兼容测试。
- [ ] 只保留当前文件版本的投影，删除/替换立即淘汰。内存预算按 P0 全量实测的 4× 工作集至少留 25% 余量确定，首轮候选上限 192 MiB；记录实际 heap/RSS，不能把标准化序列化字节等同真实堆占用或只凭抽样外推通过验收。使用简单有界淘汰，不新增配置界面。
- [ ] 在本阶段就跑 1×/2×/4× 容量检查；若候选上限不能容纳，或顺序遍历发生反复淘汰/重新全文解析，立即将持久化私有投影纳入 P2b。保留有界 RAM 和可恢复失效语义，不将这项推到 P6 再返工，也不自动突破上限。
- [ ] 缓存投影视为只读输入；检查 planner/builder 的全部调用，避免一次统计改变缓存对象并污染后续规划。只在确实会改写的局部复制，不逐请求深拷贝整个工作集。

进程内缓存重启后需重新预热，这是明确边界。持久化投影若触发，应在 P2b 明确表/版本、原子写入与失效、恢复和迁移回退，再实施并验证；不无条件标脏全库，尝试记录不得泄露到公开 report。内容探针时间和投影容量是两个独立增长限制，解决其一不能视为另一个也通过。

检查：连续三轮不变坏内容后告警/排名相同且全文读取为零；同 home 健康线程追加只影响该线程；坏内容修复、读取失败恢复、发布回滚重试、同尺寸同 mtime 改写、WAL 改写、归档迁移、新增无样本文件、真实删除、未知归属均保持原行为。

执行：`node --test test/perf-codex-index.test.js test/perf-codex.test.js test/perf-state.test.js test/perf-store.test.js test/perf-codex-api.test.js`，同步验证内存与 store 路径一致。

退出条件：不变轮次不会重复全文解析和候选发布，单文件变化不重建无关线程，当前规模达到第 2 节 P2 sync 中间目标，4× 容量已验证；故障仍被正确隔离且可恢复。测试应验证这些行为，不能仅修改旧断言使取消告警通过。

## 6. P3：读路径复用与一致失效

依赖：P1、P2；只有先识别真实数据变化，才能避免每次 sync 清空全部缓存。文件：`usage-store.js`，必要时 `server.js` 与既有计价更新接入点。

### 修订与缓存边界

- [ ] 为每个 store 的实际提交变更建立实例内修订标记；覆盖用量替换/删除、限额变化、TPS 候选与发布状态、来源身份及 service-tier evidence。事务回滚不标成成功变更；事务中已读取的派生缓存失败后清理。
- [ ] 不把 `checkedAt/generatedAt` 的例行更新视为用量变更；不只依赖尺寸/mtime 来源 fingerprint 判断缓存有效。
- [ ] 同一索引可能被 CLI 或其他连接提交：使用 SQLite `PRAGMA data_version` 检测外部提交，失效派生结果并重载必要持久元数据；仅比较同一连接的前后值。自身连接的提交仍依赖上述修订标记，不能误以为它会检测自身写入，见 [SQLite 官方语义](https://www.sqlite.org/pragma.html#pragma_data_version)。
- [ ] 各派生结果按所需修订失效；先用简单单条 memo，只有实际切换开销值得保留更多项时才加有限条目。close/open 清理；live 与 frozen store 实例分开。

### 历史新高、限额、metadata、周期对比和全局 home

- [ ] 历史新高分成“按完整 scope 计算各周期冠军”和“判断冠军完整落在当前范围”。前者按数据修订、有效价目（含汇率）、service-tier evidence、时区与规范排除集合复用；后者每请求执行，保留严格新高、并列和至少两期可比规则。
- [ ] 不给全历史纪录计算直接添加今日 WHERE。价格或历史数据改变时允许一次重建，随后今日/week/month 共享同一历史结果。
- [ ] `quotaObservations()` 复用已提交行的规范映射；每请求仍根据当前或冻结 `asOf` 计算窗口、stale、倒计时和 reset，不能缓存这些时间相关结果为永久值。
- [ ] 将 `metadata()` 的 `COUNT(DISTINCT session_id)`、按 home 统计与模型集合纳入实际数据修订缓存，无变化 sync 不清空；先复用已有 metadataCache，不新增维护计数表。`generatedAt/homes/warnings` 按各自实际语义更新，模型活动的未来事件过滤和 `asOf` 边界每请求仍正确。
- [ ] 保留现有 `periodComparisonCache`，按实际数据变更失效，保留时区、日历日和排除集合键；响应 `asOf` 使用当前时刻。跨日/周/月与冻结时刻必须正确。
- [ ] `rankedHomeIds` 使用必要身份列/全局集合的聚合投影，避免解码全部 sample JSON。保留 partial/degraded 发布过滤及全局语义，不能仅从“今日已取样本”推导全局 home。
- [ ] 首轮保留完整 `summary.perf` 契约，不因用户当前看用量而省略该字段；TPS 新独立区域可能同时消费它。
- [ ] 不首发整段 HTTP JSON 缓存。若仍需该优化，必须覆盖所有过滤、价格、时间边界、quota、snapshot/full 与响应时刻字段，单独复测后再进入范围。

检查：scope 顺序归一、来源开关、价格/汇率/档位变化、历史修正、并列纪录、跨日与 quota reset、不同 freeze/snapshot 实例均正确；反复相同输入不重复全历史计价。

执行：`node --test test/usage-store.test.js test/three-path-parity.test.js test/perf-summary-parity.test.js test/perf-summary.test.js test/perf-server.test.js test/server.test.js`。

退出条件：今日读路径达到第 2 节门槛，历史新高暖态只执行范围判定，限额时钟和冻结契约不因命中缓存而失真。

## 7. P4：网页响应与残余成本处理

依赖：P2、P3。先重测最长连续阻塞，再决定最小改动；这一步是最终验收必经步骤，具体实现按证据选择。将独立执行器的设计/验证工时纳入预留，不假设插入 `setImmediate` 就一定能通过 250 毫秒门槛。

- [ ] 在事务之外，对全文件指纹/解码等长循环按约 8 毫秒工作预算使用 `setImmediate` 让出事件循环。单个较慢操作需另行定位，不能靠固定“每 N 个文件”保证最大延迟。
- [ ] 读事务和发布事务内不插入 `await`，避免共享连接在事务中被其他请求操作。让出后仍做原有来源稳定性验证。
- [ ] 复核 P1 探针去重的窗口边界与读取字节，保留发布前新鲜复核和同尺寸改写检测；本阶段优化残余 I/O/调度，不再首次处理探针重复调用。
- [ ] 分别测发布事务、摘要读事务、metadata/周期统计、序列化的最长不可中断时段。每段超过 200 毫秒即触发定向优化或隔离评估，不能在禁止 await 的事务中用“8 毫秒让出”掩盖长块。
- [ ] 保留现有并发同步合并、错误返回和重试行为，不用 TTL 跳过手动检查；`skipCheck` 的等待/无等待两类按第 2 节分别验收。

升级决策：

1. P2b 的容量问题在 P2b 解决；P4 单列持久化后剩余的冷态读取和内容探针预算，不通过增加缓存声称消除了探针 I/O。
2. 若同步/发布使静态或轻量 API 超过门槛：将相应工作移至一个 worker/子进程，HTTP 用独立读连接；复用既有 `UsageStore`，保持单写者。手动刷新仍等待其发起的同步结果，静态资源无需等待。
3. 若超标块位于 HTTP 的摘要、首次纪录构建或其他查询，单独移走 sync 不算解决。将对应计算安排到独立执行器/独占查询连接，或在实测支持时预计算；事务与结果仍来自一致的已提交视图，禁止在共享连接事务中插入 await。
4. worker 方案需明确私有消息边界、读侧 homes/evidence/告警同步、崩溃重启、关闭清理、初始化和冻结一致性。不得共享 `DatabaseSync` 实例，不在候选发布中途冒充完成；读侧缓存依据已提交修订失效。

升级属于同一性能目标的条件阶段，必须先交付残余 profile、拟改文件和新增测试，再实施该方案；不把“暂未做架构升级”当作性能验收通过。原始用户数据始终保留。

退出条件：同步期间网页和轻量 API 达到响应门槛，所有超过预算的单段同步操作都有实测归因或已消除。

## 10. 执行批次、预计工作量与回退

以下阶段描述总体工作量；实际派工和进度以 [Implementation Plan](2026-10-09-dashboard-refresh-performance-implementation-plan.md) 为准。它拆为 28 个基础单元、5 个条件单元，最多 3 个 worker 与 1 名主审协作；共享 store 的增量/读路径修复串行，计价、独立客户端修复和固定快照测量并行。每张卡由 worker 交审、主审确认质量；不达标及时返工，依赖卡不得提前施工。

行为依赖仍为 **H0 → P0 → P1 → P2a → P2b（容量分支在此收口）→ P3 → P4 → P6**。客户端中不依赖服务端契约的机械修复可在基线通过后并行；自动刷新调度待 P2/P3 稳定后实施，联合交付必须通过 P5。每批形成可独立检查和回退的变更，不依据旧计划派发其他任务。

- H0：约 15–30 分钟，独立索引修复、恢复点和最小 A/B。
- P0：约半天，产出可重跑基线与测量条件。
- P1：约半天，消除确定的查询/计价/解码热点，单独 A/B。
- P2：约 1–2 天，重点是稳定失败、归属与发布一致性，不压缩故障测试。
- P3：约 1 天，复用历史计算并验证失效与时钟。
- P4/P5：约 1 天，按残余 profile 控制改动，验证网页响应与客户端。
- P6：约半天至一天，联合、增长和真实桌面复测。

核心预计约 **4–6 个工程工作日**；额外预留 **1–3 天**用于 P2b 容量分支或 P4 独立执行器/长读事务处理。若两项均触发，分别估算并更新排期，不声称这份预留覆盖任意架构工作。以上取决于 P0 容量与 P3/P4 实测，是工作量估算，不是日期承诺。

回退要求：

1. H0 前保存其最小恢复点，P1 前完成 P0 的完整工作集恢复演练和一致性索引备份；每批记录前后摘要、归档/commit 标识与仅本批逆向补丁。有隔离提交时可定向 revert，归档路线则先在临时目录恢复比对，不直接覆盖其他任务新增内容。当前未提交/未跟踪改动不得被 reset/clean 或一起误提交。
2. P1 索引为兼容性增加，回退代码可保留它；不为回退删除索引、降版本或清空真实用量库。
3. P2/P3 实例内缓存随进程重启清空，回退恢复旧重算路径；缓存失效不删除业务数据。
4. 出现费用、归属、告警或冻结错误，停止推进并回退最近一批，再保留最小失败样例修复。不得仅禁用断言或隐藏字段继续交付。
5. 条件阶段若引入 schema，另附新旧兼容策略与迁移故障测试；不能直接将旧程序打开新库作为回退方案，也不能用旧备份覆盖期间新增索引数据。
6. 正式服务切换前全部检查在隔离实例完成；产品重启沿用现有 CLI 生命周期，记录切换版本和重新打开的冷态耗时。

只有业务等价、恢复路径与性能目标均有新版本证据时，才将本计划标记完成。
