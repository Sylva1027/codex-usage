## 建议

围绕现有 `dashboardHistory` 和 `summaryProjectionCache` 做一件事：**一次读取建立可复用的事实统计，价格变化只重新报价。**

具体包含两个互补部分：首次请求减少重复全量统计；调价请求复用有界、按原顺序保存的计价输入，不再次构造整张时间线、各维度分组和仓库统计。保留逐事件金额运算与累加顺序，不能用“按模型汇总 token 后乘单价”替代现有计价。

不把收益押在更大的事件结果 memo、恢复覆盖索引、跳过验证、关闭 scheduler 或另加一个工作线程上。也不先推广此前被否决的模型名 resolver/最低费率微调。

## 第一部分：分开事实与报价的失效边界

扩展现有单槽 projection，而不是新建通用缓存系统：

1. **事实统计**：时间桶中的次数、token、去重会话、渠道、原始模型维度，以及仓库/观测/周期统计。跟随实际事件修订、来源身份、完整冷热权威、范围、时区和排除集合失效。
2. **报价结果**：总费用、时间桶模型费用、币种、priced/unpriced/minimum-estimate、原因与版本。跟随本次请求绑定的完整 catalog 和 tier evidence 失效。
3. **当前时间字段**：quota、asOf、未来观测过滤及相对周期仍使用本次 now；不能顺手缓存成静态事实。

模型展示名是一个交叉依赖：目录增加/移除模型可能改变别名归并，不能把所有 model 分组都宣布成与 catalog 无关。保留原始模型维度；只有实际解析映射未变时，才复用规范模型分组。映射变化先沿原完整重建路径，不在首卡加入复杂重分组逻辑。价格识别沿现有请求绑定完整 catalog 机制，不能只比较 checkedAt 或模型键数。

同理，signature-only 的 tier evidence 变化也必须失效，即便 `storeRevision` 未递增。外部写入、回滚、close/open 和私有冻结实例沿原来的修订/隔离机制处理。

**收益边界：只拆缓存不足以解决首次请求，也不能保证调价达到2秒；它是避免重复工作的必要接点，不是最终性能结论。**

## 第二部分：首次构建只遍历事实一次

从已有 `costEventsForRange` / timeline 扫描出发，逐卡把已明确重复的消费者接到同一次同步读快照；不要建立新的全功能报表引擎。

推荐迁移次序：

1. 先接仓库计数、token、路径集合、session 集合和最早出现时间，替代 `repositoriesRange` 的重复全量 GROUP BY。
2. 再接 metadata 原始模型库存与 `(channel, model, home)` 观测。未来事件场景继续用现有按 asOf 的正确回退；不把 summary 的 excludeHomes 错误应用到 metadata 库存。
3. 最后处理仓库周期的16项指标，复用原有指标定义与期间边界；已有有效模型/日 rollup 查询继续使用，不重复再实现一遍。

必须保留当前 SQL 对拍契约：仓库 `MIN(path)` / `MAX(kind)` 与 period 的 `MIN(kind)` 并不相同；`COUNT(DISTINCT NULLIF(cwd,''))`、跨冷热 DISTINCT session、同额排序以及 `session_ids` 最早事件次序都不能省略。相同最早时间的 payload 比较沿用现有少量 tie 查询，不为它保留百万完整行。无法精确保持的条件先保留原 SQL 回退。

所有求和仍保持原语义。该方案会用少量 JS 累加替换重复 SQL，**移除扫描不自动等于净提速**；必须实际核对完整 HTTP，而不是只数“SQL 从几次变一次”。

第一张窄卡只做仓库消费者，断言：完整结果等旧实现；真实重复扫描被移除；tie/排除条件仍正确。它应有独立可审实物，不让 worker 一次承担上述三个消费者。

## 第三部分：保存有界的计价输入，调价按原序重放

事实不变而价格改变时，继续从 SQLite 解码百万次并重建 Map/Set 是浪费。建议在现有 projection 内保留**一份紧凑的计价输入缓冲**：

- 只存 `estimateEventCost` 实际需要的数值、状态和小字典 ID；不是完整事件、会话详情或每事件计价结果对象。
- token、timestamp、requestInput 等用保持原精度的数值列；缺失/未知用明确状态位，不把 null 与0混淆。模型、渠道、sourceKind、tier、context 和 TTL 等原始字符串使用字典。
- 保留原消费顺序及时间桶 ID。每条事件按旧乘除顺序重新计算金额，再按旧顺序进入总费用和桶费用累加器；不得按模型分组后重新关联浮点求和。
- 暂不保存由旧价格推导的 context 阈值分类、峰谷分类、最低价类别或币种。新 catalog 可能改变这些规则，必须从原事实重新判定。
- 尽量从现有 `estimateEventCost` 提取并共享“规范输入→报价”步骤，现有公开函数继续调用同一套规则。不要复制第二份220行计价器，也不要用 benchmark 专用简化报价器。
- 对同一目录下重复的原始模型，沿当前解析函数得到一次结果并在本轮复用；这是整个报价路径整理的一部分，不单独重开之前已否决的跨请求 resolver memo 微优化。

建议先把新增缓冲设计为单槽、最多约128MiB的已分配数值存储与保守字典预算；具体列宽需列清后计算。百万条纯数值/ID理论量级约64–96MiB，**这不是实测 RSS，也不是承诺总峰值**。到达预算即放弃保留该缓冲，仍以原流式路径完成完整请求；不能返回半份数据。只保留一份，不同时留原对象数组、旧缓冲及新副本。最终仍按服务 PID 的1GiB RSS门槛验收，7GiB只是测试 Job 上限。

这会增加少量有界内存以减少重复取数和解释，适合当前约196MiB服务 RSS的基线；若现有普通对象重建仍占主要成本，应在同一报价接点用复用输入结构完成，不扩成列式数据库或代码生成器。

**新增缓冲必须挂在既有验证之后。** 每次请求照常完成冷文件/manifest/身份验证，即便事实及报价缓存命中，缺段或篡改也必须整体失败。不允许直接命中 projection 而绕过 `withVerifiedHistoryArchiveCandidate`。

## 实施范围与不选的替代方案

主要接点：

| 文件/现有机制 | 建议变化 |
| --- | --- |
| `src/usage-store.js` 的 projection、timeline 消费和生命周期 | 分开事实/报价失效；逐个融合重复消费者；拥有唯一有界缓冲 |
| `public/timeline-utils.js` 的构建逻辑 | 必要时提取现有事实/费用累加步骤；公开默认调用和客户端语义保持一致 |
| `src/pricing.js` 的事件计价/费用累加器 | 共用正规化与报价规则，支持已有解析结果，保持金额和原因字段精确一致 |
| `src/usage-types.js`（仅确有需要时） | 描述新增内部形状，避免第二份公共协议 |
| `src/usage-executor.js` 的现有 pricing context | 原样沿用；仅回归验证，不另建并发通路 |
| 对应 history/pricing/timeline 专测 | 在既有用例中加入实际失效、调用和完整载荷断言 |

以下暂不做：

- 不改 `history-backup.js` / `history-archive.js` 的首次完整内容验证。它是约3.4s的真实成本，但仍小于统计构建；先保留这个确定的正确性基础。
- 不把“按日/模型加总 token 再报价”当等价计算。上下文/输出阈值、峰谷、未知细节的最低价分支、币种和浮点次序都使这种替换不成立。
- 不增加持久化结果 sidecar、schema22/覆盖索引、数据库迁移、全局无界 memo 或另一套 authority。
- 不靠启动预热、把工作藏进 seed、关闭 scheduler、后台提前返回不完整结果来通过首请求指标。
- 不同时推广 overlay、多段、任意 preset 的新快路；先限现有 all-hot 及单段无overlay的已验证 SQL 分支。其他路径继续原正确实现。

## 最小验证顺序及停损条件

恢复实施后依次做；本次分析没有执行这些测试。

1. **小行为夹具**：对照旧算法完整 summary/metadata/period payload；含冷热交界、仓库 tie、Unicode排序、同名home、排除home、future观测、UTC/local与跨日。
2. **报价失效夹具**：同 checkedAt 改真实 rates、改变模型键/归并、阈值/峰谷/fast/币种、unknown/free/auto-review、cache-write TTL及signature-only tier变化。逐事件 estimate 与全部聚合金额严格比较，不加宽容差；新的计价缓冲也不得使用原先已停用的事件结果 memo。
3. **真实失败**：命中缓存后移走/篡改候选仍整体失败，恢复后结果一致；事实写入/回滚和冻结 A、实时 B并发继续使用各自 catalog。预算耗尽确实走完整流式回退。
4. **一次中等规模完整 HTTP 对拍**：已有100k工具、相同输入、核对每次实际绑定的完整 catalog，默认 scheduler保留。记录first、实际调价重算、同价目暖读、服务RSS和阶段耗时。目录不同不得宣称严格因果 pair，不为好看数字重跑。
5. 只有结构收益明确且资源正常，再做一次1M诊断；达到接近目标后才做原定20×20、两种布局、WAL及最终工程门禁。小数据收益不能线性外推为1M已通过。

优先复用测试：`history-summary-projection.test.js`、`history-summary-fused-groups.test.js`、`history-timeline-direct-cost.test.js`、`history-timeline-currency-order.test.js`、`pricing.test.js`、`claude-pricing.test.js`，以及现有 SQL 冷读/冻结/缺段/executor并发用例。

费用层拆分时，原来断言“换价必须调用整个 timeline”的测试需改为：费用确实按新目录变化、事实分组没有重扫、返回对象仍隔离。这是更新内部实现断言，不是取消报价行为证明。

所有执行 Main 串行、Windows Job限额、Available≥8GiB预检；不用产品树副本、不并发百万/全仓。某卡没有可复核净收益即停止该卡，不把补丁全堆上再跑百万。

目标预算只能用于决策，不能写成结果：在保留验证的前提下，首次统计构建需要从约13s降到约5s量级，整体才有望落到10s附近；调价层需满足完整HTTP p95≤2s/max≤5s。**当前证据支持该方向，尚不能证明这些数值可达。** 若融合后新增 JS成本抵消 SQL节省，或紧凑重报价仍超限，应依据那一次完整profile重新决策，而不是继续重复叶子微调。

## 给恢复实施模型的交接

先做一个完整小对照：**事实未变、实际价目已变时，统计事实复用而所有费用/覆盖字段正确更新**。不要先做通用缓冲框架或跳到百万。

随后仓库融合及紧凑输入重放各自交付可审diff，以实测选择保留项。整个方案是一个依赖拆分方向，不是要求一次提交全部改造。最终仍需关闭19和20；生产启动、数据库写入与OS服务不在授权内。
