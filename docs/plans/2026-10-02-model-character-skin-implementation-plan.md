源文件名恒为 `.png`；公开 URL 的扩展名由 3.4 的编码决策决定。上面按已确认的 WebP 无损列出；若最终改用 LA-PNG，则改回 `.png`，且必须与 `skins:check` 强制的一致。

文件名第一段就是资源皮肤名；深色侧视必须为 `side-dark-lineart`，不是 `dark-side-lineart`。使用显式登记的已知前缀生成清单，不用模糊匹配或取目录第一张图。经典主题没有人物资源。

当前文件名核对为浅深各二十张、总计四十张；尺寸、RGBA、透明内容、实际视角与显示结果由 P0 逐套核对。不得把有 alpha 通道等同于人物内部透明。素材准备脚本不移动、不重命名、不修改源图；它按 3.4 的确定性无损变换生成公开副本，并以哈希验证「声明的变换(源) == 副本」，而不是「源字节 == 副本字节」。

### 3.2 注册表形状

以下为要实现的结构约定，不是已存在 API；函数名可局部调整，但信息边界和模式独立性必须保留：

```js
export const SKIN_PREFERENCE_KEY = "codexUsageSkinV1";
export const DEFAULT_SKIN_PREFERENCE = {
  version: 1,
  skinId: "classic",
  showCharacters: true,
  opacity: 0.5,
};

// 示例仅说明结构，十套按同一规则登记；不在此指定任何新色值。
const chatgpt = {
  id: "chatgpt",
  name: "ChatGPT",
  assetPrefix: "ChatGPT",
  variants: {
    light: {
      assets: {
        side: "/assets/skins/light/ChatGPT-side-lineart.webp",
        front: "/assets/skins/light/ChatGPT-lineart.webp",
      },
      palette: null,
    },
    dark: {
      assets: {
        side: "/assets/skins/dark/ChatGPT-side-dark-lineart.webp",
        front: "/assets/skins/dark/ChatGPT-dark-lineart.webp",
      },
      palette: null,
    },
  },
};
```

每个 variant 可另登记左右独立的缩放／锚点参数；不得把这些几何参数混进配色。必须导出纯函数覆盖：查找／校验皮肤、解析当前 variant、偏好归一化、枚举完整资源清单、解析当前模式 palette。返回值不要允许运行时修改全局注册表。

浅深分别保留 `palette: null`。后续用户颜色对象按下面的接口接入：

- `tokens`：现有语义 CSS 颜色变量的覆盖映射，例如页面、面板、文字、边框、陶瓷高光／阴影颜色、交互状态和图表文字等；键名白名单集中维护。
- `chartSeries`：可选的图表系列色数组；未指定时继续走既有 `CATEGORY_PALETTES`／颜色分配行为。
- `swatchKeys`：比较色块使用哪些 token 及其标签，值从 `tokens`／对应模式基底读取，不另维护展示色。

不接受通过配色字段覆盖字体、尺寸、间距或布局变量。没有指定的字段沿用对应模式的原有样式。`null` 与“用户已指定但只覆盖部分字段”的对象区分，卡片标注待定或沿用项；不为了填满卡片伪造色值。经典主题复用项目已有浅深基底，不建立新的色板。

### 3.3 偏好与首屏

现有 `codexUsageTheme` 和语言键保持不变。新键只保存 `{version, skinId, showCharacters, opacity}`；默认首次为经典，用户选角色后再记忆。

- version 不支持、JSON 损坏、未知 skinId → 安全归一化至经典默认，不沿用错误结构。
- showCharacters 必须为布尔值；opacity 必须为有限数且在 0—1 范围内。缺失／非法字段使用默认，0 必须是合法值，不能用 `value || 0.5`。
- 读取／写入异常时页面继续工作，当前会话仍可切换；正常本地存储恢复时保持当前明暗和语言偏好。
- 生成的 `skin-bootstrap.js` 从同一注册表派生有效 id、默认值、校验逻辑及已指定的模式颜色，不能再手写一套 id 或色板。读取既有主题恢复结果，绘制前设置 `data-skin`、人物显示／opacity 属性和必要颜色覆盖；DOM 模块启动后使用同一归一化契约校准。
- 同步普通脚本在 stylesheet 前执行；离线导出内联该脚本，不保留外部 src。默认经典不产生图片请求，恢复角色时正确图片在 decode 完成前保持隐藏。
- 颜色切换先清除**上一次由皮肤写入的白名单属性**，再写当前 variant 的覆盖；回到 null／经典时无残留。不要清掉根节点其他业务 style。

生成物需提交，使克隆后可直接启动。调整注册表、用户色值或源图后运行准备命令，并通过一致性检查拒绝陈旧生成物；不把每次启动服务都复制图片作为运行时依赖。

### 3.4 显示副本的编码决策（2026-10-02 用户确认）

用户已确认：**页面实际加载的公开副本只使用 WebP 无损，public 中不出现 PNG**。源图 `lineart assets/**` 永远是原始 PNG，只是"源"；WebP 是唯一发布格式，二者不是并存关系。

依据为全量实测对照，见 [P0 证据第 6 节](../validation/2026-10-02-model-character-skins/README.md) 与像素级证据图 `docs/validation/2026-10-02-model-character-skins/baseline/compression-look.png`：

- 40 张源图全部满足 **R == G == B（逐像素）**，即单色墨 + alpha。
- WebP 无损实测 40 张合计 **18.46 MB**，且 `maxAlphaDelta = 0`、`maxVisibleRgbDelta = 0`，即在**全部可见像素**上与源图零差异；差异仅存在于完全透明像素的 RGB，不参与渲染。
- 因此完整离线单文件约为 **28.5 MB（现有看板）+ 24.6 MB（40 张 base64）≈ 53 MB**，相对直接内嵌原始 PNG（约 71 MB）显著降低。
- 4× 最近邻放大与 ×20 增强差异图均无可展示差异。灰度+alpha 只是 WebP 编码前的中间表示，不产生独立的 PNG 产物。

**约束与语义变更（本节覆盖其他章节中「原样副本／PNG 副本／PNG MIME」的措辞）：**

1. **源图永不改动**：`lineart assets/light/`、`lineart assets/dark/` 保持原字节，不移动、不重命名、不覆盖、不压缩。
2. **只补 `image/webp` MIME**；不需要 `image/png`（页面不加载 PNG）。若将来改用 PNG 发布，才需要 `image/png`。
3. 公开副本是**声明的确定性无损变换结果**，不是字节复制。`skins:check` 校验的是「对源施加声明的变换后得到的期望哈希 == 副本哈希」；变换实现或参数一旦变化必须使校验失败，不得静默通过，也不得降级为「文件存在即通过」。
4. 这不违反「保留原图外观、不自动反色、不重着色」：变换无损且保持极性，深色仍来自用户 `dark/` 目录的原文件，**绝不通过反色生成**。
5. `skins.js` 中各 variant 的 `assets.side`／`assets.front` 扩展名必须与副本实际编码一致（本决策下为 `.webp`），并由 `skins:check` 强制，避免注册表与副本脱节。
6. **生成与校验的分工（用户 2026-10-02 已确认接受此分离）**：Node 没有内置图像编码器，而准备／校验脚本受「只用内置 fs/path、不新增生产依赖」约束，因此 40 个 WebP 副本由开发侧**一次性生成器**产出并提交（生成器可使用非生产依赖，不进入 `dependencies`）。`skins:prepare` 负责从注册表派生清单、bootstrap 与期望哈希并原子写入；`skins:check` 负责只读校验副本哈希、陈旧生成物、扩展名一致与 40 个 URL 齐全。二者都不得尝试现场编码图像，也不得因无法编码而静默跳过校验。
7. **已接受的限制**：由于第 6 条，「修改源图后运行准备命令即可更新副本」这条链路**不成立**。源图一旦变更，必须重新运行开发侧生成器 `docs/validation/2026-10-02-model-character-skins/generate-skin-webp.py`，再运行 `skins:check` 验证。`skins:check` 必须能检测出「副本与当前源不一致」并使校验失败，因此源图变更不会被静默忽略——只是需要人工触发重新生成。相关命令的帮助文本与文档必须写明这一分工，不能让使用者误以为准备命令能重新编码。
8. 缩尺寸方案（75%／50%／q90@50%）**未被采纳**，不得擅自启用；它们会真实改变线条观感（1:1 下 alpha 最大差可达 193）。
9. 体积编码只影响交付体积，不改变显示参数、图层与布局契约。

## 4. 前端实现契约

### 4.1 装饰层与加载

在 body 中、`.shell` 之外添加 `#skinCharacters`，包含左侧与右侧 `<img alt="">`；容器 `aria-hidden="true"`、`pointer-events: none`、fixed、视窗锚定、不进入正常流。

图层处于页面环境背景之上、现有看板和全部浮层之下。不要用可能掉到 body 背后的负 z-index。根据实际 stacking context 给装饰及既有内容确定稳定层级，检查不会覆盖日期菜单、tooltip、计价子 dialog 或来源／皮肤 modal。

只调整人物高度、左右锚点、overflow 裁切；保持 `.shell` 的原宽度，禁止预留 gutter、建立三列主体、重排工具栏或降低框体不透明度。手机可以隐藏人物，功能层仍走原断点。50% opacity 只设置在装饰容器；减少动态效果时关闭淡入淡出。

每次应用 skinId／theme 增加加载序号，捕获该次 variant 的精确 URL，预加载／decode 当前两图。应用前核对序号及当前选择仍一致；迟到的 load/error 不得覆盖新模式。缺失视图隐藏对应装饰，保持功能可用，不借另一模式或历史根目录图片填补。缓存键使用精确 URL，隐藏／经典状态无需加载整库。

### 4.2 同款入口

在 `#languageToggle` 前插入 `#skinToggle`，`class="theme-toggle skin-toggle"`，type button，内联衣服 SVG；不额外套新的按钮框体。复用公共按钮样式，不降低文/A 按钮尺寸来适配第三按钮。

提供 `aria-haspopup="dialog"`、`aria-controls="skinDialog"`、正确的 expanded 状态、中文／英文 title 和无障碍名称。使用前景色与相同线条视觉；hover、active、focus、disabled 等背景、边缘、阴影及按钮光泽与文/A 相同。按实际语言按钮计算样式对比，不只比设计值。

验收新增入口时同时检查标题、原两按钮的边界与排布。若窄屏第三按钮造成真实碰撞，不能自行缩标题、缩原按钮、改主框体、把入口挪走或宣称通过；记录准确视窗与测量证据，单独列出未满足的约束，先完成不受影响部分。这是验收失败的处理规则，不是允许改变用户布局要求。

**用户裁定（2026-10-02）：390px 下接受换行。** 第三个按钮使 `.topbar-actions` 由 128px 增至 196px，与 188px 标题在 370px 容器内无法同排，`.topbar` 因此换行——标题占第一行，三个按钮整体占第二行（同一行内保持 皮肤 → 文/A → 主题 顺序，尺寸仍为 60×38，无横向溢出）。此为**用户确认接受的窄屏布局**，故 4.2 的碰撞判定在 390px 改为：标题与按钮组不得在**两个轴向上**同时重叠（而非要求同排）。≥768px 仍必须与标题同排且零位移。

### 4.3 独立弹窗与状态

与 `#importDialog`／`#pricingDialog` 同级添加 `#skinDialog.dialog-backdrop[hidden]`，内部 `.dialog.skin-dialog`，role dialog、aria-modal、标题关联。放在 body 同级，不嵌进来源／计价窗口，复用原遮罩、材质、字体、圆角和柔和弹窗投影。只有自身宽度／内部矩阵可以不同。

稳定元素：`#skinDialogTitle`、`#skinGrid`、`#skinCharactersToggle`、`#skinOpacity`、百分比输出、底部“简洁模式”及“关闭”按钮。删除恢复 50% 按钮、标题栏 × 和解释段落。范围输入 0—100，内部转换到 0—1；默认 50% 不变，已有偏好保留。图标横杠与滑杆主题色、共享凹槽及按钮样式以最新视觉修改计划 R1—R8 为准。

打开时记录 opener、渲染当前选择、聚焦当前皮肤或首个可操作项。关闭按钮、遮罩空白点击、Escape 走同一关闭函数，恢复入口焦点与已有滚动状态。点击内容不能误关。

将皮肤窗口加入现有 `trapDialogFocus()` 的顶层窗口选择与 Escape 分发，只处理当前实际活动窗口；保持原生 `#modelPricingDialog` 的顶层优先行为。背景业务控件在 modal 活动期间不可被键盘操作；必要的临时 inert／aria 属性在关闭时完整恢复，不破坏另外两个弹窗。

卡片采用可键盘到达的选择按钮或单选语义，当前项用清楚标记及 aria 状态表达。选择即应用、弹窗保持打开用于比较；关闭再开保留选择。角色开关与 opacity 不修改统计或计价状态。

### 4.4 同屏浅深比较

十套角色采用统一卡片，放入一个连续的大凹槽；每卡包含名称、浅色预览、深色预览、两组色块、选择状态。左右预览常驻，不跟主页面模式一起只保留一套。缩略图人物向右构图，优先露出脸部与躯干，参数独立于页面两侧立绘。

**简洁模式规则**：Classic 卡片及其无图预览从可见矩阵移除，保留注册表内 `classic`。底部“简洁模式”按钮负责进入并表达状态，文字及无障碍信息覆盖中英；调用已有回到经典的逻辑，保持没有人物图片请求的行为。旧“Classic 首卡”审计规则已被本轮要求替代。

≥1024px 桌面固定五列两行的十卡矩阵，1440×900／1280×800／1024×768 下名称与两组预览／色块、控制行及操作按钮同屏可见。节省空间时先简化示意细节，保留人物辨识度，不改页面后方看板。小屏可降列并允许弹窗内容区纵向滚动，仍保留每卡浅深同时展示及简洁模式按钮可访问；具体断点与验收以视觉修改计划 R3 为准。

每个 preview 具有局部 `data-preview-theme="light"`／`"dark"`，从对应 variant 获取自己的图与 palette。所有皮肤用同一个微型模板：相同标题、文字、面板、按钮与图表示例，角色参考透明度统一 50%。主页面上用户调整人物透明度不改变比较模板。

关键点：根节点为 dark 时，浅色 preview 不能继承根的深色变量或另一皮肤的覆盖。为现有**变量声明块**添加限定的 preview 作用域别名，保留原全局 selector、声明顺序和色值，仅使同一浅／深基底也能落在对应局部容器；再在该容器应用自身 palette。不要复制一组易过期的手写基底，也不要为了预览重写全局组件样式。使用 `.skin-preview-*` 的局部组件 class，避免与真实主题按钮和框体选择器互相影响。

配色为 null 时可以呈现既有对应模式基底与用户原图，但显式标注“配色待定”，不能称为该角色正式配色。只有用户实际指定的 token 进入该组色块，继承项清楚标为沿用。色块和微型界面共用解析器；打开弹窗不轮流切换页面主题来截取颜色。

### 4.5 与现有 app 联接

`bootDashboard()` 创建皮肤 UI，读取并归一化偏好；不得给不存在的元素无保护绑定，避免导出或纯函数测试导入时抛错。新增 UI 模块不要 import app.js 或在 Node 导入时自动启动。

`setTheme()` 在现有根 theme 属性与偏好更新之后、既有 render 前同步应用该模式的 skin 配置。切换皮肤只改变皮肤状态、装饰及已指定的颜色，并使用现有重绘入口；不重新拉取用量、不重建页面表单或执行 pricing 保存。

`setLanguage()` 更新皮肤弹窗动态文案、名称标签及衣服按钮无障碍名称，保留 raw assetPrefix。必要的图表系列色挂钩在配置非空时取新数组；null 时严格返回原有颜色分配。全页真实配色尚待用户指定，不趁本轮重做图表或硬编码组件色。

## 5. 静态资源与导出契约

准备脚本只处理注册表期望的四十个源文件，按 3.4 的无损变换生成公开副本与启动脚本，输出可重跑清单、源哈希与「声明变换后的期望哈希」。不删除未登记文件，也不把 `.archify`、`.zcode`、本机浏览器配置或根临时截图复制进 public。在 package.json 添加 `skins:prepare` 与只读 `skins:check`；生产 serve/export 不需要 node_modules 或先运行生成命令，仓库 public 中须带齐有效生成物。

`src/server.js` 只补 `image/webp` MIME 和相应路由回归，沿用既有 `serveStatic()`，不新增图片 API；40 个资源 URL 仍经它返回。现有目录边界检查保持。40 个公开 URL 均应 200、`image/webp` MIME 且字节与「源经声明变换后的结果」一致（期望哈希由准备脚本记录并由 3.4 语义校验），未知图为 404。不要把 `lineart assets/` 作为任意磁盘文件接口直接开放。

导出必须在同一批完成以下工作：

1. 按现有方式内联 `skins.js`、`skin-ui.js` 的命名依赖和 IIFE 边界，消除未解决 import／export 和全局名字冲突。
2. 将 `skins.css` 的 link 转为内联样式；将生成的普通启动脚本 src 转为内联脚本，放置位置与在线一致。
3. 枚举全十套、两种模式、两视角的 40 个 URL，读取 **public 副本** 转 data URL。运行时注册表、人物 src、比较缩略图和所有可能的 CSS 资源引用共用同一内嵌映射，不仅替换当前显示的两图。
4. 序列化脚本数据保持既有 `safeScriptJson()` 的转义要求；不要用不加边界的全局字符串替换误改资源名或业务数据。
5. 自包含断言覆盖新增模块、样式、bootstrap，以及皮肤资源映射。不得残留 `/assets/skins/`、源文件盘符、相邻目录 fetch、动态 import 或远程缩略图依赖。data URL 本身不得被当外部资源拒绝。
6. 从 `file://` 禁网运行，切换全部十套 × 浅深、开关角色与调整 opacity，显示卡片比较。每种资源要被实际取用并验证解码，不只数 HTML 中 data URL 字符串次数。
7. 记录相对基底的体积增加、40 个引用数与去重后的实际内嵌数；仅在内容完全相同且所有映射仍正确时按哈希去重。

既有“无 node_modules 独立导出”测试只复制 `src/`、`public/`：保持这一能力，不能让导出器依赖原 `lineart assets/`、scripts、开发包或本机路径。整包完整性检查负责保证 public 副本随交付存在。既有路径含空格、业务嵌入及三路一致测试不得削弱。
