## 0 结论摘要

| 问题 | 诊断 | 建议 | 优先级 |
|---|---|---|---|
| 价目不全 | 发现只查 OpenAI；带 `/` 的线路名被拒；缺价用最低费率生成金额 | 先暴露未知份额与普通模型手动纠正；明确线路手动价独立交付；自动发现逐提供商扩展 | 第一、二、四批 |
| 汇率机制 | 无独立周期调度；价格更新时间不代表所有来源成功；汇率有独立状态与兜底 | 先展示部分失败、汇率来源及过期；后台调度单独交付 | 第一、三批 |
| 代理嵌套 | 同名可能对应不同卖家、币种、峰谷和订阅规则；事件缺独立线路身份 | 独立线路价，只支持身份有依据的事件；未知身份不猜卖家；账本核验可选 | 第二批及可选后续 |
| 手动填价 | 缺价行不能编辑，重新匹配实际是全局强制刷新 | 复用编辑器与字段覆盖；自动缓存继续更新，手动字段优先，撤销恢复最新自动值 | 第一、二批 |

当前价目主要按模型名定位，实际选择还受卖家线路和适用场景影响。本版优先使金额依据清楚、未知部分可见，不以消除全部缺价为承诺。

### 0.1 统一的费用与历史口径

费用继续表示 **API 等价估算**，说明采用官方模型价、明确线路价、手动价还是最低费率假设，不声称是服务商账单、订阅扣费或结算金额。网关账本是相同线路与规则下的观测证据，不直接作为供应商实付真值。

历史采用 **C：按当前有效价目回算**，保留原始 tokens 和来源事实，明确价格变更可改变历史估算。订阅的 API 等价值标明订阅及采用的价目；没有可用价目时保持未知，不能因网关 `cost=0` 就认定免费，也不能与实际支出混成无说明的合计。

本计划不启动任何实现；后续批次与范围由用户的确切要求确定。

## 2 当前链路

```
转录/索引事件（model 名）
  → resolvePricingModel：精确 → 显式别名 → -free → Claude 守卫 → 最长前缀
  → 价目条目：currency、short/long/fast、peakWindows、offPeakMultiplier
  → estimateEventCost：峰谷、档位、缓存场景、最低费率兜底
  → byCurrency.USD / byCurrency.CNY 分开累计
  → 展示时按 USD/CNY 汇率折算
```

价目来源是三层覆盖：

```
内置目录（103 个）
  → 自动补丁：models.dev / LiteLLM / MiMo / StepFun / Kimi / GLM
  → 手动字段覆盖：~/.codex-usage/pricing.json
```

自动补丁和自动发现是**两条不同的路径**：

- **补丁**（`modelsDevPricePatches`）遍历已有目录模型，按 `pricingSourceProviderFor` 找到提供商，再按提供商下的精确模型键取价。它已经认识 11 个提供商：anthropic、alibaba、google、glm、openai、xai、kimi、mimo、minimax、meta、stepfun。
- **发现**（`parseOpenAIModelPricing`）只处理**缺价的新名字**，只查 models.dev 的 `openai.models[名字]` 和 LiteLLM 的 `[名字]` / `openai/名字`。名字必须匹配 `^[a-z0-9][a-z0-9._-]{0,79}$`，带 `/` 的名字直接返回 `unsupported-provider`。

这个不对称是问题一的根。

## 3 问题一：价目不全

### 3.1 实测

在用 28 个模型里 8 个缺价（2026-10-22 的 `usageCoverage`）：

| 模型 | harness | 线上发现结果 | 直接原因 |
|---|---|---|---|
| `opencode-go/deepseek-v4.1-flash` | Codex、DSH | rejected / unsupported-provider | 名字含 `/` |
| `opencode-go/gemini-4-argon-contributor` | Codex | rejected / unsupported-provider | 名字含 `/` |
| `opencode-go/muse-spark-1.3-contributor` | Codex | rejected / unsupported-provider | 名字含 `/` |
| `opendesign/deepseek-v4.1-flash` | Codex | rejected / unsupported-provider | 名字含 `/` |
| `stepfun-cn/step-5-preview` | Codex | rejected / unsupported-provider | 名字含 `/` |
| `workbuddy-ai/deepseek-v4.1-flash` | Codex、DSH | rejected / unsupported-provider | 名字含 `/` |
| `workbuddy-ai/deepseek-v4.1-flash-sg` | Codex | deferred / retry-after | 冷却中；解析器直接调用仍是 unsupported-provider |
| `sensenova-6.8-flash-lite` | ZCode | deferred / not-found | 只查 `openai`，没查 `sensenova` |

7 个带 `/` 的名字里，6 个已经落成终态 `unsupported-provider`，第 7 个（`-sg`）只是因为冷却期没到而显示 `retry-after`，冷却结束后会得到同样的终态。用当日的 models.dev 与 LiteLLM 快照直接调用解析器，8/8 与线上一致。

### 3.2 发现路径的四个缺口

1. **提供商不对称。** models.dev 本来就有 `deepseek`、`moonshotai`、`zhipuai`、`stepfun`、`sensenova`、`opencode-go`、`meta`、`alibaba` 等条目，补丁路径已能按目录中确认的提供商定位；发现路径却只看 `openai`。实测：`opencode-go` 提供商下 33 个模型，三条缺价线路的名字逐字存在，价格也完全对得上；`sensenova` 下也有 `sensenova-6.8-flash-lite`。它们从没被查过。
2. **前缀被当成非法字符。** LiteLLM 的 4,245 个键里 3,579 个带 `/`，发现路径全部忽略。反过来把任意前缀当官方价也不行：`azure/`、`github_copilot/`、`aihubmix/` 都是转售价。
3. **官方页面只能补丁，不能发现。** StepFun、MiMo、Kimi、GLM 的解析器只更新目录里已有的模型，不能新增。目录外的模型即使官方页面有价，也进不来。
4. **零费率缺少证据分类。** models.dev 的 `sensenova/sensenova-6.8-flash-lite` 是 `0/0/0`。这可能是免费档，也可能是未配置；账本对它的 8 条记录是 `priced=false`，没有可用网关价格证据。当前它先被提供商发现范围挡住，并未作为免费模型入库；扩展发现时必须先区分明确免费与未配置，不能仅以数值非负判有效。

### 3.3 最低费率兜底的真实影响

缺价模型不会留空，而是按**同币种全表逐项最低费率**估算（`minimumRatesFor` → `minimumRateSets`）。当前生效的最低向量是：

| 币种 | input | cachedInput | cacheWrite | output |
|---|---|---|---|---|
| USD | 0.03（qwen3.7-flash） | 0.002（muse-spark-1.2-contributor） | 0（deepseek-v4-flash-0731） | 0.13（qwen3.7-flash） |
| CNY | 0.1（glm-4-flashx-250414） | 0（glm-4-airx） | 0（deepseek-flash） | 0.1（glm-4-flashx-250414） |

这个向量按类别独立取最低值，不对应任何真实模型，也不保证是未知线路费用的下限。全历史 14.7% 的 tokens 走这套费率，而 `unpricedTokens` 是 0——这些没有可靠价目依据的流量仍有金额。`minimumRateModels` 当时列出 9 个名字：7 条带 `/` 的线路、`sensenova-6.8-flash-lite`、`Unknown model`。

用账本样本对比（同样的行、同样的 token 语义：`input = in + cache_read`、`cached = cache_read`、`detailMask` 完整）：

| 线路 | 定价行数 | 账本 USD | 看板估算 USD | 比例 |
|---|---|---|---|---|
| `opendesign/deepseek-v4.1-flash` | 9,344 | 16.858158 | 5.434487 | 0.322× |
| `opencode-go/deepseek-v4.1-flash` | 2,001 | 4.841420 | 1.414050 | 0.292× |
| `opencode-go/gemini-4-argon-contributor` | 118 | 11.305539 | 0.095851 | **0.0085×** |
| `opencode-go/muse-spark-1.3-contributor` | 2 | 0.030842 | 0.009719 | 0.315× |
| `stepfun-cn/step-5-preview` | 186 | 4.547475 | 0.111602 | **0.0245×** |

这些样本的估算约为账本金额的 1/3 至 1/118，说明最低费率假设与网关记录明显不同；该倍率不代表供应商实付金额已经独立核验。

### 3.4 建议

1. **先暴露依据。** 按当前查询范围显示最低费率假设的模型数、tokens 和占比，并另列真正未定价部分。时间范围、来源排除与冻结快照一致；不能用近期模型覆盖率解释全历史费用。`minimumEstimatedTokens` 是已计价 tokens 的子集，不能再与其相加；其他可重叠诊断也不直接求和。分母为零时显示无适用数据。
2. **分步调整兜底。** 第一批保留当前金额算法，但合计明确标为含最低费率假设，不称为可靠费用或实际下限。第二批缺少可用费率的部分保留 `unpriced`，不再默认补最低价，合计标为「已定价部分合计」。若保留旧算法，只作独立参考，不混入该合计。
3. **复用通用部分。** 已有目录沿用确认的提供商映射；新模型只接受明确身份或显式映射。拆分 `<provider>/<model>` 只能生成候选，不能认定官方提供商、跨卖家取同名价或回填裸名。
4. **保留厂商校验。** 新模型解析器还有 OpenAI 的上下文政策校验和缺省两倍 Fast 价，不能直接推广。缺少长档、Fast、缓存写入或 TTL 证据时，不自动复制、乘倍数或填零；无法完整表达所需场景的候选不发布为有效新价目。
5. **区分零与未知。** 全零且无免费政策证据的来源标 `zero-rates`；某个字段经可靠来源明确为零仍可接受，不一律拒绝零缓存费率。已有明确免费政策保持原优先级。
6. **终态可重新评估。** 当前能力不支持的身份不因冷却到期反复全量刷新；解析能力、提供商映射或用户绑定变化后允许再查。网络错误按冷却重试，`not-found` 在目录更新后可再发现。只在实际安排重试时显示下次时间。
7. **逐来源扩展。** LiteLLM 只补充已确认的同一提供商和计价面；官方页面新增模型逐来源交付，不作为手动填价、全部线路支持或首批上线的前置条件。

## 4 问题二：汇率刷新机制

### 4.1 完整机制

| 项目 | 现状 |
|---|---|
| 来源 | `https://api.frankfurter.dev/v2/rate/usd/cny`，重发布 ECB 参考汇率 |
| 超时 | 10 秒（`RATE_FETCH_TIMEOUT_MS`） |
| 校验 | `base=USD`、`quote=CNY`、`1 ≤ rate ≤ 20`、日期为合法 `YYYY-MM-DD` |
| 失败处理 | 保留上一次汇率，不更新 `exchangeRateUpdatedAt`，记一条 `exchangeRate` issue |
| 成功门 | 上次成功满 **24 小时** |
| 失败门 | 上次失败或部分失败满 **1 小时** |
| 触发 | 浏览器启动；页面打开且计价弹窗关闭时的小时轮询；手动「刷新价目」；任意「重新匹配」（force）；索引同步后的缺价发现 |
| 手动覆盖 | `pricing.json` 的 `usdToCnyRate` 优先，UI 有「恢复自动汇率」 |
| 作用范围 | **仅展示换算**：USD 和 CNY 原生金额分开存，不重写价目条目，也不改变逐事件成本 |
| 兜底 | 硬编码 `DEFAULT_USD_TO_CNY_RATE = 6.72` |

`due()` 的语义是：没有尝试记录 → 立即到期；有成功记录且成功时间不早于尝试时间 → 24 小时；否则 → 1 小时。

### 4.2 实际刷新节奏不是「每天一次」

**服务端没有独立的周期定时器。** `src/server.js` 里唯一的定时器是缺价发现的一次性 1 秒 debounce（`scheduleUsageDiscovery`，回调后重新检查；仍在冷却时清除定时器）；`src/cli.js` 只有启动等待用的 `setTimeout`；`pricing-store.js` 和 `pricing-auto.js` 里没有任何 `setInterval`。因此：

- 页面关着且没有缺价发现等其他触发 → 不主动刷新；24 小时是到期门槛，不是独立的每日更新保证。
- 计价弹窗打开期间，小时轮询会因为 `state.pricingCatalog` 非空直接返回（`refreshPricingAutomatically` 第一行）；手动按钮和「重新匹配」仍可强制刷新。弹窗关闭时该字段被清空，轮询恢复。
- 缺价发现会绕过 24 小时门：只要有缺价模型，`discoveryDue.length > 0` 就把 `updatePrices` 置真，六个价格源**整份重拉**，而不是只查相关提供商。
- 发现解析器拒绝 `unsupported-provider`，但服务端只按 1 小时判断冷却；后续索引检查满足门槛时仍会触发全量刷新。这不表示已有独立的每小时重试定时器。
- `pricePartialFailure` 为真时，后续触发按 1 小时门槛重试。调查时 MiMo 和 StepFun 持续失败，状态会维持到来源或适配器恢复，不能据此断言永久失败。

实测：`priceUpdatedAt` 停在 2026-10-21T00:25Z，`priceAttemptedAt` 已经是同日 18:13Z，一天内多次尝试都没有推进成功时间。该轮 6 个价格源只成功 5 个（LiteLLM 抓取失败），另有 MiMo、StepFun 两个解析失败，`priceUpdateSummary.fetchedSourceCount` 记 5。代码里还有一条旁路：只要本轮有价格变更（`pricesUpdated`），即使存在价格 issue 也会把 `priceUpdatedAt` 推到当前时间。所以「最后成功时间」既不代表「全部源都成功」，也不保证「没有 issue」。

### 4.3 缺口

1. **没有服务端定时器。** 不打开看板，汇率和价目就冻结。
2. **没有过期告警。** `exchangeRateDate` 已经在 UI 显示（「报价日期」），但没有和今天比较；ECB 周末和节假日返回上一工作日，界面无法区分「今天的价」和「上周五的价」。
3. **兜底汇率没有标识。** 6.72 是硬编码；首次运行或长期抓取失败时会静默使用，只有 `exchangeRateDate` 为空时显示「内置」。
4. **参考汇率不是结算汇率。** ECB 参考汇率与银行卡/账单的实际结算价有差；文档没有写这一点。
5. **部分失败缺少直接状态。** `pricePartialFailure` 已持久化，但未由 `getAutomaticPricingStatus()` 直接返回。前端仍可读取 `issues` 的分类与来源，不能仅凭 `priceUpdatedAt` 判断所有来源成功。汇率报价日期、独立更新时间和错误列表仍有信息价值，并非所有刷新信号都不可信。

### 4.4 建议

**第一批先修状态与说明，不依赖后台定时器。**

- 直接返回价格侧部分失败状态及本轮来源结果，区分抓取成功、解析成功和适用价格通过校验。`priceUpdatedAt` 不再单独标成所有来源更新成功；不同模型的核验日期不能由一个全局时间代替。
- 分别显示价格与汇率的尝试时间、有效更新时间、来源和错误。只变状态元数据不能冒充有效费率变化。
- 区分自动、手动与内置汇率，注明「参考汇率，非结算汇率」；首次联网失败也要看出在使用兜底值。
- 由报价日期和当前时间派生年龄，不持久化会自行过时的年龄。先以超过 5 个自然日提示过期，避免新增工作日历；失败保留旧值并说明，不把下载日当报价日。
- 自动汇率继续缓存最新有效值；撤销手动后恢复最新自动值或明确标注的兜底值。不做多源平均，本批不增加备用源。

**第三批独立补服务端调度。**

- 启动和运行期间检查到期，保留成功 24h / 失败 1h 门槛。基础检查周期采用 1h，或按下一到期时间安排；不能用 6h/24h 调度却声称按 1h 门槛及时重试。
- 复用 `requestPricingRefresh` 的并发合并，浏览器和服务端不重复抓取。定时器 `unref`，关闭服务清理，不使 CLI 常驻。
- 只刷新到期或发现所需来源；整份上游目录可一次下载复用。缺价发现不顺带强制拉取所有源和汇率，正常估算读取不等待联网。
- 网络失败保留旧值并记录问题；终态筛选与可恢复重试遵守 §3.4。

原生 USD/CNY 继续分别累计，只在展示时换算。网关 USD 等值不证明卖家原生币种，不得据此反推 CNY 价后再用当前汇率二次折算。

## 5 问题三：代理嵌套与线路价

### 5.1 账本反解方法

Magpie 账本每条请求有 `req`（线路）、`model`（网关配置模型）、`served`（网关报告的上游模型）、`in` / `out` / `cache_read` / `cache_write`、`cost`、`priced`、`access`。对同一线路的样本解

```
cost = (in × a + cache_read × b + out × c) / 1,000,000
```

的最小二乘，在样本可识别且同批规则稳定时可推断网关费率。`priced=true`、`cost>0` 和 token 总量为正只是样本门槛，不保证唯一求解。安全核验步骤见 §10；`served` 不视为实际模型身份已独立验证。

反解得到的是**网关的 USD 等值费率**，不是供应商账单，也不一定是卖家的原生币种。这一点很重要：账本无法区分「卖家收 USD」和「卖家收 CNY、网关按汇率折算」。

两个字段的坑要先记住：`req` 可能缺失（本机 ZCode 的 2,224 行全部没有 `req`，只能按 `model` 组织待核对样本，不能据此认定卖家）；`agent` 是账本自己的口径（`codex`、`dsh`、`opencode`、`zcode`、`claude-desktop`、`claude`），和看板的 harness 名不是一一对应，映射要显式列出，不能猜。

### 5.3 峰谷证据

`opendesign` 的 9,344 条定价行按 DeepSeek 官方高峰时段（北京时间周一至周五 9:00–12:00、14:00–18:00）切分：高峰 1,354 行 $2.506001，空闲 7,990 行 $14.352158。**两侧都用同一组平价费率精确成立**（最大相对误差 4.2e-16），合计 $16.858158 与账本完全一致。也就是说这批样本中网关对线路使用固定费率，没有按官方峰谷切换；数值与官方空闲价折算重合。裸名 `deepseek-flash` 线路同样两侧精确成立（221 + 680 行）。

这说明仅凭 served 模型不能证明该线路采用官方计费规则：将本地 `deepseek-flash` 的官方 CNY 峰谷价用于这批请求，结果是账本的 1.148×（`opendesign`）至 1.361×（裸名线路），高峰时段单条约为 2 倍。若产品选择官方模型价场景，应如实标注；不能将其冒充已经核验的线路价或实付金额。

### 5.4 五种失败模式

1. **同名不同价。** `opencode-go/deepseek-v4.1-flash` 是 0.15 / 0.003 / 0.6，裸名 `deepseek-v4.1-flash` 是 0.3 / 0.03 / 1.2；前缀剥离会高估 2.41×。
2. **同名不同币种与峰谷。** `opendesign` 的上游是 `deepseek-flash`，但网关按固定 USD 等值记录，卖家原生币种未确认；本地 `deepseek-flash` 是官方 CNY 峰谷价。按 served 定价，高峰时段高估 2 倍，也不能由账本 USD 等值直接确认卖家的原生币种。
3. **同名改价。** StepFun 官方页面写明「价格自北京时间 2026 年 10 月 14 日 00:30 起由 0.35 元／百万 tokens 调整为 0.70 元／百万 tokens」（缓存命中）。名字没变，本地价目还是 0.35；StepFun 适配器当前又报「Invalid StepFun pricing page」，所以变更从未进入价目。账本反解 0.10461 USD ≈ 0.70 CNY，能精确抓到这次变化。
4. **同名但无价。** `sensenova` 在 models.dev 是 0 / 0 / 0，账本 `priced=false`；`workbuddy-ai` 是订阅，账本 `cost=0`；裸名 `deepseek-v4.1-flash`（约 19,600 行）和 `muse-spark-1.3-contributor`（413 行）来自 DSH，同样是 `priced=false`。这些状态均不足以确认「免费」，需分别保留未配置、订阅或价格证据不足的原因。
5. **近似名不能确定同价。** 若给 `workbuddy-ai/deepseek-v4.1-flash-sg` 剥离前缀并借裸名价，本地缓存读 0.03 USD 与官方候选 0.04 CNY ≈ 0.006 USD 相差约 5 倍，高缓存命中率会放大候选选择的影响。这是候选价差异，不是已核验的实付高估倍率。当前线路发现仍被拒，账本对 `-sg` 是 `priced=false`，无同价证据。

### 5.5 同名在公开源上本来就没有唯一价

models.dev 当日快照里，`deepseek-v4.1-flash` 这个名字出现在 **25 个提供商**下：3 个是 0 价（`alibaba-token-plan`、`alibaba-token-plan-cn`、`sensenova`），22 个非零，input 从 $0.04（engy）到 $0.672（scaleway），**相差 16.8 倍**。`step-5-preview` 出现在 6 个提供商下：`stepfun` 1.04613、`aihubmix` 1.08、`stepfun-ai` 1、`requesty` 1、`opencode-go` 1、`empiriolabs` 1。

结论：**模型名不能单独证明卖家线路价。** 要声称采用某条线路的报价，须有可确认的卖家线路身份；选择官方模型价作为 API 等价场景仍可行，但要明确其来源和假设，不能因同名就认为与网关账本同价。

### 5.6 可选的离线核验协议

账本适配器不是正常估算依赖。优先将来源明确的候选费率逐行代入，必要时才反解未知系数；结果用于差异检测，不自动替换有效价目。用户选择从结果预填后，仍需按手动表单确认保存。

1. **定义比较对象。** 按明确线路、适用时段、币种、缓存语义和规则分组；疑似改价或跨档样本先分段，不用一套向量吸收所有差异。
2. **验证请求连接。** 使用来源已确认的响应 ID，核对 home/来源归属与输入包含关系，再逐项核对输入、输出、缓存读写。字段缺失或连接覆盖不足时记录未知，不将 ID 相似当全量关联。
3. **先核对候选。** 记录逐行残差、覆盖字段和档位。全零成本不能反解正费率；小金额同时使用绝对与相对容差，避免除零和舍入放大。
4. **反解需可识别。** 原调查的 ≥20 行、跨 ≥2 日和最大相对误差 <0.1% 只是样本参考门槛，不能替代满秩、条件稳定、费率非负与有限性检查。峰谷两侧覆盖也不能证明所有时段和档位同价。
5. **按字段和场景记录证据。** 保存来源、样本范围、ID 连接覆盖、匹配数、残差、核验日和比较币种。无写入样本时写入价未知，未覆盖长档/Fast 时这些档位未知；不能填零或复制短档补成完整有效价。
6. **明确证据边界。** 极小残差只证明重现了该批网关计价函数，不等于实际账单验证。记录公开目录与网关可能的同源关系，不默认两者独立；USD 等值不能证明卖家原生币种。
7. **差异只触发复核。** 不一致时保留两边证据并标 `disputed`，不因反解覆盖自动价或手动字段。「变化 >1%」只保留为将来差异检测的初始参考，不是自动发布门槛，也不要求每次普通刷新重跑账本。

**绑定的实测覆盖率（2026-10-22）。** 本机 30 天内 `agent=claude-desktop` 的账本约 2,100 行，`~/.claude/projects` 下 24 个转录文件、26,729 条记录、9,514 条 assistant、4,219 个唯一 `message.id`。两边能按 `message.id` 连上的只有 **34 行**，但这 34 行的四项 token 计数**全部逐项相等**（34/34，0 分歧）。其余行来自 Claude Desktop 自己的会话存储，不在该目录。`agent=claude` 在该窗口内是 **0 行**，没有可用于核验 Claude Code `mythos-magpie-*` 线路的对应记录；仅凭该筛选结果不能断言所有此类请求都不经过网关。

这 34 行的请求名全部是 `claude-haiku-5-5`，而线上模型是 `deepseek-flash`（8 行）和 `deepseek-v4.1-flash`（26 行）——正是问题三要解决的层次：harness 别名、线路、配置模型、served 模型可以四个都不一样。其中 8 行有价格：账本 $0.012753；按线上模型（本地 CNY 峰谷价）估算 ¥0.085019，折 $0.012740，比例 0.999；按请求名（`claude-haiku-5-5` 不在价目里，走最低费率兜底）估算 $0.002932，比例 0.230。**线上模型对得上，请求名对不上。**

但这个 0.999 有一个必须说清的巧合：8 行全部发生在北京时间 23:00 前后，即 DeepSeek 的空闲时段，本地价目因此套了 0.5 倍空闲折扣（2 / 0.04 / 8 CNY → 1 / 0.02 / 4 CNY ≈ 0.15 / 0.003 / 0.6 USD），恰好等于这批账本记录使用的固定费率。如果这些请求落在高峰时段，线上模型估算会高估 2 倍。所以这 8 行**不能**证明「served 模型就是定价依据」，只能证明「这批流量的账本固定费率与官方空闲价折算重合」。这正是 §5.3 峰谷证据的同一件事。

因此线路验证只能覆盖账本确实记录的那些 agent，不能宣称全量。绑定覆盖率必须和价格一起显示。

### 5.7 线路身份与数据边界

第一版只支持原始记录已有明确线路前缀，或来源确实提供可靠线路证据的事件。裸名不能通过当前配置、同名模型、会话级 provider 或后缀猜卖家；相同前缀有歧义也不能静默合并。保留原始请求名、网关报告模型和 canonical 归属，不因展示改名丢证据。

费用事件当前缺独立线路身份，见 [usage-types.js](../../src/usage-types.js)。perf 的 source/model/effort/provider 是测速分组身份，provider 不自动等于收费卖家。共用请求证据与可确认的规范化字段，各自保留合适的统计分组，不强制共用整个测速键。

[usage-core.js](../../src/usage-core.js) 的 project-log `requestLinked` 只是判断是否带请求 ID、用于上下文判断，不是已持久化的对账关系。后续优先检查并复用 [request timing 存储](../../src/perf-request-timing-store.js) 的 home/response/thread 证据和 [Codex 请求关联](../../src/perf-sources/codex-request-timing.js)，验证费用事件粒度与归属；不能把 turn 累计费用当单请求事实，也不另建靠时间或模型名猜连接的机制。

线路进入计价时，来源解析、索引费用投影、可恢复事实、共用计价入口和缓存键必须保留所需身份；有效线路费率与绑定变化参与有效价目版本。只有 canonical 的绑定只确认模型归属，借用模型价必须是显式的模型价假设，不能冒充该线路报价。

### 5.8 有效目录、手动文件与覆盖规则

有效目录新增 `routes`，与 `models` 分开。手动文件实际使用 schema 2 的 `modelOverrides`；本版规划 schema 3 保留已有字段覆盖格式，新增 `routeOverrides`。自动缓存分别保存最新有效自动线路价及来源元数据，不能把有效目录整份写回手动文件。

以下仅是手动文件的结构示例：**假设用户明确确认四项标准费率、缓存写入为零及标准长短档同价**。它不是原账本已证明的完整价目，也不是可直接提交的全量 API 载荷。

```json
{
  "schemaVersion": 3,
  "modelOverrides": {},
  "routeOverrides": {
    "opencode-go/deepseek-v4.1-flash": {
      "canonical": "deepseek-v4.1-flash",
      "currency": "USD",
      "short": { "input": 0.15, "cachedInput": 0.003, "cacheWrite": 0, "output": 0.6 },
      "long": { "input": 0.15, "cachedInput": 0.003, "cacheWrite": 0, "output": 0.6 }
    }
  }
}
```

- **名称与容量。** 规范化线路键允许 `/`、长度 1–160，拒绝空段、大小写归一化冲突和危险对象键。线路单独限额512，不占模型的256，不自动截断。原请求体上限128 KiB；2026-10-24实施实测256模型+512普通线路规范化载荷175,518字节，主审据此决定仅价目PUT提高到256 KiB，仍须验超限明确失败且旧数据不变。
- **先范围，再覆盖。** 已有明确免费政策保持原优先级；其余优先选择身份精确且适用的线路价，没有时才考虑有依据的模型价或显式模型价假设。普通模型手动价不自动覆盖更具体的线路，未知线路不剥前缀借价。
- **同一对象内手动字段优先。** 有效线路价是最新有效自动价叠加 `routeOverrides`；模型沿用原覆盖规则。`verified` 是证据状态，不是可越过手动字段的额外价格层。
- **自动缓存继续更新。** 自动价分叉仍保存最新通过校验的自动值；手动覆盖字段不改变生效值，未覆盖字段可自动维护并显示混合来源。差异可见，逐字段撤销后恢复最新有效自动值，不冻结自动缓存。
- **冲突与手动差异分开。** 同线路自动来源冲突时保留上一份有效自动值，无旧值则未知；用户手动值不同是显式选择，提示差异而不屏蔽手动值。
- **未知不补全。** 新候选缺必需字段或档位政策就不进入有效目录。默认复制 long、Fast 两倍或继承官方峰谷都不能替代线路证据；场景不支持时保持未知，或按用户明确选择的标准场景单独标注估算。
- **来源类型不冒充 URL。** `source` 仍接受合法 HTTP(S) 来源 URL；manual/ledger 等类型另存元数据。订阅显示 API 等价值及采用的价目，无价保持未知，不因网关零支出判免费。
- **迁移与保存。** 兼容 schema 2、旧全量配置、自动缓存与无线路配置；保留原子写入、并发版本校验、取消及失败回滚。价目 schema 不等于索引 schema，不预占数据库迁移版本；未知版本或非法字段明确报错。
- **各视图同一算法。** 汇总、时间图、明细、冻结及导出共用目录与结果；按 canonical 展示不丢线路差异。新增分组开关不是首版要求，涉及聚合时遵守 §7。

## 6 问题四：手动填价

### 6.1 现状

- 缺价行只渲染一句「缺少模型费率，当前按最低费率估算」和一个「重新匹配」按钮（`public/app.js` 的 `renderPricingModelList`）。
- 「重新匹配」调用 `refreshPricingAutomatically(true)`，即 `POST /api/pricing/refresh` 的**全局强制刷新**，不是针对该模型。
- `openModelPricing` 在 `!entry` 时直接返回，所以缺价行不可点击、不能编辑。
- 后端其实允许新增普通模型名的条目：`PUT /api/pricing` 会走 `validatePricingCatalog` → `savePricingFile`，新增的普通模型会作为 `modelOverrides` 持久化。
- 但 `validatePricingCatalog` 要求所有内置模型都在、单模型名不允许 `/`、最多 256 个。斜杠线路名即使走 API 也加不进 `models`。
- 没有 `routes` 命名空间，也没有「新增模型」表单。

### 6.2 为什么当前「重新匹配」不能纠正这些缺价

名字、映射和解析能力不变时，`unsupported-provider` 仍会被拒绝，强制重拉六个源不能纠正。调查时 8 个缺价里 7 个属这一类（含冷却中的 `-sg`）。但拒绝不是永久禁用：升级解析器、明确映射或用户绑定变化后应重新评估；`not-found` 保留随目录更新再发现的机会。

### 6.3 建议

- 第一批开放普通缺价模型的手动填价/新增入口，复用现有编辑器与字段覆盖，离线可用。新增项满足必需费率与场景校验；未知不零填，取消不保存，保存可撤销。
- 第二批实现明确线路的手动填价，按 §5.8 保存，可先于 provider-aware 自动发现交付。裸名缺身份仍只能编辑模型价，不能标成线路价已确认。
- 币种、四类费率及现有上下文/峰谷字段沿用校验；新填长短档相同须明确确认，Fast 不默认倍增。来源 URL 可选，来源类型由覆盖层元数据记录；本批不引入历史生效价表单。
- canonical 绑定只确认归属；显式借模型价时显示「模型价假设」。不新增「忽略此模型」，避免通过隐藏流量美化覆盖率。
- 行内区分匹配方式与发现错误，显示原因、最后尝试及实际重试安排；终态在能力变化后可重新评估，可恢复错误仍可重试。
- 第四批再将「重新获取」改成单模型、非强制发现，复用已下载目录；全局「刷新全部价目」单独保留。
- 账本预填为可选后续，只填有证据字段，空缺继续待确认，经用户保存后成为手动覆盖，不自动发布反解价。
- 主看板按查询范围显示最低费率假设及未定价提示，与各视图合计口径一致。

## 7 历史价格、事实保留与聚合边界

### 7.1 本版选择 C：按当前有效价目回算

`pricingVersionForTimestamp(_timestamp)` 当前直接返回活动版本，逐事件估算使用当前有效价目（见 [pricing.js](../../src/pricing.js)）。原调查的汇总只见一个活动版本；事件记录 `price_version` 不能据此解释为展示已按历史生效价计费。

本版沿用 [计价说明](../11-pricing.md) 的 API 等价估算定位，明确展示「历史费用按当前价目重算」。修改模型价、线路价或手动覆盖后，历史估算可以变化，原始 tokens 与来源事实不改写。C 是当前语义和最小实施范围的取舍，不是唯一与事实保留兼容的选择。

A（保存索引时成本）和 B（按真实生效日期选价）本批不实施。A 可以与原始事实同时保留，也可重新估算，但会新增默认展示口径、误价修正和版本维护规则；B 需要可靠历史价格与真实生效日期，抓取时间或 `verifiedAt` 不能代替 `effectiveFrom`。以后确需历史对账再定义，不让它们阻塞明确线路的手动价。

目录修订日、逐来源核验日、最近尝试时间和汇率报价日各有含义；不能把一个 `checkedAt` 或 `priceUpdatedAt` 命名成所有模型的统一最新价，也不能当作历史生效日期。

### 7.2 与历史保留实施计划的接口

[历史保留实施计划](2026-10-22-history-retention-implementation-plan.md)要求保留可恢复事实，汇总不能成为唯一副本，第一版费用继续逐事件计价/memo。这提供 C 的重算条件，但不要求先改 rollup 才能决定 C 或交付费用状态说明。

- 线路成为计价输入时，身份及证据必须进入可恢复事实、费用投影和缓存键；有效线路价及显式绑定变化纳入有效价目版本。只改变证据日期或错误状态不能冒充费率变化。
- 原始模型名已有明确线路时，第一版可先用该身份，不为未来功能建空表或猜填历史未知值。实际新增身份字段时再评估索引迁移和热/冷归档兼容；恢复资料须带齐该版重算所需目录与绑定。
- 线路进入分组、过滤或费用聚合时，rollup 和 DISTINCT 关系不得丢失影响结果的维度。聚合暂不能保真时，费用或该查询族保留逐事件路径；不能把丢失线路身份的聚合行直接交给估算器，也不因缺少 rollup 阻塞所有计价修正。
- 重算、各视图缓存失效、冻结隔离和热/冷路径要有等价验收；不能让实时价目或绑定更新改变旧冻结视图。

### 7.3 与 perf 身份链的接口

复用已确认的响应 ID、home/来源归属及规范化证据；perf 保留测速所需分组，费用保留卖家线路、模型及计价场景。共享底层事实不等于共享整个统计键。provider 字段和 `requestLinked` 布尔值均不能单独证明已完成请求级线路关联。

## 8 唯一交付顺序（B 已启动隔离施工）

本节替代原 P0/P1/P2 和两轮评审的排序。各批按 A/B 实施计划拆小；只有执行记录中的卡才是已派发任务。每批只要求本批验收，不把后续线路或账本验收冒充首批前置条件。

### 8.1 第一批：费用可见性、状态说明与普通模型手动纠正

- 明确 API 等价估算及 C 的历史回算；先显示最低费率假设和真正未定价份额，暂不改旧金额算法。
- 普通缺价模型可手动填价、保存、取消及撤销；未知字段不零填，离线也可完成。
- 返回部分失败，展示价格/汇率独立结果、来源、内置兜底和报价年龄；不等待后台定时器。
- 停止无能力变化时的无效自动重试，保留升级解析器、映射或绑定后的重新评估机会。

### 8.2 第二批：身份明确的手动线路价

- 有效目录 `routes`、手动 `routeOverrides`、兼容加载与原子保存；验证线路身份、名称冲突、容量与载荷。
- 精确线路选价、字段级手动覆盖、自动缓存持续更新和撤销恢复；证据状态不另占费率优先层。
- 缺少可用费率的部分保持未定价，取消缺价默认最低费率补价，显示「已定价部分合计」并提示口径变化。
- 打通本批实际需要的费用投影、版本、缓存与热/冷重算；聚合暂不保真时继续逐事件计算。本批不依赖自动发现或外部账本。

### 8.3 第三批：独立的服务端后台调度

- 启动/到期检查、24h/1h 门槛、来源按需抓取、并发合并、失败保留和关闭清理。
- 保留浏览器触发；服务运行且页面关闭时仍按门槛检查，CLI 不被定时器留住。
- 用户可单独安排本批，不作为第一批状态说明的依赖，也不要求先有账本机制。

### 8.4 第四批：逐提供商扩大自动发现

- 先支持身份、币种、必需费率和档位政策均可确认的来源，按精确键查价；缺字段、全零无免费证据和来源冲突不自动发布。
- 复用下载与通用校验，保留厂商规则，不推广 OpenAI 的 Fast 倍增或上下文假设。
- 行级重新获取和全局刷新分开；官方页面新增能力逐来源交付，不承诺一次覆盖所有缺价。

### 8.5 可选后续：请求关联扩展与离线差异检测

- 需要支持裸名多卖家或账本核验时，先复用并验证请求身份链，再实现可选账本适配、候选核对、反解诊断与手动预填。
- 账本缺失不影响查看和手动纠正费用；读路径不联网，反解不覆盖生效价格。
- 历史生效价、实际支出、订阅分摊、更多展示分组和备用汇率源另行规划，不默认包含。

## 9 非目标与风险

### 9.1 本版不包含

- 用估算替代账单，或本批实现 A/B 历史价格系统、订阅成本分摊。
- 用前缀剥离、后缀、同名、当前配置或 perf provider 猜未知卖家。
- 把账本反解作为自动价源，或每次普通刷新都重新反解。
- 多源平均、增加依赖、通用身份/定价引擎、预先为未来功能建表。
- 隐藏缺价流量提高覆盖率，或承诺消除 7/8 个缺价。
- 为计划修订提前修改产品、真实价目、数据库、日志或并行任务。

### 9.2 风险及处理

- **身份缺失。** 精确命中目录也可能不是该卖家的价；保留依据和场景，不把 matched 当 verified。
- **账本缺失或低覆盖。** 适配器可选；沿用适用价目或显式模型价假设，无依据则未知。原调查 34/约 2,100 的连接覆盖不能扩成全量验证。
- **同源与币种歧义。** 公开目录和网关可能同源；账本证明 USD 等值观测，不证明独立账单或原生币种。
- **部分样本与退化。** 空样本、全零、共线和未覆盖写入/长档/Fast 只支持实际覆盖部分，失败不发布费率。
- **回算与缓存。** C 允许历史估算随价目变化，需明确提示；线路与绑定变化不能漏进版本/缓存，实时更新不能污染冻结视图。
- **持久化与容量。** 兼容旧文件、自动/手动分层、未知 schema、并发保存和载荷上限；失败不写半份文件，不丢旧条目。
- **上游改版。** 抓取成功不等于解析成功，保留旧有效价并显示来源失败；自动来源冲突和手动差异分别处理。
- **并行施工与归档。** 历史保留和 perf 仍可能变化；实施时重新核对接口和实际 schema，不照抄旧行号或预占迁移版本。

## 10 只读复核方法与证据限制

本轮未执行以下请求。复查使用 PowerShell 7（`pwsh`），保留实际观测日期；新观测不得直接冒充原调查快照。

### 10.1 价格与覆盖

```powershell
$pricingSnapshot = Invoke-RestMethod 'http://127.0.0.1:3765/api/pricing'
$pricingSnapshot.usageCoverage | ConvertTo-Json -Depth 10
$pricingSnapshot.automatic.discoveryResults | ConvertTo-Json -Depth 10
```

### 10.2 账本取样

```powershell
$ledgerPage = Invoke-RestMethod 'http://127.0.0.1:3425/v1/magpie/usage/requests?period=30d&limit=500&offset=0&q=opencode-go%2Fdeepseek-v4.1-flash'
$ledgerPage.rows | Where-Object { $_.req -ceq 'opencode-go/deepseek-v4.1-flash' }
```

这只读取第一页，不是全量样本。完整复查需翻页并按可靠记录身份去重，记录窗口和分页期间数据增长的限制；`q` 为模糊搜索，仍须按 `req` 精确筛选。`req` 缺失不能用模型名证明卖家；先核对输入/缓存读写的包含关系和币种口径，再比较金额。

### 10.3 安全核验与反解边界

原稿 `fit.mjs` 示例没有空样本、奇异/近奇异矩阵和非法系数保护，本版移除该可直接复制运行的脚本，不把调查代码作为实现方案。原调查数值保留，本轮没有重算。以后如安排核验工具，应遵守 §5.6，至少覆盖：

1. 来源字段非负、有限，单位和输入/缓存语义一致；优先逐行核对候选价。
2. 空样本、全零费用、缓存列恒零、输入和缓存固定比例时，不发布唯一完整向量；跨日或全量翻页也不自动消除退化。
3. 参数可识别、数值稳定且非负；不得以无主元/条件检查的普通消元作为发布依据。
4. 未覆盖的写入、长档、Fast、峰谷或调价日期保持未知，只报告实际覆盖部分。
5. 同时使用绝对与相对容差，并说明拟合与核验是否使用同一数据；微小拟合误差不代表账单准确度。
6. 线路规则变化时按时间/场景分段，不用同一向量证明整段历史永久同价。

## 11 统一决策记录

两轮评审合并为以下取舍，不再提供相互竞争的执行顺序：

- **费用定位与历史。** API 等价估算，选择 C，明确按当前价目回算；保留事实不排斥另存历史成本，只是本批不增加 A/B 的口径和维护复杂度。
- **首批范围。** 未知份额、普通模型手动纠正与刷新状态说明前移；后台调度独立分批，不把所有刷新信号判为不可信。
- **线路与发现。** 手动线路价可先于 provider-aware 发现交付，不依赖账本或联网；裸名缺身份时不猜卖家。
- **身份复用。** 共享 perf 已有请求证据，不强制使用测速统计键；provider 与布尔 `requestLinked` 不是费用线路连接已完成的证据。
- **覆盖语义。** 自动层继续缓存最新有效值；同对象手动字段优先，未覆盖字段可维护，撤销恢复最新自动值。核验徽标不越过手动覆盖。
- **账本定位。** 可选离线差异检测及经确认的手动预填，不自动发布，也不冒充供应商实付真值。
- **历史保留接口。** 线路影响计价时保全事实/投影/缓存，进入分组或聚合时再落实对应 rollup 维度；逐事件路径可保留，rollup 改造不是选择 C 的前提。
- **证据范围。** 价格、倍率与账本仍是原调查快照；未知不填零，短档验证不推广长档，抓取日不代替生效日。

## 12 分批验收与工作边界

下列是未来实施的验证要求，本轮文档修订不表示产品验收已通过。

### 12.1 第一批验收

- 当前查询范围内最低费率假设和未定价份额可见，分母、来源排除及冻结条件一致；不把子集或重叠诊断重复求和。保留旧金额算法时，合计注明包含最低费率假设。
- 普通模型可新增、编辑、取消、保存和逐字段撤销；非法币种/费率/名称或容量超限明确失败，未知字段不零填、不破坏其他覆盖。
- 部分源失败与汇率失败分别可见，价格时间不被解释为全源成功；手动/自动/内置汇率和报价年龄可区分，失败保留旧有效值。
- 能力不变的拒绝不重复全量抓取；升级能力或显式映射后可重新评估；网络错误可恢复。

### 12.2 第二批验收

- 相同 canonical 的明确线路不串价；裸名多卖家、歧义前缀或缺证据时，线路身份保持未知。明确模型仍可按有依据且标注清楚的模型价场景估算，不因此声称线路已确认；现有免费政策不受新线路覆盖。
- schema 2、旧全量文件、schema 3 按约定加载；自动层更新、手动字段优先、部分覆盖显示混合来源，撤销恢复最新自动值。自动源冲突不覆盖旧有效值或手动字段。
- 无写入/长档/Fast 证据不伪造完整价目；模型价回退是显式假设；缺价不再用最低费率补入「已定价部分合计」。
- 保存失败、并发编辑、名称碰撞、接近条目与载荷上限时不丢旧数据，取消不持久化。
- 修改线路价或绑定后，页面、汇总、时间图、明细和导出使用一致的有效版本并失效缓存；旧冻结视图保持隔离。
- 本批使用的线路事实在备份恢复、无原日志及热/冷重算中保留。未启用对应分组/费用 rollup 时仍有正确逐事件路径，不宣称已验收后续聚合能力。

### 12.3 第三、第四批及可选后续验收

- **后台调度：** 启动/到期、成功/失败门槛、来源按需抓取、并发合并、断网保留、页面关闭、服务关闭及 CLI 退出分别验证；用可控时钟验证门槛，不依赖长时间真实等待。
- **自动发现：** 明确提供商身份；同名跨卖家、来源冲突、全零无免费证据、未知长档/Fast/写入、厂商特殊规则与容量均有正反例，不为提高覆盖率降低校验。
- **可选账本：** 缺失或 schema 漂移不影响正常估算；验证请求归属、四项 token 语义、低覆盖、退化与字段级证据。反解只产生诊断/候选，经确认才保存为手动覆盖。
