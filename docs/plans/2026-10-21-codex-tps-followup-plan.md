# Codex TPS 后续改进计划

日期：2026-10-21。状态：调查与确定性验证完成；A 未证明原生请求计时，B 现有归属证据不足，C 跳过，未改运行时代码。详见[执行记录](../validation/2026-10-21-codex-tps-followup/README.md)。本轮借鉴 [Claude Code 方案](2026-10-21-claude-code-tps-plan.md)，改善 Codex 的持续计时能力和活跃会话下的可用性；承接已上线的 v2 方案（工作区文件 `2026-10-21-tps-measurement-correction-plan.md`，随功能另行提交）。

## 1. 目标与边界

- 查清原始 rollout 能否提供可靠的逐请求计时，减少后续请求对外部计时导入的依赖。
- 量化“缺一个请求时长就淘汰整轮”的损失。
- 让可证明独立的历史线程不被其他活跃文件阻塞。
- 沿用现有 UI、目录筛选、轮级 n/P10/P90 和 pooled 均值。请求级采样只评估收益，本轮不暗改粒度。

本轮执行不写真实库、不重启服务；不接管 Claude 或其他并行任务的修改。

## 2. A：一次调查，同时回答计时与覆盖问题

先复用已审核的六轮、326 请求及其两个 rollout；确有结构缺口时最多补六个 rollout。优先覆盖不同模型、工具循环、主/子线程；重试有样本就纳入，没有则明确未覆盖。已有结论不重复扫描，变化中的文件本轮跳过，不循环等待冻结。

工作内容：

1. 检查原始事件，再看 `codex-jsonl.js` 当前丢弃了哪些字段。列出每个 response ID 是否有可配对的调用起点、响应终点、输出和终态。
2. 对具备身份依据的本地计时候选，与现有审核计时逐请求比较：输出是否相等、时长误差中位数/P99/最大值、pooled 偏差，并解释最差样本。
3. 对同一批已结束轮次统计：全部请求数/输出、已有有效计时覆盖、完整轮数，以及因少量缺失被连带丢弃的已计时请求/输出。计数未知时单列，不能填零或假装全量覆盖。

采用条件：请求身份明确、计数范围一致、计时包含等待与完整响应，排除后续工具执行和用户空闲；重试范围须独立说明。数值接近不能替代边界证明。

停止条件：没有能关联请求的起点，或无法排除工具/调度间隙，即结束本地计时分支。保留现有审核导入，不再尝试相邻 usage 差值、item span、整轮减工具时间等补法。

产物只保留一个可复跑脚本和一份简短滚动记录，记录采用/拒绝理由与脱敏反例；不保存正文、凭据或原始账本，不做例行哈希清单。

## 3. B：缩小活跃文件变化的影响范围

此项与 A 独立，可并行；主要检查 `usage-store.js` 的发布前复核、现有线程依赖和 `codex-thread.js` 的归属规划。

先写一个确定性反例：历史线程 H 已发布，另一线程 L 读取期间追加；验证 H 是否被整 home 阻断。然后复用已有依赖关系，只让**归属与完整依赖集仍能证明、内容未变**的线程继续发布，变化线程保留重试。

必须同时守住：

- 新文件、删除文件、多 header 或身份转移使依赖无法确定时，保留必要的阻断；不能仅凭“旧文件以前属于 L”就断言本次变化只影响 L。
- 失败不覆盖最近一次成功结果；保留的旧发布维持原版本/时间，不伪装成本轮刷新成功。用户排除的目录仍须立即排除。
- 同一线程多个 rollout、跨线程重复响应、身份从 H 转移到 L，沿用现有冲突规则。
- 内存、SQLite 和 API 对相同输入的结果一致；重复同步与重开稳定。

若现有归属证据不足以安全隔离，记录具体缺项并保留原规则，不扩大成新存储框架。

## 4. C：证据通过后才接线

A 能证明本地计时成立时，在现有 reader → request timing → turn builder 链路接入，优先复用当前接口。保留时间来源区别与冲突检查，不把时间戳推导伪装成显式时长；本地值与已导入值存在合理写盘差时，不直接合并成同一规范证据或制造假冲突，依据 A 的边界证明固定取值规则。

接线必须覆盖：普通与工具请求、时间倒退、陈旧起点、无终态、重试、重复/冲突响应，以及后续追加请求无需人工逐条导入即可更新。未认证结构继续使用既有缺失路径。若改变候选计算或投影形状，按现有版本机制失效重建，不能让旧缓存掩盖新逻辑。

A 不通过则跳过 C，B 可独立交付。覆盖统计若表明请求级采样收益明显，另列一次明确的口径改版建议，说明 n/分位、日期归属与旧数据兼容成本；本轮完整轮公式不变。

## 5. 验收与收口

1. A 的调查脚本自检与 B/C 的确定性反例各跑一次；只重跑被实际修改影响的测试。
2. 完成内存/store/API 对拍，再跑 typecheck、目标文件 lint/format；最终整合只跑一次全仓。
3. 独立临时库验证历史重建和后续追加，沿用现有页面核对数值、目录/时间筛选，无需新增 UI。
4. 共用一份滚动记录，结论明确为“本地计时接入/不成立”“活跃隔离完成/证据不足”“请求级是否值得另做”。不拆多轮 handoff，不把试验通过写成全来源认证。

执行顺序：A、B 可并行 → A 通过才做 C → 一次整合验收。真实库导入和正式服务切换在实施结果可审核后单独安排。
