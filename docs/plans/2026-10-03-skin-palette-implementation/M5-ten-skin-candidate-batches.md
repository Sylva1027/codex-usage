# M5：十套风格输入、双皮肤批次与选择收敛

> 2026-10-18：当前执行使用[恢复说明](../2026-10-18-skin-palette-recovery.md)。先看真实配对预览，再对有价值的候选做完整捕获；未完成验证仍标 pending，不得自动 ready。下面原批次目标保留，旧的工具修补队列不继续展开。

前置：M5.1 在 M0 后即可开始；M5.2—M5.7 等待 M2—M4 可用。遵守[总计划](../2026-10-03-skin-palette-implementation-plan.md)。保留 7 个原任务编号；实际执行改为[输入/生成/单候选捕获/视觉/结算小卡](M5-batch-subtasks.md)。双皮肤编号是汇总节点，不再是一张长执行卡。

允许修改：`scripts/skin-palette/profiles.json`、本轮候选/评审/截图/报告/选择记录与 handoff。产品配色只读，工具公式和 policy 不在此模块自由修改。

## M5.1 十套初始配方

各节参数、调整权限与完成标准保留；领取任务时按[M5 小卡与实例](M5-batch-subtasks.md)和[执行规则](execution-and-subagents.md)固定输入、输出、停止点。

**目标：** 先明确十套分工，再逐套求解，避免其他 agent 各自选相近的蓝紫灰。

初版每皮肤字段固定为 `skinId / version / styleTitle / rationale / identityHex / identitySource / surfaceH / surfaceC / pageL / accentC / lockedFields`。`pageL` 有 light/dark；version 起始 1。H 在 `[0,360)`，surfaceC 在 `[0,0.045]`，pageL light 在 `[0.88,0.98]`、dark 在 `[0.15,0.31]`，accentC 在 `[0.045,0.24]`。本轮没有用户指定锁色项，首版 `lockedFields=[]`；新锁色要求须由协调者补充确切映射和验收后再支持，不静默忽略，也不因为已发布或本表有默认值自动锁定。

执行步骤：

1. 回看角色源色注释/装饰图，核对上述 HEX 来源并将源文件、源色组写入 `identitySource`。如源文件已变，记录差异，不凭记忆改为官方色。
2. 编写十份明确 rationale，说明浅深共享什么身份、区别最近邻靠什么；不使用“美观高级”作为唯一解释。
3. 用 M0 `validateProfiles` 校验 ID、单位、有限数值、12 token 之外无产品配置；surface 参数保持在 M2 可用范围。
4. 生成前保留当前 profiles 快照及摘要。初版按本表执行，不先让每个 agent 挑新的色环位置。

调整权限：M5 可以基于实际失败/用户反馈调整**本卡负责的皮肤**，每次记旧值、新值和原因并增加 version。首轮允许 surfaceH ±12°、surfaceC ±0.010、pageL ±0.030、accentC ±0.040；accent H 仍取身份锚，不更换身份源。超此范围或改身份锚先给协调者提交具体备选，不自行把十套重新分配。

验收：十套均有可机读配方和可解释的分工；没有已发布款“沿用旧值”的特殊分支；输入可追溯，默认不锁旧颜色。

## M5.2 ChatGPT / Grok 试点

**目标：** 两种最有价值的困难组合先证明流程，再扩展八套。

任务分为固定小步骤：

1. 仅生成 `chatgpt,grok`，检查每款 3 个 a/b/c 起点及 rejected 原因。
2. 按**一候选一捕获命令**顺序执行 M4；每结束一组浅深就写证据，不等六组全跑完才保存。
3. 对两款各保留 2—3 个 ready 候选，查看原尺寸与互动局部。ChatGPT 重点核查深色主/次文字与蓝色小字；Grok 重点核查浅色金色小字和填充/选中态。
4. 做代理视觉初筛，补 style 理由与实际最近邻；报告不展示失败候选作为可选项，但保留其诊断入口。
5. 若不足两组，按 M5.1 权限修正配方重跑；试点初轮加修正轮合计最多两轮。仍不足时写明确原因和具体下一步，不能放宽文字阈值或无限调色。
6. 将得到的生成耗时、必要角色失败、测量可靠性和候选重复情况交回协调者。工具/阈值确需改动时回原模块单独修复，更新版本并重测，不在 M5 私改。

验收：两款各至少 2 组实际页面浅深 ready 候选，有首屏、状态、视觉意见和完整参数；或准确标记阻塞，没有假 PASS。用户对试点的主观反馈可以待回复，其余工程与配方仍可继续；不能代填用户选择。

试点后固定 policy/roles/生成算法版本，再做剩余批次。若后续必须改工具公共规则，前面受影响候选重测，不能一半使用旧门槛。

## M5.3 Claude / Mimo 暖色批次

只调整这两份 profiles，其他皮肤输入只读。依次：生成 → 单候选捕获 → 硬门槛 → 原尺寸视觉初筛 → 双皮肤比较 → handoff。

重点：赤陶与橙色小字在浅色按钮/凹槽上通过；深色不发脏；两款暖底与 Grok 的金色能区分。不能把两款统一换成同一个棕色来解决可读性。

验收：每款 2—3 组成对 ready；与试点至少有同尺度对照；没有旁改已发布 Claude 为“只修文字”。每皮肤最多一轮局部配方修正，仍失败时单列原因，不扩成十套重算任务。

## M5.4 GLM / Muse 蓝色批次

流程同 M5.3，一次只生成并评审两款。

重点：GLM 表面接近中性但不能全白失去凹凸；Muse 暖底与蓝强调协调；与 ChatGPT 冷底的区别在实际页面可辨。深色 mode 也参与区别，不能只凭浅色六个色块判定完成。

验收：每款 2—3 组成对 ready；三种蓝系至少能解释背景冷暖、强调彩度/明度和装饰差异；局部修正预算同 M5.3。

## M5.5 DeepSeek / Kimi 沉稳批次

流程同 M5.3，只调整这两款。

重点：低彩度表面保留陶瓷层次；深色主/次文字、placeholder 和图表标签余量足；Kimi 的灰度不能靠降低次要文字亮度体现；DeepSeek 避免与 ChatGPT/Qwen 看成同一款。

验收：每款 2—3 组成对 ready；角色关闭和聚光开启时文字仍通过，原尺寸有证据；局部修正预算同 M5.3。

## M5.6 Gemini / Qwen 紫色批次

流程同 M5.3，只调整这两款。

重点：Gemini 粉调与 Qwen 深紫灰分开；高光不洗成无层次纯白；深色保留身份，不能变成相同黑灰配浅紫按钮。

验收：每款 2—3 组成对 ready；与 DeepSeek/ChatGPT 的近邻提醒经实际对照处理；局部修正预算同 M5.3。

## M5.7 十套整体协调与有效选择

**目标：** 不以五个各自合格的小批次代替十套整体完成。

步骤：

1. 将五个批次的有效候选合成新的总 CandidateSet。只合并完整、版本相容的对象；不改旧 candidate 的 token/ID/hash。总集重新计算 setHash，保留原批次摘要与证据来源。
2. 核对每个候选的 profileSnapshot 与当前该皮肤配方相符；公共 policy/roles/derivation/实现摘要必须相容。其他皮肤的配方调整不自动使未变的候选失效，但任何实际影响该候选的规则变更都需重跑。
3. 汇总新 assessments 和 captures-index，分别验证 candidateHash 与原证据。不能为复用截图伪填新的 sourceHashes；只允许登记未变化的依赖和原始出处。
4. 提供十套同尺寸 light 网格、dark 网格以及各套浅深配对原图。对每套列最近邻、区别点、代理推荐和第二选择；推荐不等于选定。
5. 仅回调被认定过于相似或材质不足的皮肤，一次最多两款。每次产生新的候选和证据，旧结果保留。候选 ID/hash 变化后，旧用户选择不静默转移。
6. 用户按皮肤选一组浅深候选；允许一次选择多套或直接表达“这个更暖/更沉稳”。代理把反馈转换成受限配方修正，无须要求用户填 HEX。用户明确授权代选时记录授权原话和实际推荐结果。
7. 最终 `selections.json` 恰好十项，绑定最新总集与 assessment 摘要，每项指向 ready candidate 的准确 hash；用 M0 validator 和 `review-cli verify --require-selections` 验证。

验收：十套均有新的候选、真实页面和可解释差异；十套选择齐全、未过期且来自真实用户决定或明确代选授权。没有用户选择时交付报告与 pending 清单，M6 不执行正式替换；其他已完成结果保持。

模块出口：十套完整有效选择和可追溯总报告。所有正式色值仍保持基线，等待 M6。已发布五套与延期五套在此模块的完成口径一致。
