# GPT-6.1 Sol 计价缺口调查与改进计划

> **历史归档 · 2026-10-01**。原路径：`docs/gpt-6.1-sol-pricing-improvement-plan.md`。相关实现已纳入提交 `28568ef`。正文中的旧进度、测试数字、路径与施工指令保留当时语境，不作为当前任务。现行说明见[计价与自动更新](../../11-pricing.md)，遗留验证见[任务清单](../../02-tasks.md)，资料关系见[本批归档索引](00-index.md)。

调查日期：2026-09-30（北京时间）。状态：调查完成，待实施。

实施与交接请使用独立的 [Implementation Plan](gpt-6.1-sol-pricing-implementation-plan.md)。本页保留调查背景与当时快照；实施文档包含后续工作区变化的兼容要求（包括已新增的 `-free` 规则）。

本次只编写计划与文档索引。没有修改业务代码、运行中的价目、用户价格文件或原始用量日志。工作区已有 DSH、自动计价等未提交改动；以下结论以当前工作区及本机正在运行的服务为依据。

## 1. 结论与影响

`gpt-6.1-sol` 已被正常识别和统计，但内置价目没有它。自动更新只刷新内置模型，无法把上游新模型补入本地价目。计价弹窗只展示能匹配到价目的模型，因此在用列表与全部列表都看不到它。

这个缺口也影响费用：记录进入 `unknown-model-price-minimum-scenario`，使用同币种价目中各类 token 的最低费率估算，明显低于 GPT-6.1 Sol 的公开价格。usage 的 token 数量无需修复；需要修复价目覆盖和缺价可见性。

推荐按三个阶段实施：先补上 6.1 sol 的独立官方费率，再让缺价模型始终可见，最后支持从实际用量中发现新模型并可靠补录。不能把 6.1 sol 直接映射成 6 sol：两者的缓存命中费率不同。

## 2. 已核实的证据

### 2.1 本机服务与索引

- `GET http://127.0.0.1:3765/api/pricing`：价目有 85 个模型，没有 `gpt-6.1-sol`。
- 自动价目最近更新时间为 2026-09-30 14:36:59，自动匹配 25/85；缓存的 `pricePartialFailure` 为 `false`。更新成功不代表所有实际使用模型都有价格。
- `GET /api/summary` 的 `metadata.harnessModels.Codex` 包含 `gpt-6.1-sol`，费用汇总的 `minimumRateModels` 也包含它。
- `~/.codex-usage/pricing-auto.json` 没有 6.1 sol；本机没有 `pricing.json` 手动覆盖文件，因此这次不是旧手动配置覆盖了新模型。
- 2026-09-30 15:17:22 的只读索引快照中，6.1 sol 有 27 条事件、1,802,869 个 tokens。最大单次请求输入为 133,884，全部为短上下文，缓存写入已知且为 0，服务档位全部为 `unknown`。这是调查快照，后续新记录会改变数量。

对这 27 条事件，在独立 Node 进程中使用同一份在线价目计算，再仅在内存中加入官方 6.1 sol 条目：

- 当前估算：`$0.009776382`；全部 1,802,869 tokens 标为最低费率估算。
- 补入官方价目后的试算：`$0.6107076`；未知模型造成的最低费率标记消失。
- `service-tier-unknown-standard-scenario` 仍保留，因为事件没有明确 Standard/Fast 证据。

试算使用项目现有的“服务档位未知时按 Standard”假设，表示 API 等价估算，不代表实际账单或订阅扣费。没有向运行中的服务提交价目。

### 2.2 上游已经有价目

2026-09-30 15:16 左右读取了项目实际使用的两个公开来源：

- [Models.dev 数据](https://models.dev/api.json) 的 `openai.models["gpt-6.1-sol"]` 已存在，包含四类短上下文费率及 `272000` 阈值的长上下文档。
- [LiteLLM 数据](https://raw.githubusercontent.com/BerriAI/litellm/main/model_prices_and_context_window.json) 的 `gpt-6.1-sol` 已存在，`litellm_provider` 为 `openai`，含短、长上下文和 Priority 费率。
- 将这两份真实 payload 交给当前解析器和默认价目，两者均没有产生 6.1 sol patch。

因此，即使现在再次点击“立即更新”，当前实现也无法补入这个新模型。网络超时、上游未发布价格、大小写差异都不是本次的直接原因。

### 2.3 代码链路

1. **usage 按日志模型标识统计。** [src/usage-core.js](../../../src/usage-core.js) 的 `turn_context` 分支直接读取 `payload.model`（调查时第 1030–1032、1401–1403 行），事件不依赖内置价目是否收录。
2. **价目缺少新模型。** [src/pricing.js](../../../src/pricing.js) 的 `MODEL_PRICES` 包含 `gpt-6-sol` 等条目，没有 `gpt-6.1-sol`；`PRICE_ALIASES` 也没有它。
3. **自动更新是已有模型的补丁更新。** [src/pricing-auto.js](../../../src/pricing-auto.js) 的 `modelsDevPricePatches()`、`liteLLMPricePatches()` 都遍历 `catalog.models`。而 [src/pricing-store.js](../../../src/pricing-store.js) 的 `refreshAutomaticPricing()` 给两者传的是 `getDefaultPricingCatalog()`，所以不在内置价目的远端模型不会被读取；只存在于手动/自动扩展中的模型也不能自动刷新。
4. **未知模型仍产生一个费用数字。** [src/pricing.js](../../../src/pricing.js) 的 `normalizeModel()` 没匹配到条目后，`minimumRatesFor()` 从同币种价目取各 token 类别的最低价；`estimateEventCost()` 添加 `unknown-model-price-minimum-scenario`，状态为 `minimum-estimate`。
5. **展示列表提前过滤缺价模型。** [public/app.js](../../../public/app.js) 的 `catalogKeysForNames()` 只返回精确或前缀匹配成功的 catalog key；`pricingHarnessGroups()` 使用这些 key；“全部”则直接遍历 `catalog.models`，两条展示路径都会漏掉它。
6. **覆盖率的分母只包括价目条目。** `getAutomaticPricingStatus()` 的 `unmatchedModelCount` 是“已有条目中未自动更新的数量”，没有计算“实际使用但完全没有条目的模型”。

另一个相关缺口：后端会识别 `gpt-5.6`、`gpt-daybreak-blue-latest` 别名，前端 `catalogKeysForNames()` 没有对应别名规则。修复新模型可见性时应统一解析，避免再次出现费用能匹配而列表匹配不到的情况。

## 3. 6.1 sol 的目标费率

以 2026-09-30 实际打开核对的 [OpenAI 模型页](https://developers.openai.com/api/docs/models/gpt-6.1-sol) 和 [官方定价页](https://developers.openai.com/api/docs/pricing) 为依据，单位为 USD / 百万 tokens，字段顺序为 `input / cachedInput / cacheWrite / output`：

- Standard 短上下文：`2 / 0.10 / 2.50 / 10`。
- Standard 长上下文：`4 / 0.20 / 5 / 15`。
- Fast 短上下文：`4 / 0.20 / 5 / 20`。
- Fast 长上下文：`8 / 0.40 / 10 / 30`。

单次请求输入 **严格大于 272,000** 才使用长上下文档，整次请求适用对应费率；不能用一个时间范围累计的输入量判档。Fast 为 Standard 的 2 倍，Priority 按现有服务档位规范视为 Fast。

当前 6 sol 的 Standard 缓存命中费率为 `0.20 / 0.40`，6.1 sol 为 `0.10 / 0.20`。因此应保留两个独立条目。

本计划继续采用项目已有的 Standard/Fast 估算范围；Batch、Flex、地区附加费和其他工具费用不在本次接入范围内。日志没有明确服务档位时，继续保留 Standard 场景提示。

## 4. 阶段 P0：补齐当前模型，修正费用

### 改动

1. 在 `src/pricing.js` 中增加独立的 `gpt-6.1-sol` 条目，填写上述四档费率、`currency: "USD"`、官方来源及 `longContextThreshold: 272_000`。
2. 更新内置价目版本与此次核对日期；说明这是本次新增条目的核对日期，不能据此宣称全部厂商价目都在当天逐项核对。
3. 不增加 `gpt-6.1-sol -> gpt-6-sol` 别名。带日期后缀的真实标识可按已有、已验证的模型后缀规则匹配，未经核实的其他名称不猜测归属。
4. 复用默认价目、自动缓存、手动覆盖的现有合并顺序。检查旧全量价格文件及 schema v2 的字段覆盖文件均能补上新条目并保留原有手动值。
5. 升级后重启本地服务并刷新页面，使运行进程加载新内置条目；不需要清空 SQLite 或重新解析历史日志。当前费用按活动价目读取时重算，服务指纹已经包含价目版本。

### 验收

- `/api/pricing` 有独立 6.1 sol 条目；“在用”和“全部”均能搜索到并编辑。
- 离线且没有价格缓存时仍可估价。
- 已知、完整明细事件不再含 `unknown-model-price-minimum-scenario`，`minimumRateModels` 不再因 6.1 sol 收录缺失而包含它。
- `serviceTier: "unknown"` 的事件仍保留服务档位不确定提示；不能因为模型有价就把全部费用标为已知实际费用。
- 原有 6 sol、DSH、人民币模型、汇率与手动覆盖行为保持一致。

P0 可以独立交付，及时修正现在的费用；无需等候自动发现机制完成。

## 5. 阶段 P1：让所有在用模型的计价状态可见

### 统一模型解析

新增纯函数模块 `public/pricing-models.js`，由后端 `src/pricing.js` 和前端 `public/app.js` 共用。模块只处理模型名称和给定价目，不依赖 Node、DOM 或网络。

- 统一 trim、大小写、显式别名和已支持的后缀规则。
- 返回 `{ rawModel, catalogKey, matchType }`，其中 `matchType` 为 `exact / alias / suffix / missing`。
- 精确匹配优先；别名目标必须确实存在；多个后缀候选按更长的 key 优先，避免较短名称抢先匹配。
- 这次不把任意新版本、小数版本、提供商前缀或未知后缀当成官方别名；相关名称只有经确认才增加映射。
- 不与尚未实施的 OpenCode `-free` 规则混合；其后续优先级需在独立计划中接入共享解析器。

同时修改 `src/static-export.js` 的显式模块内联闭包，并遵守 [静态导出约定](../../13-static-export.md)。不能仅增加浏览器 import 而漏掉离线 HTML。

### 列表与状态

1. “在用模型”以 `metadata.harnessModels` 的实际模型标识为起点。已匹配条目沿用现有编辑行；缺价模型显示自己的名称及“缺少模型费率，当前按最低费率估算”。缺价行应可查看处理说明。
2. 对已匹配条目保留现有跨 harness 去重；对缺价模型按实际 harness 展示，避免整个分区变空。别名行明确展示实际使用名称及对应计价名称。
3. “全部”显示 `catalog.models` 与实际使用缺价模型的并集，避免切换范围后缺价记录又消失。
4. 先提供“重新匹配”动作和可读提示；不要用全零费率创建假条目。完整的新增模型手动费率编辑器可后续接入，不能复用只会编辑已有条目的 `openModelPricing()` 并让点击无反应。
5. 在 `public/i18n.js` 增加中英文文案，必要样式放入 `public/styles.css`；缺价状态使用文字，不能仅靠颜色区分。

### 接口补充

`/api/pricing` 增加独立的用量覆盖信息 `usageCoverage`，建议字段：

```text
usedModelCount
matchedUsedModelCount
missingUsedModels: [{ model, harnesses }]
```

这里的计数以规范化后的实际使用模型标识计数，别名匹配成功也算覆盖；保留现有自动更新覆盖字段，二者表达不同问题。

- “未自动匹配”表示有价目但没有从本轮远端来源得到更新。
- “缺少模型费率”表示连本地可用条目都没有，费用正使用未知模型回退。
- 任一缺价实际用量模型存在时，界面给出明确数量；不能仅用更新时间和 `25/85` 让用户推断覆盖完整。

覆盖信息由后端从已初始化的索引模型清单计算，前端复用共享解析器作为旧服务缺少新字段时的兼容路径。不得通过本机 HTTP 自调用获取模型清单。

## 6. 阶段 P2：按实际用量发现并补录新模型

### 补录范围和更新流程

首轮只支持能够验证的 OpenAI USD 文本模型，候选来自实际索引；不把整份远端目录全部导入。

1. 后端把去重后的实际使用模型名称传给 `refreshAutomaticPricing()`；远端请求仍只下载公开目录，不上传名称、用量、路径或会话内容。
2. 更新已有模型时，候选价目从 `automaticBase()` 取默认条目与已缓存扩展条目的合并结果，而不是仅用 `getDefaultPricingCatalog()`。手动覆盖仍最后应用，不能拿手动费率当远端字段缺失时的基础值。
3. 将“更新已有条目”和“发现新增条目”分成独立解析路径。当前 patch 结构只包含部分字段，不能直接作为一个新模型保存。
4. 新条目只接受精确的 `openai` 提供商和模型 ID；LiteLLM 需验证 `litellm_provider`。检查文本计价能力、USD 语义、名称及费率合法性，媒体、音频、图像专用模型排除。
5. 新模型的四类费率必须有可靠字段或经过核实的规则。缺少缓存命中/写入费率时不能借用别的模型，也不能默认为 0；证据不足则保留缺价/待核实状态。
6. 长上下文要有明确阈值和完整档位；不能把模型最大上下文当成收费阈值，也不能默认所有 OpenAI 新模型都是 272K。6.1 sol 的 272K 规则已经官方核实，可明确接入。
7. 新增成功时生成完整 `PriceModel`，存入自动缓存，重算活动价目版本。重启后仍可离线使用；下一轮更新能继续刷新该扩展条目。
8. 来源优先级沿用 Models.dev、LiteLLM；手动字段覆盖优先于两者。已有有效缓存不能因为来源短暂缺失就删除。

对已有模型，缺失的某个远端字段仍可保留已有有效内置/自动值，但须区分“本轮刷新字段”和“沿用字段”。已有 patch 的宽松更新条件不能用于首次创建条目。

### Fast、来源和冲突

- 可靠 Fast/Priority 数据可更新独立 Fast 档；缺少可靠数据时保留内置 Fast 档。新模型若只能使用项目的 Fast 2 倍假设，应明确标为推算，不宣称自动取得官方 Fast 价。
- 单个 `source` 无法准确表达“Standard 来自远端、Fast 沿用内置”的混合情况。新增自动缓存元数据，按模型/档位记录来源与核对时间；没有取到的档位不能跟随全局日期自动变成“已更新”。
- 两来源对同一完整档位有差异时记录冲突详情，使用上次已核实值或内置官方值，并标为待核实；不能把两个不一致档位的字段拼成一套未经验证的费率。
- 价格版本按最终有效费率/结构变化更新；覆盖状态或来源信息变化也应触发相应界面状态刷新，不能只依赖费用版本。

### 新模型出现后及时触发

当前成功更新后通常 24 小时才再获取价格。如果新模型在这期间首次出现，不能再等待下一天：

- 在完成用量加载后检查新增缺价候选，候选集合变化触发一次价格发现，汇率继续使用原有独立调度。
- 候选请求合并并去重；相同缺价模型失败后一小时重试，手动“立即更新”可强制重试。新增候选采用短防抖，不能每次 60 秒用量轮询都发起同样下载。
- 索引未初始化时推迟发现到首次用量加载完成，避免价目初始化与索引加载互相等待。
- 离线、部分来源超时或字段不足时继续保留旧值，并清楚报告哪些实际使用模型仍缺价。

### 现有容量限制

`validatePricingCatalog()` 当前最多允许 100 个模型，已有 85 个；`PUT /api/pricing` 的请求上限是 128 KiB。自动扩展必须一起处理这两个限制。

首轮保留现有上限，按实际使用候选补录，到容量上限时逐模型返回明确的 `catalog-capacity` 状态，优先保证已有价目可用；不允许第 101 个模型使整次刷新回滚而丢掉前面有效结果。候选排序与接纳顺序固定，新增手动条目仍走同一验证边界。若未来需要扩容，应同时调整请求字节限制并单独评估，不能只去掉模型数量校验。

## 7. 实施顺序与验收测试

建议三个独立变更：

1. **P0：6.1 sol 官方价目与迁移回归。** 修改 `src/pricing.js`、`test/pricing.test.js`；在现有三路一致性测试里加入该模型。优先验证离线默认费率与历史重算。
2. **P1：共享解析、缺价展示与用量覆盖率。** 修改 `public/pricing-models.js`、`src/pricing.js`、`public/app.js`、`src/server.js`、`src/static-export.js`、文案/样式及相应测试；同步静态导出文档。
3. **P2：可靠补录、持续更新和重试状态。** 修改 `src/pricing-auto.js`、`src/pricing-store.js`、服务调用与状态展示、相关自动更新/服务测试，更新中英文 README 中自动更新范围的说明。

### 必须补齐的回归场景

- 短上下文 Standard 样例：输入 10,000、缓存命中 5,000、写入 0、输出 1,000，费用必须是 `$0.0205`；当前未知模型回退为 `$0.00029`。Fast/`priority` 为 `$0.041`。6 sol 同样样例仍为 `$0.021`。
- 缓存写入样例单独验证写入费率，不能只用写入为 0 的 fixture。
- 272,000 和 272,001 的请求输入边界，确保严格大于才切换长档；未知上下文与未知服务档位保留提示。
- 老全量文件、v2 手动覆盖、已存在的自动缓存、首次离线启动，新增模型都不会被旧文件遮掉；已改字段仍优先。
- 只有 usage、没有 catalog 的模型在“在用”和“全部”都可见；别名已计价也应在列表中可见；中英文、搜索与 harness 分组一致。
- 两个上游都含新模型但本地未收录：产生完整新条目并保存；重启后保留；下一轮能更新该条目。
- 缺费率、错误提供商、收费阈值缺失、长档不完整、媒体模型、非法名称、超过容量、来源冲突均有明确结果，且不破坏旧价目。
- 同日成功更新后新增缺价模型能发起发现；来源失败遵守重试与合并请求规则，不形成每分钟下载循环。
- 手动覆盖不被自动刷新覆盖，价目编辑版本冲突仍返回 409；新增价格使汇总和时间轴更新。
- 内存、SQLite、静态导出在同一事件与价目下费用一致；静态 HTML 无外部脚本/模块依赖，旧导出保持导出时价格，新导出使用新价。

实施阶段运行相应定向测试后，再运行：


这些全量检查尚未在本次调查中执行。新增共享前端模块后，还必须按静态导出约定在无 `node_modules` 的场景验证导出，并通过浏览器检查产物。
